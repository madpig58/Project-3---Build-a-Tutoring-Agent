Context and memory in an agent: what the model sees and what it keeps

By the end of this lesson you can decide, for the makerspace assistant, what stays in context during a request, what is saved between sessions, and how it finds the right manual page, and you can defend each choice by its effect on cost and accuracy.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, stay inside a small model budget, and remember each student's training between visits. All three problems come down to one question: what text does the model get on each step? That is the choice you will defend at your design review.

Warm-up 3 min

Think of a small game. While it runs, the player's position and the list of enemies sit in RAM, and they change every frame. When the player quits, the process ends and RAM is wiped. The game keeps progress only if it wrote a save file on purpose, such as {"level": 4, "keys": 2}.

Your assistant has the same two storage problems. Some text matters only while one request runs. Some facts, like a student's training status, must survive until the next visit. This lesson answers three design questions: what stays in context, what is saved, and how the right manual page is found.

First, two recall questions from earlier lessons. Answer in your head, then check.

Recall 1: the loop

A student asks, "Can I book the 3D printer on Thursday afternoon?" Name, in order, the four things that happen in one trip around the loop, and say what ends the loop.

Check your answer

The model asks for an action, such as a calendar check for the printer on Thursday. The program runs it. The result goes back to the model. The model then either asks for another action or writes the final answer. A final answer, or a step limit, ends the loop.

Note who does the work: the model only asks, and the program carries the action out. That is why an agent needs a program around the model.

Recall 2: what the model knows

Besides what it learned in training, what does the model know when it writes its next token?

Check your answer

Only the text it is given. A tempting answer is "it also knows my earlier chats". It does not: an earlier chat is known only if its text is given again. Today we look at exactly what that text is.

Tokens and what fills the context window 4 min

Start with a concrete case. A student asks the assistant, "What nozzle temperature for PETG on the Prusa?" The assistant decides to search the manuals. What exactly does the model read on its next step?

First, a unit. A token is a small chunk of text, often a short whole word or a piece of a longer one. The model reads and writes tokens, and tokens are what get counted and billed. The phrase "Nozzle temperature" might be split as Noz + zle + temperature. That split is illustrative: real splits differ by model. As a rough, uncited rule of thumb, one page of a manual is about 500 to 800 tokens.

Second, a name for what the model reads. The context window is all the tokens the model can use when it writes its next piece, including its own reply. It has a fixed maximum size. The Claude docs call it the model's "working memory" and note that it includes the response itself (Claude Platform docs: context windows).

Two pieces to know before the example. The system prompt is fixed instructions for the assistant, such as its role and rules. Tool definitions are descriptions of the tools it may ask for.

Worked example: filling the window, step by step

All token counts here are illustrative, invented to show the pattern.

  1. The system prompt goes in first: the assistant's role and rules, about 400 tokens. The student never sees it, but the model reads it.
  2. The tool definitions go in: check_calendar, book_machine and search_manuals, about 600 tokens together. The model can only ask for search_manuals because it reads this description.
  3. The student's message goes in: about 15 tokens. So far the window holds 400 + 600 + 15 = 1,015 tokens.
  4. The model replies with a request for search_manuals: about 40 tokens. The reply counts too, because it is sent back in on the next step.
  5. The program runs the search and adds the tool result, a manual excerpt: about 1,500 tokens.
  6. At the next step the window holds 1,015 + 40 + 1,500 = 2,555 tokens. The student typed 15 of them, under 1%.

Here is the same step as a Python sketch. It shows the idea, not any specific library's exact API.

messages = [
    {"role": "user", "content": "What nozzle temperature for PETG on the Prusa?"},
    {"role": "assistant", "content": "request: search_manuals('PETG nozzle temperature')"},
    {"role": "user", "content": "tool_result: <manual excerpt, about 1,500 tokens>"},
]
reply = call_model(system=SYSTEM_PROMPT, tools=TOOLS, messages=messages)

role says who wrote each entry. Here the program's tool results are stored under "user" because they come from outside the model; real libraries label them differently. system and tools travel with every call. messages is the history, which includes the tool result. The window counts all three, plus the reply.

Size matters for more than cost. The Claude docs say that as token count grows, accuracy and recall degrade, a phenomenon they call "context rot", so curating what is in context matters as much as how much room is left (context windows). Anthropic's engineering team states the goal as the smallest possible set of tokens that actually help the model (Effective context engineering for AI agents).

A common mix-up

"The context is what the student typed." It is tempting because the student sees only their own messages and the final answer. But in the example the student typed 15 tokens and the window held 2,555. The rest is the rules, the tool descriptions, the model's own request and the manual excerpt. All of it is counted, and all of it is billed.

Check yourself

A student asks, "Is the vinyl cutter free on Friday?" The model replies with a calendar request, and the program adds the calendar result. Which statement about the window at the next step is true?

Show the answer

The last option. The window holds everything the model reads and writes: system prompt, tool definitions, the question, the model's own request and the calendar result.

Every step re-sends the history 4 min

You know Python, so think of a function with no state inside it:

def call_model(messages): ...   # keeps nothing between calls
                                # pass everything in, every call

The model behaves like that function: its output depends only on the text you pass in. So on every step of the loop, the program must send the whole history again. As the Claude docs put it, each turn's input is all previous history plus the new message, and the output becomes part of the input for the next turn (context windows).

Two terms follow. Input tokens are the tokens you send in on a call, which is everything in the window so far. Output tokens are the tokens the model writes back. Both count toward the window and both are billed, so cost grows with tokens. This lesson names no prices.

Worked example: adding up the bill for one request

Request: "Can a first-year student use the Prusa on Friday, and what temperature for PETG?" The numbers are illustrative.

  1. Call 1. System prompt and tool definitions are 1,000 tokens and the question is 30. Input: 1,030. Output: a search_manuals request, 40 tokens.
  2. The program appends that request and the tool result (1,500 tokens). Call 2 input: 1,030 + 40 + 1,500 = 2,570. Output: a check_calendar request, 40 tokens.
  3. The program appends that request and the calendar result (200 tokens). Call 3 input: 2,570 + 40 + 200 = 2,810. Output: the final answer, 150 tokens.
  4. Add up the input billed: 1,030 + 2,570 + 2,810 = 6,410 tokens. The final window was only 2,810, so the bill is more than twice the final window. Output billed: 40 + 40 + 150 = 230.
  5. The 1,500-token excerpt is paid for in call 2 and again in call 3. Two levers follow: keep tool results small, and set a step limit.
Providers also offer caching, which can discount text that repeats from call to call. Cached tokens still fill the window, and caching is a topic for a later lesson (context windows).
If the input alone exceeds the window, the request fails, and for some models generation can stop when the window fills (context windows). A long run needs a plan for that.
A common mix-up

"The model remembers the earlier steps, so the program only needs to send the new result." A chat feels continuous, so this is tempting. But suppose the program sent only "Mon 2-4 pm free". The model would see a bare fragment, with no question and no idea which machine. It could not answer. The program must re-send the full list on every call.

Your turn (numbers)

Request: "Which drill press bit for acrylic, and is the drill press free on Monday?" Call 1: system prompt and tool definitions are 900 tokens and the question is 20, so input is 920. Output: a search_manuals request, 30 tokens. The program adds that request and an 800-token manual result, so call 2 input is 920 + 30 + 800 = 1,750. Output: a check_calendar request, 30 tokens. The calendar result is 120 tokens.

(a) What is call 3's input? (b) What is the total input billed over the three calls?

Show the solution

(a) Call 3 re-sends the whole history: 1,750 + 30 + 120 = 1,900 tokens. (b) 920 + 1,750 + 1,900 = 4,570 tokens: three full windows, not one.

If you got 150 (or 30 + 120) for (a), you assumed each call sends only what is new. The model keeps nothing between calls, so the 920 and the 800 must be sent again. If you got 1,900 for (b), you counted each piece once (920 + 30 + 800 + 30 + 120); each piece is billed again on every later call.

Between steps and between sessions 3 min

Back to the game. Variables in RAM vanish when you quit, unless the game wrote a save file. The assistant's message list is like RAM. Two terms before a story: a session is one conversation, from the student's first message until they leave, after which the program may exit. To persist something is to save it outside the running program, such as in a file or database, so that it survives.

Worked example: Sam's two visits
  1. Monday, visit 1. Sam asks about the laser cutter and says safety training is done. The messages list grows across the steps. This is "kept between steps".
  2. Sam closes the chat. The Python process ends, and the list is freed from RAM.
  3. The code starts every session with a fresh list: 
    def run_session():
    messages = []          # new, empty list every session
    ...
  4. Wednesday, visit 2. Sam asks, "Can I book it now?" The list is empty, so the model has nothing about Monday and asks about training again.
  5. The cause: nothing was saved. The model never held Sam's training, because it only reads what it is given. The fix, in one line, is to load a saved record into the new list. The next two sections supply the tools to do that.
Kept between stepsKept between sessions
The message list in the running program, re-sent on each call Nothing, unless the program writes it to a file or database and reads it back

In game terms, the message list is RAM and a file is the save. The Claude docs make the same point about the memory tool: the context window "might be reset at any moment", so progress should be written to files (memory tool docs).

Two common mix-ups

"The model remembers earlier chats by itself" and "the program's message list is the memory." Both are tempting because within one session the list does carry things forward. But quit a game without saving and the progress is gone. The list is RAM. A list that vanishes with the process is not memory across sessions, and the model holds nothing of its own.

Check yourself

The assistant is your team's own Python program calling a model. On Tuesday, Jo says, "I only print in PLA." On Wednesday a new session starts. Where could the assistant learn Jo's preference?

Show the answer

The first option: a note file saved by the program on Tuesday and loaded on Wednesday. The other three assume the model or provider keeps something between sessions, and neither does.

Retrieval: finding the right manual page 4 min

Picture an open-world game. The engine does not load the whole world at once; it loads the tiles near the player. Your assistant needs the same trick for manuals. Suppose the printer A manual has 400 pages. At roughly 600 tokens a page (approximate, uncited), that is about 250,000 tokens. From the last section you know that anything in the history is paid for again at every step.

Retrieval means searching a store of documents and putting only the best matches into the context. A chunk is a small piece of a document, a few paragraphs, stored and searched on its own.

Worked example: "Why does printer A say 'thermal runaway'?"
  1. Prepare once, ahead of time. Split each manual into chunks and store each with a label, such as printer-A.pdf, p.37.
  2. At question time, the model calls search_manuals("thermal runaway"). The search finds chunks whose words or meaning match the question; good systems combine both kinds of matching (Anthropic: Contextual Retrieval).
  3. The search returns the top three chunks, about 600 tokens, with page labels.
  4. Only those chunks enter the context as the tool result. The model answers and cites "printer A manual, p.37".
  5. Cost, illustrative. Assume this request takes three calls, as in the last section. The chunks arrive after call 1, so they are re-sent in calls 2 and 3: 600 × 2 = 1,200 input tokens. The whole manual, loaded from call 1, would be in all three calls: 250,000 × 3 = 750,000.
  6. One failure to know. A chunk reading "restart it" with no machine or section is useless alone. So store each chunk with its source and heading. In Anthropic's own tests, having a model write a short description of each chunk's place in its document, and adding it to both the meaning-based and the word-based search, cut top-20 retrieval failures from 5.7% to 2.9% (49% fewer). A failure means the right chunk was not among the 20 best matches the search returned. That is their result, not a promise for the makerspace.

Notice that the model asks for pages only when it needs them, through your search_manuals tool. Nothing is loaded up front. Anthropic's article describes this load-when-needed pattern in more depth (context engineering article).

A common mix-up

"A bigger window means no need for retrieval." If everything fits, loading it all feels simpler and safer. But a bigger window raises the limit; it does not lower the cost. In the example, loading the manual is 750,000 input tokens against 1,200, for an answer on one page. Accuracy suffers too: in one study, models did best when the relevant text was at the start or end of the input and worse when it was in the middle (Lost in the Middle).

Check yourself

A sponsor says: "The window now holds 2,000,000 tokens and all manuals total 900,000, so skip retrieval." What is the best reply?

Show the answer

The third option. Fitting in the window only means the request is allowed. Each step still re-sends and bills everything, and the model reads buried text less reliably.

Notes and memory files 4 min

Back to the game save file. For the assistant, think of one small file per student, such as students/sam.md. A memory file is a file the assistant writes notes into and reads back in a later session. A memory tool is a tool the model calls to ask for file operations, such as view or create, which the program then runs. In Claude's memory tool, "Claude requests file operations, and your application runs them" (memory tool docs).

This is not a new kind of magic. Anthropic calls the idea structured note-taking: the agent writes notes outside the window and reads them back later. Their example is a model playing a Pokemon game that kept tallies and maps across thousands of steps (context engineering article).

Worked example: Sam's visits again, now with a memory file
  1. Visit 1 starts. As its system prompt tells it, the model views /memories for a file on Sam. None exists.
  2. Sam completes laser-cutter safety training. The model calls the memory tool: create students/sam.md with "Safety training: laser cutter, passed 2026-11-24. Prefers evening slots."
  3. The program runs the file operation and returns "ok". The model only asked, as with any tool.
  4. The session ends and the process exits. The file stays on disk.
  5. Visit 2. The program starts with an empty messages. The model's first move is to view /memories, and it reads Sam's file: a few dozen tokens, not Monday's whole transcript.
  6. Sam asks, "Can I book it now?" The model knows the training is on record and goes straight to the calendar.
  7. Rule 1: write facts and decisions, because those are what a later session needs.
  8. Rule 2: do not write whole transcripts or raw tool output, because they are bulky and go stale.
  9. Rule 3: keep notes short, because every read costs tokens.
  10. Rule 4: read on demand. The file is loaded only when the model asks for it, so unread files cost nothing (memory tool docs).
  11. A question for later: if a wrong note could let an untrained student use a laser cutter, where should the real record live? A note is written by the model, so it can be wrong or out of date. A booking database is a record the program itself checks before it allows a booking, so the program does not have to trust the model.
A common mix-up

"Memory means the model stores things inside itself." Saying the assistant "remembers" sounds like something inside it changed. But the memory is an ordinary file. The model asks to create or view it, and the program does the reading and writing. Delete the file and the memory is gone, while the model is unchanged.

Worked example and practice: design the assistant's memory 5 min

Now use all of it. For each thing the assistant might hold, choose one of three homes: always in context, retrieved when needed, or saved between sessions. No new terms here.

Worked example: Priya and the acrylic

Request: "I'm Priya, I need to cut acrylic on the laser cutter next week. What settings, and book me a slot." Candidate items: system prompt, tool definitions, the question, the laser-cutter manual (250 pages, about 150,000 tokens, rough), Priya's training status, the calendar for all machines, and past chats with all students. Token counts are illustrative.

  1. System prompt and tool definitions: always in. They define the assistant and are small, about 1,000 tokens.
  2. The manual: retrieved. Only the top chunks enter, about 700 tokens, not 150,000.
  3. Priya's training status: saved, in her memory file or the booking database, and read at the start of her visit. The booking database is the program's own record of bookings and training, which the program checks before it allows a booking.
  4. The calendar: fetched with check_calendar for one machine and one week. It changes, so it is never stored.
  5. Past chats of all students: not loaded, and not saved in full. They are bulky and mostly irrelevant.
  6. Trace the run. Call 1 reads Priya's file. Call 2 searches the manual. Call 3 checks the calendar. Call 4 books the slot. Call 5 writes a note: "Priya: cut acrylic, booked Tue 2 pm." Call 6 writes the final answer.
  7. Sizes. Base: 1,000 for system prompt and tools, plus a 40-token question, so 1,040. Each model request is 40 tokens, except the note request, which is 60. Results: Priya's file 60, manual chunks 700, calendar 250, booking confirmation 50, and "ok" for the note 10. Now add them up:
    • Call 1: 1,040.
    • Call 2: 1,040 + 40 + 60 = 1,140.
    • Call 3: 1,140 + 40 + 700 = 1,880.
    • Call 4: 1,880 + 40 + 250 = 2,170.
    • Call 5: 2,170 + 40 + 50 = 2,260.
    • Call 6: 2,260 + 60 + 10 = 2,330.
    • Total input: 1,040 + 1,140 + 1,880 + 2,170 + 2,260 + 2,330 = 10,820 tokens.
    Loading the whole manual would add about 150,000 × 6 = 900,000.
  8. Check by removal. Without the file read, the assistant asks about training again. Without retrieval, cost multiplies. Without the note, the next visit starts blank.

A tempting shortcut

"To be safe, put the whole manual in the system prompt." It feels like nothing can be missed. But the manual is re-sent and billed at every call, and relevant text in the middle is read less reliably. Retrieval gives the same page for a fraction of the tokens.

Reflect

Which of your choices saves the most tokens, and which one protects the student's safety?

Show a model answer

Retrieving only the roll-loading chunks saves the most tokens. Checking the training record in the database the program reads, rather than trusting a convenience note, protects safety. One more option for very long runs: programs can summarize the history and restart with the summary (context engineering article).

Summary 3 min

  • The context window holds everything the model sees on a step: system prompt, tool definitions, history, tool results and the reply, all counted in tokens.
  • Every step is a new call that re-sends the history, so cost grows with the number of steps and with what is carried.
  • The message list lives in the running program, so it lasts between steps and not between sessions. The model remembers nothing by itself.
  • Retrieval puts only the relevant chunks in. A bigger window raises the limit, not the quality, and does not make a long manual cheap.
  • Notes and memory files carry facts across sessions, and the program reads and writes them on the model's request.
