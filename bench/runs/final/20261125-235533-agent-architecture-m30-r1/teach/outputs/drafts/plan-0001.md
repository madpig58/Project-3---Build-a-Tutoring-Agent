# Plan: lesson 0001, Context and memory in an agent (O3), 30 minutes, 4500 words

Win: By the end of this lesson you can decide, for the makerspace assistant, what stays in context during a request, what is saved between sessions, and how it finds the right manual page, and you can defend each choice by its effect on cost and accuracy.

Starts from:
- Record 0001: a model maps text in to text out, token by token, and knows only its training plus the text it is given. This is the floor: context and memory are both about what text is given.
- Record 0002: the agent loop (model asks for an action, the program carries it out, the result goes back, repeat until a final answer or a limit). Not yet checked: that every step is a separate model call and that the program runs the tools. Quiz 0001 tests that, so the lesson only recalls it and does not re-teach it.
- NOTES.md: Riley has heard "token" and "context window" but cannot say what they limit or why they affect cost. Riley has not met memory or retrieval. Python is comfortable (lists, dicts, JSON), so the lesson uses short Python snippets and game-engine analogies (RAM versus save file, level streaming).
- The budget is small and the first design review is in five weeks, so cost framing recurs throughout.
- Likely misconceptions: the model remembers earlier chats by itself; a bigger window means no retrieval is needed; the program's message list is the memory.

Learning objectives:
1. You can say what a token is and list what fills the context window at each step: system prompt, tool definitions, history, tool results, and the reply.
2. You can explain that each step is a separate model call that is re-sent the whole history, and estimate how that grows the tokens billed.
3. You can separate what is kept between steps (the message list in the running program) from what is kept between sessions (nothing, unless the program saves it).
4. You can explain how retrieval puts only the relevant manual chunks into context, and why that beats loading the whole manual.
5. You can use notes and memory files to carry a student's training status across sessions, and say what to write, when to read it, and who does the file work.

## Section 1: Tokens and what fills the context window (600 words, objective 1)
- New terms (two): token, a small chunk of text, often a whole short word or a piece of a longer one, and the unit the model reads and writes and that is counted and billed. Context window, all the tokens the model can see when it writes its next piece, including its own reply, with a fixed maximum size.
- Opening example (about 80 words): a 3D printer manual page pasted into a chat. Show a short sentence split into tokens, for example "Nozzle temperature" split as "Noz", "zle", " temperature". Label it clearly "illustrative split, real splits differ by model". Give a rule of thumb: a page of a manual is roughly 500 to 800 tokens, and token counts are what get counted, not words. Mark the rule of thumb as approximate and do not cite it.
- Worked example (about 250 words): lay out the context at step 1 of one request in the makerspace assistant, as a stack of labelled boxes with approximate token counts:
  1. System prompt, the assistant's role and rules, about 400 tokens.
  2. Tool definitions: check_calendar, book_machine and search_manuals, about 600 tokens.
  3. The student's message: "What nozzle temperature for PETG on the Prusa?", about 15 tokens.
  4. Add the model's reply, which asks for search_manuals. About 40 tokens.
  5. Add the tool result, a manual excerpt, about 1,500 tokens.
  6. Show the final context as a table with a total, and say that the window counts all of it, including the reply, the definitions and the tool results, not just what the student typed.
  Show it as a Python list of dicts, `messages = [{"role": "user", ...}, {"role": "assistant", ...}, {"role": "user", "content": [tool_result]}]`. Keep the code to a few lines, and say it is a sketch of the idea, not a specific library's exact API. Say what each part is.
- Short paragraph on why the size matters. More text is not automatically better, because recall gets worse as the window fills ("context rot"). Mention "context rot" only inside one sentence as a name, and do not make it a third term. The practical goal is the smallest set of high-signal tokens.
- Practice: "Which of these count toward the context window: (a) only the student's typed question, (b) the question and the model's reply, (c) the system prompt, tool definitions, history, tool results and the reply, (d) only the manual excerpt?" Options are the same length, and the right answer is in a position other than the first. Tempting wrong answer: (a), because the student sees only the chat and assumes only that text is in play. The feedback explains that tool definitions and tool results are tokens the model reads too, and that the reply counts because it becomes part of the input on the next step.
- Misconception: "the context is what the student typed." Head it off with the box stack.
- Citations:
  - Context = set of tokens given when sampling, and curating the smallest set of high-signal tokens - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Window includes the response, system prompt, tool definitions and tool results, and more context is not automatically better - https://platform.claude.com/docs/en/build-with-claude/context-windows
  - Recall decreases as tokens grow (context rot) - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://platform.claude.com/docs/en/build-with-claude/context-windows

## Section 2: Every step re-sends the history: the cost link (600 words, objective 2)
- New terms (two): input tokens, the tokens you send in on a call, which is everything in the window so far. Output tokens, the tokens the model writes back. Both are billed. Say plainly that cost grows with tokens, and do not state any prices.
- Opening example (about 80 words): a game-engine analogy. A stateless function in Python: `def call_model(messages): ...` has no memory between calls, so each call needs the full state passed in. Riley already knows functions, so this lands. The model is like a pure function of the text it is given.
- Worked example (about 300 words): a three-step request, "Can a first-year student use the Prusa on Friday, and what temperature for PETG?", with invented but labelled illustrative numbers.
  1. Base: the system prompt and the tool definitions, 1,000 tokens, plus the question, 30 tokens. Call 1 input is about 1,030 tokens, and the output is a search_manuals request of 40 tokens.
  2. The program appends the model's request and the tool result, 1,500 tokens. Call 2 input is 1,030 + 40 + 1,500 = 2,570 tokens, and the output is a check_calendar request of 40 tokens.
  3. The program appends that request and the calendar result, 200 tokens. Call 3 input is 2,570 + 40 + 200 = 2,810 tokens, and the output is a final answer of 150 tokens.
  4. Add up the input tokens billed: 1,030 + 2,570 + 2,810 = 6,410. Compare with the 2,810 tokens in the final window. The cost is more than twice the size of the final context, because the early text is paid for again at every step.
  5. State the takeaway: cost grows with both the number of steps and the size of what is carried. Show how a big manual excerpt that stays in history is paid for again each later step. Suggest two levers, fewer or smaller tool results, and a step limit. Do not teach prompt caching, because it is out of scope.
- Practice (numeric, faded): "Same request, but the manual excerpt is 4,000 tokens instead of 1,500. What is call 3's input?" Answer: 1,030 + 40 + 4,000 + 40 + 200 = 5,310. Tempting wrong answer: 200 + 40 or "only the new calendar result", because the learner assumes each call sends only what is new. The feedback explains that the whole history is re-sent, with the arithmetic.
- Misconception: "the model remembers the earlier steps, so it only needs the new result." The model has no memory between calls, and the program re-sends everything. This is also the first place to show that exceeding the window gives an error or stops the request.
- Citations:
  - Each turn's input is all prior history plus the new message, and the output becomes input for the next turn (progressive accumulation) - https://platform.claude.com/docs/en/build-with-claude/context-windows
  - Input and output tokens both count - same source
  - Exceeding the window gives an error or a stop - same source
  - Note in the lesson that the numbers are invented to show the pattern. Real counts need a tokenizer and are out of scope.

## Section 3: Between steps versus between sessions (500 words, objective 3)
- New terms (two): session, one conversation from the student's first message to the end, after which the program may exit. Persist, to save something outside the running program, such as in a file or a database, so that it survives.
- Opening example (about 80 words): a game. The variables in RAM, such as the player's position and the enemies, last while the game runs. When you quit, they are gone, unless the game wrote a save file. Match them: the message list is RAM, and a file is the save.
- Worked example (about 220 words): follow Sam, a student, across two visits.
  1. Visit 1 (Monday): Sam asks about the laser cutter, and the assistant finds out that Sam finished the safety training. The `messages` list grows in the program across the steps. This is "kept between steps".
  2. Sam closes the chat, the Python process ends, and the list is garbage collected. A short code sketch: `messages = []` at the top of `run_session()`, a fresh list for each call.
  3. Visit 2 (Wednesday): the program starts with `messages = []`. Sam asks, "Can I book it now?" The model has nothing about Monday, so it asks Sam again about training.
  4. Name the cause: nothing was saved, and the model never held the information in the first place. Show the fix in one line, "load the saved record into the new list", and say that Sections 4 and 5 supply the tools to do it.
  5. Make a two-column table: kept between steps (the message list in the program, re-sent each call); kept between sessions (nothing, unless the program writes it to a file or database and reads it back).
- Practice: "After the student closes the chat and returns the next day, where could the assistant have learned the student passed safety training? Options: (a) from the model's weights, which update during chatting, (b) from the old message list, which stays in the model between sessions, (c) from a file the program saved and loaded at the start, (d) from the context window, which is saved by the provider." The right answer is (c), and the options have matching length. Tempting wrong answer: (b), because "the conversation is still there" feels natural. The feedback explains that the list lives in the program's memory, which ends with the process, and that the model has no memory of its own.
- Misconceptions headed off here, both named explicitly: (1) "the model remembers earlier chats by itself"; (2) "the program's message list is the memory." The list is only working storage for one run, and memory has to be written out and read back on purpose.
- Citations:
  - Context window as working memory, with history re-sent each turn - https://platform.claude.com/docs/en/build-with-claude/context-windows
  - Files in /memories persist between sessions, and the window can be reset at any moment - https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool

## Section 4: Retrieval, finding the right manual page (650 words, objective 4)
- New terms (two): retrieval, searching a store of documents and putting only the best matches into the context. Chunk, a small piece of a document, such as a few paragraphs, that is stored and searched on its own.
- Opening example (about 90 words): level streaming in a game engine. A big open world is not loaded all at once. The engine loads the tiles near the player. Retrieval does the same for a 400-page manual: load only the few chunks that matter for this question. Add the cost link back to Section 2: a 400-page manual could be about 250,000 tokens (rough) paid for again at every step, so it does not fit and would not be affordable.
- Worked example (about 300 words): the question "Why does the Ender-style printer say 'thermal runaway'?", from the makerspace manuals.
  1. Prepare once, ahead of time. Split each manual into chunks of a few paragraphs, with a label such as `printer-A.pdf, p.37`.
  2. At question time, the program (or the model, through a `search_manuals(query)` tool) searches the chunks. Say in one plain line that two search styles exist. Keyword search matches exact words such as the error name. Meaning-based search, "embeddings", matches a question to chunks that say similar things in different words. Do not explain embedding math, and do not make it a new term. Say that the best systems combine both.
  3. The search returns the top three chunks, about 600 tokens, with their page labels.
  4. Only those chunks enter the context as the tool result. The model answers and cites "printer-A manual, p.37".
  5. Compare the cost with loading the whole manual. 600 tokens are re-sent per later step, not 250,000.
  6. One failure to show: a chunk that says "restart it" without saying which machine or section loses its context, which is why the chunk label and heading are stored with it. Mention that adding a short description of where each chunk comes from improved retrieval, with the 49% figure (top-20 retrieval failures from 5.7% to 2.9%), and make clear that this figure is from the source's own tests and not a promise for the makerspace.
- Also in this section: the "bigger window" misconception. Even if the whole manual fits, accuracy is highest when the relevant text is at the start or end of the input and drops in the middle, and it costs the whole manual again every step. A bigger window raises the limit but does not make a large manual cheap or reliably read.
- Practice: "A new window can hold 1,000,000 tokens, and the manual is 250,000 tokens. Why still retrieve? (a) The manual would not be read by the model at all, (b) Every step would pay for the whole manual again, and the answer can get lost in the middle, (c) The window is billed only when full, (d) The tool definitions would be deleted to make room." Same length, with the right answer placed third. Tempting wrong answer: (a) or the idea that "it fits, so it's fine", because limit and quality are confused. The feedback explains the cost re-send and the lost-in-the-middle effect, and that the model does read it, just less well.
- Misconception: "a bigger window means no need for retrieval."
- Citations:
  - Chunks, embeddings plus BM25 keyword search, isolated chunks lose context, and the 49% / 5.7% to 2.9% result - https://www.anthropic.com/engineering/contextual-retrieval
  - Up-front retrieval versus just-in-time retrieval through lightweight identifiers such as file paths and queries; CLAUDE.md up front, glob/grep just in time - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents. Mention in one sentence only that the assistant can fetch by `search_manuals(query)` just in time.
  - Accuracy is highest at the start or end of the input and drops in the middle - https://aclanthology.org/2024.tacl-1.9.pdf

## Section 5: Notes and memory files (550 words, objective 5)
- New terms (two): memory file, a file the assistant writes notes into and reads back in a later session. Memory tool, a tool the model calls to ask for file operations (view, create and so on), which the program runs.
- Opening example (about 70 words): a game save file with a small JSON like `{"level": 4, "keys": 2}`. Riley has read JSON. The assistant needs a small save file for each student, such as `students/sam.json`. Note the point from the source: Claude playing Pokemon kept tallies and maps in notes across thousands of steps. Keep it to one sentence.
- Worked example (about 270 words): Sam's two visits again, now with a memory file.
  1. Start of visit 1. The program (or the model, by instruction in the system prompt) checks `/memories` for a file on this student. None exists.
  2. During the visit, Sam completes laser-cutter safety training. The model calls the memory tool, `create students/sam.md` with "Safety training: laser cutter, passed 2026-11-24. Prefers evening slots."
  3. The program runs the file operation, because the model only requests it (same pattern as any tool in record 0002), and returns "ok".
  4. The session ends and the process exits. The file stays on disk.
  5. Visit 2: the program starts with an empty `messages`. The first thing the model does, as instructed, is view `/memories`. It reads Sam's file, which costs a few dozen tokens, not Monday's entire transcript.
  6. Sam asks, "Can I book it now?" The model now knows that the training is on record and goes straight to the calendar.
  7. Rules of thumb in a short list: write facts and decisions, such as training status and preferences; do not write the whole transcript or raw tool output; keep notes short, because they cost tokens whenever they are read; read on demand, so the files take no space until read.
  8. Note a design caution without teaching it as a topic: a training record that gates safety is better kept in the booking database that the program checks. A memory note is for convenience. Frame this as a question for the main exercise.
- Practice: "Which of these belongs in Sam's memory file? Options (same length): (a) the full text of the three manual pages read on Monday, (b) the training status and the machines Sam is cleared for, (c) the calendar results from every check made, (d) the model's step-by-step reasoning for each answer." Right answer (b), placed second. Tempting wrong answer: (a) or (c), because "more notes is safer". The feedback explains that those are bulky and stale, since the calendar changes, and that they cost tokens at each read.
- Misconception: "memory means the model stores things inside itself." In fact the files are ordinary files, and the program runs the reads and writes.
- Citations:
  - Memory tool: Claude requests file operations, the application runs them, and files in /memories persist between sessions - https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool
  - Claude checks memory before a task, reads on demand so that files do not occupy the window until read, and the window may be reset at any moment, so record progress - same source
  - Structured note-taking, notes persisted outside the window (NOTES.md, a to-do list; Pokemon) - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Do not teach compaction as its own section. Allow one sentence in Section 6: "when a very long run fills the window, programs can summarize and restart", cited to the engineering article. Do not make it a term.

## Section 6: Main worked example and faded practice, design the assistant's memory (700 words, objectives 1-5)
- New terms: none.
- Worked example (about 330 words), a decision table for one new request: "I'm Priya, I need to cut acrylic on the laser cutter next week. What settings, and book me a slot." The steps, each with a one-line reason:
  1. List every item that could go into the context: system prompt, tool definitions, the question, a laser-cutter manual (250 pages), Priya's training status, the calendar for all machines, and the past chats with all students.
  2. Decide each item as "always in context", "retrieved when needed" or "saved between sessions", with a reason in terms of tokens and accuracy. System prompt and tool definitions: always in, since they define the assistant, and they are small. The manual: retrieved, with the top chunks only. Priya's training status: saved in her memory file or database, and read at the start of her visit. The calendar: fetched with check_calendar for one machine and one week, not loaded in full, since it changes. Past chats of all students: not loaded, and not even saved in full.
  3. Trace the run. Call 1 reads Priya's file. Call 2 searches the manual for acrylic settings. Call 3 checks the calendar. Call 4 books it. Call 5 writes a note: "Priya: cut acrylic, booked Tue 2 pm." Say how big the final context is and why this is far under the window and the budget.
  4. Present the result as a table of item, where it lives, and why.
  5. One-sentence check: where would the answer break if each step were removed? For example, without the training status step the assistant asks again, and without retrieval the cost multiplies.
- Faded practice (about 300 words): a new request, "I'm Marcus, I want to use the vinyl cutter and I'm not sure how to load the roll. Can you book me for Friday?" The learner fills in a blank table. The first row is given. The reasons are given for the first row only, then fully blank. The steps, faded: (a) the table (2 rows given, 3 blank), (b) the call order (blank), (c) what to write in Marcus's note (blank). The solution is revealed on demand, with a model answer and the reasons: the roll-loading steps are retrieved from the vinyl cutter manual, the Friday slot is fetched from the calendar, and the note records "Marcus: first vinyl session, loaded roll question". The feedback names the tempting wrong answer: putting the whole vinyl manual in the system prompt "to be safe". The reply: this is paid for every step, and it hurts accuracy.
- Reflection prompt (about 70 words): "Which of your choices saves the most tokens, and which one protects the student's safety?"
- Citations: reuse earlier ones. No new claims.

## Section 7: Summary and Go further (450 words)
- Summary (about 150 words), five lines:
  1. The context window holds everything the model sees on a step: system prompt, tool definitions, history, tool results and the reply, all counted in tokens.
  2. Every step is a new call that re-sends the history, so cost grows with steps and with what is carried.
  3. The message list lives in the running program, so it lasts between steps and not between sessions. The model remembers nothing by itself.
  4. Retrieval puts only the relevant chunks in. A bigger window raises the limit, not the quality, and it does not make a long manual cheap.
  5. Notes and memory files carry facts across sessions, and they are read and written by the program on the model's request.
- Prompt to explain in their own words (about 40 words): "In two or three sentences, explain to a teammate why the assistant forgot Sam's training, and what you would add so that it does not."
