## Section 1: The context window: what has to fit

- Serves: LO1.
- New terms: **token** - a small chunk of text (a word, part of a word, characters) that the model works in. **context window** - all the text the model can use for one reply, including the reply itself, with a maximum size in tokens (that text is the "context").
- Opening example: a game level with a fixed memory budget: every texture and sound loaded takes a share, and the level cannot load past the limit. One model call has a budget like that, counted in tokens.
- Explanation points: rough estimate tokens = characters / 3.5 for English with recent Claude models, varies by model. Everything sent counts: standing instructions, tool list, every message, tool results, images, documents; the reply counts too. The window is working memory, separate from what the model learned in training. Its size depends on the model.
- Worked example: will this makerspace request fit? Made-up window of 20,000 tokens, 500 kept free for the reply, 1,400 characters per manual page. Steps:
  1. Standing instructions: 2,100 characters / 3.5 = 600 tokens.
  2. Tool list: 1,400 characters = 400 tokens. It takes space even if no tool gets used.
  3. Student question: 140 characters = 40 tokens. Subtotal 1,040.
  4. Add the whole 60-page manual: 60 x 400 = 24,000, giving 25,040. The input alone is over 20,000, so the request is rejected with a "prompt is too long" error.
  5. Add only the one relevant page: 1,040 + 400 = 1,440, plus 500 for the reply = 1,940. It fits with lots of room.
  Include a three-line Python helper `estimate_tokens(text)` returning `len(text) / 3.5`, explain the one line, and call it a rough estimate only.
- Practice: "Made-up window: 8,000 tokens. Your input is 7,600 tokens and a full answer needs about 900. On a newer model, what happens?" Options (6 words each, correct second):
  - "The request is rejected before starting" - wrong: the input alone (7,600) is under 8,000.
  - "The reply starts, then stops early" - right: only 400 tokens remain, and the reply counts.
  - "The whole reply fits without trouble" - the tempting wrong answer, because it treats the window as a limit on input only; 7,600 + 900 = 8,500.
  Note in the feedback that behaviour at the limit differs between models.
- Misconception: "The window only limits what the student types." Tempting because a chat box shows only your message. In the worked example the question is 40 of 1,440 input tokens.
- Citations:
  - Token definition; about 3.5 English characters per token, varying by model - https://platform.claude.com/docs/en/about-claude/glossary
  - Window definition including the response; working memory distinct from training data; everything in the request and the output counts; size depends on model; over-long input errors, and on newer models generation that reaches the limit stops early - https://platform.claude.com/docs/en/build-with-claude/context-windows

## Section 2: Between steps: the whole history goes again

- Serves: LO2.
- New terms: **message history** - the running list of everything said and returned so far. **short-term memory** - that history, kept for one session (one ongoing conversation, such as one visit).
- Opening example: a student's second message is "and for 6 mm?" On its own it means nothing; it works only because the earlier messages are sent along with it.
- Explanation points: each new call's input holds all earlier history plus the new message; history piles up and re-sent turns count as input again. In an agent, each step's request and tool result join the same history and take up space. The history can be saved so that same conversation can resume later; it still belongs to that one conversation (Section 4 covers carrying facts across conversations).
- Worked example: a four-question chat, made-up numbers. Instructions plus tool list 1,000 tokens (from Section 1); each question 40; each reply 160; with question 2 the student pastes an 800-token manual section. Show the code first:

  ```python
  history = []                      # short-term memory for this visit

  def ask(question):
      history.append({"role": "user", "content": question})
      reply = call_model(instructions=INSTRUCTIONS, messages=history)  # stand-in, not a real library
      history.append({"role": "assistant", "content": reply})
      return reply
  ```

  Explain the important lines: the list lives in your program; the whole list is passed each time; the reply is appended so the next call includes it. Steps:
  1. Call 1 input: 1,000 + 40 = 1,040.
  2. Call 2: 1,040 + 160 (reply 1) + 40 + 800 = 2,040.
  3. Call 3: 2,040 + 160 + 40 = 2,240.
  4. Call 4: 2,240 + 160 + 40 = 2,440.
  5. Total input paid for: 7,760, although the last input is only 2,440. At 1 made-up credit per 1,000 input tokens that is 7.76 credits. The pasted section alone was sent three times (2,400 tokens).
- Practice: "Reply 4 is 160 tokens. The student sends a fifth question of 40 tokens. How many input tokens does call 5 carry?" Options (2 words each, correct third):
  - "40 tokens" - the tempting wrong answer: the chat screen makes it feel as if only the new message is sent, but the history goes too.
  - "200 tokens" - counts the last reply and new question, leaving out everything earlier.
  - "2,640 tokens" - right: 2,440 + 160 + 40.
- Misconception: "The model remembers the earlier turns, so my program only sends the new message." Tempting because chat apps feel continuous. In this setup the continuity comes from the history being sent again; drop it and "and for 6 mm?" has nothing to refer to.
- Citations:
  - Each turn's input contains all previous history plus the new message; history accumulates; re-sent turns count as input; tool results count - https://platform.claude.com/docs/en/build-with-claude/context-windows
  - Short-term memory is the thread's (one conversation's) message history and can be persisted so it resumes - https://docs.langchain.com/oss/python/concepts/memory (call it a "conversation"; do not introduce "thread")

## Section 3: A crowded context: clear and summarize

- Serves: LO3.
- New terms: **context rot** - as the token count grows, the model gets less accurate at recalling what is in the context. **compaction** - summarizing a conversation that is nearing the limit and starting a fresh window with the summary.
- Opening example: an AI game master in a long text adventure. Early on it was established that the north door is locked. Many pages of map dumps later, that one line is buried and easier to miss. Say "more likely to miss", not "will forget".
- Explanation points: context rot is a gradual slope, not a cliff at the limit; treat context as a limited resource with diminishing returns; aim for the smallest set of high-value tokens that does the job (explain "high-signal" in plain words, do not define it as a term). Clearing old tool results is one of the safest, lightest forms of compaction. A summary should keep decisions, unsolved problems and important details; first check it keeps everything that matters, then trim extra.
- Worked example: the game master's context, made-up window of 32,000 tokens. Steps:
  1. Count: standing instructions 1,000 + early talk with decisions 2,000 + four old map listings returned by a tool 20,000 (5,000 each) + recent turns 3,000 = 26,000. It fits, but most of it is old listings.
  2. Ask of each block: will a later step need this exact text? The listings have been used and can be fetched again.
  3. Clear them, leaving a one-line placeholder each (100 tokens in all, saying which map it was): 26,000 - 20,000 + 100 = 6,100.
  4. Much later: instructions 1,000 + placeholders 100 + older talk 18,000 + recent 3,000 = 22,100. Clearing is not enough now, so compact: a 500-token summary replaces the older talk and placeholders. 1,000 + 500 + 3,000 = 4,500. Keeping instructions and recent turns word for word is this example's design choice.
  5. Read the summary against a checklist: locked north door (decision), unsolved riddle (open problem), player's inventory (important detail). If one is missing, fix the summary instructions. If the program asks a model to write the summary, that call uses tokens too.
  Add one line linking back: removing Section 2's pasted section after turn 2 would make calls 3 and 4 carry 1,440 and 1,640, total 6,160 instead of 7,760, with the risk that a follow-up question needs it again.
- Practice: "The makerspace chat is getting crowded. Which item is safest to clear first?" Options (6 words each, correct first):
  - "A week-old calendar listing, already used" - right: used, out of date, and can be fetched fresh.
  - "The training rule in standing instructions" - wrong: every later answer depends on it.
  - "The student's request that's still open" - tempting because it is old text; wrong because the work is unfinished.
- Misconception: "A bigger window fixes this, so put everything in." Tempting because a bigger window removes the error. It does not remove context rot, and in our price assumption every extra token is still paid for on every call that carries it.
- Citations:
  - Context rot; finite resource with diminishing returns; a gradient, not a hard cliff; smallest set of high-signal tokens - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Accuracy and recall degrade as token count grows - https://platform.claude.com/docs/en/build-with-claude/context-windows
  - Compaction definition; what a summary keeps (the source's examples: decisions, unresolved bugs, implementation details); tune to keep everything relevant first, then cut extra; clearing old tool results is among the safest, lightest forms - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Section 4: Between sessions: notes the assistant saves

- Serves: LO4.
- New terms: **long-term memory** - information stored outside any one conversation and available in later sessions. **note** - a short piece of saved text or data, written outside the context window and loaded back when needed.
- Opening example: a game save file. Close the game and what was only in RAM is gone; what you wrote to the save file loads next time.
- Explanation points: a new session starts with a new history, so anything needed later must be saved by your system and put back into the context. A note can be a to-do list, a NOTES.md file or a record per student. The same trick helps inside a long run: the agent writes progress notes and reads them after a compaction. The model's training does not change when you save a note.
- Worked example: remembering Jordan's training status. Steps:
  1. Choose what to save: needed next visit and slow to change. Training passed and its date: yes. Friday's free slots: no, fetch fresh. The whole chat: no, too big for what it tells you.
  2. Code:

     ```python
     import json
     from pathlib import Path

     def load_note(student_id):
         path = Path(f"notes/{student_id}.json")
         if path.exists():
             return json.loads(path.read_text())
         return {}                      # first visit: nothing saved yet

     def save_note(student_id, note):
         Path("notes").mkdir(exist_ok=True)
         Path(f"notes/{student_id}.json").write_text(json.dumps(note))
     ```

  3. Visit 1 ends: `save_note("s1042", {"laser_training": "passed", "confirmed": "2026-11-03"})`.
  4. Visit 2 starts: `note = load_note("s1042")`, then `instructions = INSTRUCTIONS + "\nSaved note: " + json.dumps(note)` and `history = []`. Explain: the note counts only once it is in what gets sent (Section 2's `ask` would pass `instructions`).
  5. Compare cost: a note of about 50 tokens against last visit's chat of 1,600 tokens (4 x 40 + 800 + 4 x 160).
  6. When something changes, update the note. Keep a date so stale facts can be spotted. One-sentence design caution, stated as advice: if the makerspace has an official training record, treat that as the truth for permission to book.
- Practice: "Jordan comes back next week. Which item belongs in their saved note?" Options (6 words each, correct third):
  - "Today's free slots on laser cutter" - wrong: it changes; look it up when asked.
  - "Every word of last week's chat" - the tempting wrong answer: saving all feels safe, but loading it spends tokens on every call and crowds the context.
  - "Passed laser cutter training, 3 November" - right: small, stable and needed next visit.
- Misconception: "The model will remember Jordan next time because it talked with them." Tempting because some chat products appear to remember people. Here a new session with no loaded note gives the model nothing about Jordan; the remembering is storage plus loading that you design.
- Citations:
  - Long-term memory stores user or application data across sessions, shared across conversations; short-term memory is scoped to one - https://docs.langchain.com/oss/python/concepts/memory
  - Agents write notes kept outside the context window and pull them back later; to-do list and NOTES.md examples - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Context window as working memory distinct from training data - https://platform.claude.com/docs/en/build-with-claude/context-windows

## Section 5: Retrieval: fetching the right page

- Serves: LO5.
- New terms: **retrieval** - searching stored material while the assistant runs and adding only the relevant parts to the context. **chunk** - a small piece of a document, stored so it can be found on its own.
- Opening example: looking up one error in a game engine's docs: you search and open the matching part, you do not reread all the docs.
- Explanation points: split documents into chunks, usually no more than a few hundred tokens; at question time find the best matches and add them to the prompt. Search by exact words is good for codes and part numbers; search by meaning finds passages worded differently (it compares numeric representations of meaning; no further detail). You can also keep just a pointer (file path, page number, link) and load the text with a tool when needed: slower than preparing it in advance, and it needs good rules for where to look; a mix of some text up front and the rest fetched is possible. Skip retrieval if you can: for a knowledge base under about 200,000 tokens (about 500 pages) the source says you can put it all in the prompt, paired with a feature that makes repeated text cheaper. Tell Riley to check that it fits the chosen model's window and the budget. "Do the simplest thing that works."
- Worked example: "What does error E-42 mean on the laser cutter?" Made-up manual: 60 pages, 24,000 tokens. Steps:
  1. Split into chunks of 300 tokens: 80 chunks.
  2. Label each with machine, section and page, so it still makes sense alone.
  3. Search by exact words for "error E-42". Toy code (say plainly it is far simpler than real search):

     ```python
     def search_manual(chunks, query, top=3):
         words = query.lower().split()
         def score(chunk):              # how many query words appear
             return sum(word in chunk["text"].lower() for word in words)
         return sorted(chunks, key=score, reverse=True)[:top]
     ```

  4. Add the top 3 chunks to the context: 1,040 + 900 = 1,940 input tokens, against 25,040 with the whole manual.
  5. Check the result: does a chunk contain E-42 and name this machine? If not, search again with other words; try search by meaning for a description such as "the beam keeps cutting out".
- Practice: "A search returns a chunk that says only: 'Set the speed to 20 first.' What is the chunk missing?" Options (6 words each, correct second):
  - "More words copied from the question" - wrong: matching the question better does not say what the instruction applies to.
  - "Which machine and material it means" - right: cut from its page, the chunk lost its context; label chunks when you split.
  - "A bigger context window for reading" - the tempting wrong answer: more room does not restore information the chunk never carried.
- Misconception: "Search by meaning is the smart one, so it always finds the right page." For an exact code it may return general text about error codes and miss the one line with E-42; exact-word search suits that case.
- Citations:
  - Chunks of a few hundred tokens or fewer; meaning-based representations and similarity search; chunks added to the prompt - https://www.anthropic.com/engineering/contextual-retrieval
  - Exact-word search suits unique identifiers; meaning search can miss an exact error code; chunks can lose context; the 200,000-token (500-page) guidance with its cheaper-repeated-text feature - https://www.anthropic.com/engineering/contextual-retrieval
  - Pointers loaded at run time with tools; slower than pre-computed retrieval; needs good heuristics; hybrid approach; do the simplest thing that works - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Section 6: Worked example and faded practice (600 words, 4 minutes)

Worked example (about 340 words, with Fig 3). Case: Jordan returns and asks, "What settings do I use for 3 mm acrylic, and can I have the laser on Friday?" Made-up numbers. Sort each piece of information into: every call / load at session start / fetch when needed / clear or summarize / save for next time. Steps, each with its reason:
1. Standing instructions (600) and tool list (400): every call.
2. Jordan's note (50): load at the start, because it is small and needed.
3. Question (40): in the history. Starting input 600 + 400 + 50 + 40 = 1,090.
4. Manual: fetch 3 chunks (900) on the acrylic settings; never the whole 24,000.
5. Friday's calendar (200): fetch fresh, do not save in the note; clear the listing once it is no longer needed.
6. Check size: 1,090 + 900 + 200 = 2,190, against 25,290 if the whole manual were included.
7. If the visit runs long: clear used results first, then compact, keeping the chosen settings and any unfinished booking.
8. End of visit: save only lasting changes. A booking lives in the booking calendar, so the note need not copy it.

Faded practice (about 260 words, solution on demand). Case: a returning student asks, "Why did my 3D print warp, and is the printer free Monday?" and mentions they passed resin printer training today (confirm against the official record). Given: standing instructions and tool list (1,000) go in every call. Learner sorts: saved note (50), warping section of a 30,000-token guide (two chunks, 600), Monday's calendar (200), this visit's messages (300), the new training fact. Then estimates the largest input and says what to save at the end.
Solution: note loaded at start; fetch the two chunks; fetch calendar fresh and clear after use; keep messages in history, summarize only if crowded; save the confirmed training with its date. Input 1,000 + 50 + 300 + 600 + 200 = 2,150 (the 300 includes the question). Name the likely slips: saving the calendar; loading the whole guide.

## Section 7: Summary and Go further (450 words, 3 minutes)

Summary (about 220 words), five lines:
1. Everything the model reads and writes in a call must fit the context window, counted in tokens.
2. Between steps the history is sent again, so input grows.
3. A crowded context hurts recall: clear used results, then summarize.
4. Between sessions only what you save and load back survives.
5. Long material stays outside and is retrieved in pieces, unless putting it all in is simpler and affordable.
