Lesson 1 · 30 minutes

Context and memory: what your agent sees and what it keeps

By the end of this lesson you can decide, for each piece of information in your makerspace assistant, whether it goes into every model call, gets fetched when needed, gets saved for the next visit, or gets cleared or summarized, and estimate what that choice costs.

Objective O3: context and memory in an agent About 30 minutes

Picture this. A student asks your assistant which laser settings to use. The answer is somewhere in a long machine manual. A week later, the same student comes back.

That story raises two questions. What can the model see right now? What is still there next week?

Why this matters for you

You are designing this assistant on a small model budget. At your design review you need to say what it sends to the model, what it saves between visits, what it looks up, and why. This lesson gives you the numbers and the vocabulary to defend those choices.

One word before we start. A model call is one round trip: your program sends text to the model, and the model sends text back. What you send is the input. What comes back is the reply.

1. The context window: what has to fit 3 min

Think of a game level with a fixed memory budget. Every texture and sound you load takes a share. Past the limit, the level cannot load any more. A model call has a budget like that too.

The budget is counted in tokens. A token is a small piece of text that the model works in: a word, part of a word, or a few characters (Claude glossary).

To estimate the number of tokens in English text, divide the number of characters by 3.5. That is the rough figure given for recent Claude models, and the real count varies by model (glossary).

The context window is all the text the model can use for one reply, including the reply itself. It has a maximum size in tokens, which depends on the model. The text inside it is called the context (context windows docs).

Everything you send counts. That includes your standing instructions (the text sent every time that gives the assistant its role and rules), the tool list (descriptions of the tools it may ask for), every message, tool results, images and documents. The reply counts too (docs).

The window is separate from what the model learned in training (docs). Training is what the model already knows. The context is what is in front of it right now.

Worked example: will this request fit?

These are made-up, illustrative numbers. The window is 20,000 tokens, and you keep 500 free for the reply. The standing instructions are 2,100 characters, the tool list is 1,400, and the question is 140. The manual has 60 pages of 1,400 characters each.

This tiny Python function turns text into a token estimate:

def estimate_tokens(text):
    # rough estimate only; the real count varies by model
    return len(text) / 3.5

The return line counts the characters with len and divides by 3.5.

  1. Standing instructions: 2,100 / 3.5 = 600 tokens. They are sent with the request, so they take space.
  2. Tool list: 1,400 / 3.5 = 400 tokens. It takes space even if no tool gets used.
  3. Question: 140 / 3.5 = 40 tokens. So far the input is 600 + 400 + 40 = 1,040 tokens.
  4. Try the whole manual: one page is 1,400 / 3.5 = 400 tokens, so 60 pages are 60 x 400 = 24,000 tokens. The input becomes 1,040 + 24,000 = 25,040. That is over 20,000 before any reply, so the request is rejected. The error says "prompt is too long", meaning the input is too long.
  5. Try only the one relevant page: the input is 1,040 + 400 = 1,440. Add 500 for the reply and you need 1,940 of 20,000. It fits with lots of room.

Takeaway: add up every part of the input, leave room for the reply, then compare the total with the window.

A common mix-up

"The window only limits what the student types." It is tempting because a chat box shows you your message and little else. But in the one-page request, the question is just 40 of 1,440 input tokens. The other 1,400 are instructions, tool list and manual page, and the reply needs room as well.

What happens at the limit? In the Claude docs, an input that is too long on its own gets an error. On newer Claude models, a request whose input fits is accepted, and if the reply then reaches the window limit, it stops early (docs). Other models may behave differently.

Check yourself

Made-up, illustrative numbers: the window is 8,000 tokens. Your input is 7,600 tokens, and a full answer needs about 900. On a newer Claude model, what happens?

Show the answer

The reply starts, then stops early. The input leaves 8,000 - 7,600 = 400 tokens, less than the 900 the answer needs. A rejection would need the input alone to be over 8,000. "Fits without trouble" forgets that the reply shares the window.

2. Between steps: the whole history goes again 5 min

A student asks about cutting 3 mm acrylic and gets an answer. Then they type: "and for 6 mm?" On its own, that means nothing. It works only if the earlier messages are sent along with it.

The message history is the running list of everything said and returned so far. Each new call's input holds all of that earlier history plus the new message (context windows docs).

So the history piles up, and the earlier messages and replies count as input again on every call.

An agent works the same way between the steps of its loop. Each step is a new model call. The earlier tool requests and tool results join the same history, and they take up space like any other text.

Worked example: two steps inside one request

You ask a coding agent, "Why does my game level fail to load?" It can ask for two tools: one reads the error log, one reads a file. Made-up, illustrative numbers: instructions plus tool list are 1,000 tokens, and your question is 40.

  1. Call 1 input: 1,000 + 40 = 1,040 tokens.
  2. The model asks for the error log. That request is 30 tokens. Your program runs the tool and gets a 200-token result.
  3. Both join the history. Nothing else carries this step forward to the next one.
  4. Call 2 input: 1,040 + 30 + 200 = 1,270 tokens. You typed nothing new, yet the input grew.
  5. So far: 1,040 + 1,270 = 2,310 input tokens, or 2.31 credits at 1 made-up credit per 1,000. The request is not even answered yet.

Takeaway: to estimate an agent's cost, add up the input of every step, not only every student message.

Check yourself

Same made-up, illustrative trace. In call 2, the model asks to read a file (30 tokens), and the result is 500 tokens. How many input tokens does call 3 carry?

Show the answer

1,800 tokens: 1,270 + 30 + 500. Over the three calls, the input adds up to 1,040 + 1,270 + 1,800 = 4,110 tokens. Answering 500 or 1,570 drops text that is still in the history.

Student messages pile up the same way. Your design can treat this history as short-term memory: memory kept for one session, meaning one ongoing conversation, such as one visit. It can be saved so that the same conversation can resume later. It still belongs to that one conversation (LangChain memory overview).

Worked example: a four-question visit

To keep the sums short, this chat uses no tool steps. Made-up, illustrative numbers: standing instructions plus tool list are 1,000 tokens. Each question is 40 and each reply is 160. With question 2, the student pastes an 800-token manual section. Suppose you pay 1 made-up credit per 1,000 input tokens.

Here is a sketch of the code. call_model is a stand-in, not a real library. Assume INSTRUCTIONS is defined elsewhere and carries the tool list too.

history = []                      # short-term memory for this visit

def ask(question):
    history.append({"role": "user", "content": question})
    reply = call_model(instructions=INSTRUCTIONS,
                       messages=history)  # stand-in
    history.append({"role": "assistant", "content": reply})
    return reply
  1. history = [] makes a list that lives in your program. Each entry records who spoke (role) and what was said (content).
  2. messages=history passes the whole list on every call, not only the newest question.
  3. The second append saves the reply, so the next call includes it.
  4. Call 1 input: 1,000 + 40 = 1,040 tokens. There is no earlier history yet.
  5. Call 2: everything from call 1 (1,040), plus reply 1 (160), question 2 (40) and the pasted section (800) = 2,040.
  6. Call 3: 2,040 + 160 (reply 2) + 40 = 2,240. The pasted section is still inside that 2,040.
  7. Call 4: 2,240 + 160 (reply 3) + 40 = 2,440.
  8. Add up what you pay for: 1,040 + 2,040 + 2,240 + 2,440 = 7,760 input tokens, or 7.76 credits. That is far more than the last input of 2,440. The pasted section alone was sent three times, for 2,400 tokens.

Takeaway: anything that stays in the history is sent, and paid for, again on every later call.

A common mix-up

"The model remembers the earlier messages, so my program only sends the new one." It is tempting because chat apps feel continuous, like talking to one person. In the setup above, the continuity comes from sending the history again. Send only "and for 6 mm?", and nothing says 6 mm of what, or for which job.

Check yourself

Same made-up, illustrative chat, with nothing removed. Reply 4 is 160 tokens. The student sends a fifth question of 40 tokens. How many input tokens does call 5 carry?

Show the answer

2,640 tokens: 2,440 + 160 + 40. Answering 40 sends only the new message. Answering 200 forgets everything before reply 4. Both drop history that your program still sends.

3. A crowded context: clear and summarize 4 min

An AI game master runs a long text adventure. Early on, it was settled that the north door is locked. Many pages of map listings later, that one line is buried. The model is now more likely to miss it.

This is context rot: as the number of tokens grows, the model gets less accurate at recalling what is in the context (Anthropic on context for agents; docs).

It is a gradual slope, not a cliff at the limit. So treat context as a limited resource, where each extra bit of text helps less and can crowd out the rest. Aim for the smallest set of useful, relevant tokens that does the job (same article).

You have two ways to slim down. First, you can clear text: remove it once it has been used. Old tool results are the main example.

The second goes further. Compaction means summarizing a conversation that is nearing the limit, then starting a fresh window with the summary.

The source also counts clearing old tool results as one of the safest, lightest forms of compaction: it shrinks the context too, but writes no summary (article). In this lesson, "clear" means remove, and "compact" means summarize and start fresh.

A good summary keeps decisions, unsolved problems and important details. First make sure it keeps everything that matters. Only then trim the extra (article).

Worked example: the game master's context

Made-up, illustrative numbers: the window is 32,000 tokens. The context holds standing instructions (1,000), early talk (2,000), four old map listings returned by a tool (5,000 each), and recent messages (3,000). The early talk settled that the north door is locked, set an unsolved riddle and listed the player's inventory (the items they carry). In this game, any map can be fetched again.

  1. Count it: 1,000 + 2,000 + 20,000 + 3,000 = 26,000 tokens. It fits, but 20,000 of that is old map listings crowding the locked-door decision.
  2. Question each block: will a later step need this exact text? The listings have been used and can be fetched again, so they are good candidates to clear.
  3. Clear the listings, leaving a one-line placeholder for each, such as "Cellar map cleared; fetch again if needed". All four placeholders take 100 tokens. The context drops to 26,000 - 20,000 + 100 = 6,100.
  4. Much later, count again. The player has kept going, so the older talk (early decisions included) has grown from 2,000 to 18,000. Now: instructions 1,000 + placeholders 100 + older talk 18,000 + recent messages 3,000 = 22,100. The listings are already gone, so clearing them cannot help any more.
  5. Decide to compact. It still fits, but the window is about two thirds full and growing. In this example you choose to compact now, before the limit, so the early decisions are not buried in a long history.
  6. Write the summary: your program asks a model to write it, following instructions you give. That call uses tokens too. A 500-token summary then replaces the older talk and placeholders: 1,000 + 500 + 3,000 = 4,500. Keeping instructions and recent messages word for word is this example's design choice.
  7. Check the summary against a list: the locked north door (decision), the unsolved riddle (open problem) and the player's inventory (important detail). Suppose it has the door and riddle but no inventory. Change your summary instructions to require the inventory, then check again.

Takeaway: clear what is used up and easy to get back first. Then summarize, and check that nothing important got lost.

Now apply it to the visit from Section 2. Say your program removes the pasted section after question 2 is answered. Calls 3 and 4 then carry 1,440 and 1,640 tokens. The total input falls from 7,760 to 6,160. The risk: a follow-up question may need that section again.

A common mix-up

"A bigger window fixes this, so put everything in." It is tempting because a bigger window makes the "too long" error go away. Give the game master a made-up window ten times larger: the old listings fit easily, but they still crowd the locked-door line. And at 1 made-up credit per 1,000 input tokens, those 20,000 tokens cost 20 credits on every call that carries them.

Check yourself

4. Between sessions: notes the assistant saves 4 min

Think of a game save file. Close the game, and whatever lived only in RAM is gone. What you wrote to the save file loads next time.

A new session starts with a new, empty message history. Anything the assistant needs later must be saved by your system and put back into the context.

Long-term memory is information stored outside any one conversation and available in later sessions (LangChain memory overview).

One simple form is a note: a short piece of saved text or data, written outside the context window and loaded back when needed. Examples include a to-do list or a NOTES.md file (Anthropic article). For your makerspace, it could be one record per student.

Notes also help inside one long run. The agent writes down its progress, and reads it back after a compaction (article).

Saving a note does not change the model's training. The model sees the note only when its text is in the context.

Worked example: remembering Jordan's training

Jordan, a student, uses the assistant today and will be back next week. Jordan passed laser cutter training, confirmed on 3 November 2026. Today they also looked at Friday's free slots. Token counts here are made-up, illustrative numbers. Suppose the chat in today's visit is the same size as the one in Section 2: four questions of 40, four replies of 160 and one 800-token paste.

  1. Choose what to save: keep what is needed next visit and changes slowly. Training passed, with its date: yes. Friday's free slots: no, fetch them fresh. The whole chat: no, it is too big for what it tells you.
  2. Write two small functions: 
    import json
from pathlib import Path

def load_note(student_id):
    path = Path(f"notes/{student_id}.json")
    if path.exists():
        return json.loads(path.read_text())
    return {}        # first visit: nothing saved yet

def save_note(student_id, note):
    Path("notes").mkdir(exist_ok=True)
    path = Path(f"notes/{student_id}.json")
    path.write_text(json.dumps(note))
    load_note reads the student's file back into a dict. save_note makes the folder if needed and writes the dict as JSON, replacing the old file.
  3. Visit 1 ends: this call puts the fact on disk, outside the context: 
    save_note("s1042", {"laser_training": "passed",
                    "confirmed": "2026-11-03"})
  4. Visit 2 starts: load the note, add it to the instructions, and begin an empty history. 
    note = load_note("s1042")
instructions = INSTRUCTIONS + "\nSaved note: " + json.dumps(note)
history = []
  5. Send it: in Section 2's ask, change instructions=INSTRUCTIONS to instructions=instructions. The note counts only once it is in what gets sent.
  6. Compare sizes: allow about 50 tokens for the note, with room to spare. Today's chat is 4 x 40 + 800 + 4 x 160 = 1,600 tokens. The note is 32 times smaller, so loading it next week costs far less than loading the whole chat.
  7. Keep it current: when a fact changes, save an updated note with a new date, so stale facts can be spotted. Our advice: if the makerspace has an official training record, treat that record as the truth for permission to book.

Takeaway: between sessions, your system saves the few facts worth keeping and loads them back into the context.

A common mix-up

"The model will remember Jordan next time because it talked with them." It is tempting because some chat products appear to remember people. Start visit 2 with instructions = INSTRUCTIONS and history = [], and nothing sent mentions Jordan's training. The model has nothing to go on. The remembering is storage plus loading that you design.

Check yourself

A made-up, illustrative case: Sam finishes a visit about the vinyl cutter. During it, Sam said that step-by-step written answers always work best for them. Which item belongs in Sam's saved note?

5. Retrieval: fetching the right page 4 min

Your game engine throws an error. You do not reread all the engine's docs. You search for the error and open the matching part.

Retrieval is searching stored material while the assistant runs, and adding only the relevant parts to the context. The stored manuals act as a memory the assistant can look things up in.

To make that work, documents are split into chunks: small pieces, usually no more than a few hundred tokens, each of which can be found on its own. At question time, the best matches are added to the input (Anthropic on retrieval).

There are two main ways to match. Search by exact words is good for error codes and part numbers. Search by meaning compares numbers that stand for what a passage means, so it can find passages worded differently from the question. It can also miss an exact code (same article).

Could you skip retrieval?

Sometimes. If your documents are small enough, you can put all of them in the input instead (retrieval article). Check two things first.

Does it fit? Our made-up 24,000-token manual does not fit our made-up 20,000-token window. It would need a larger one.

Can you afford it? In a larger window, at our made-up price, the whole manual would cost 24 credits on each call. Sending only three small pieces of 300 tokens each would cost 0.9 credits. On those numbers, fetching pieces wins.

Worked example: error E-42

A student asks, "What does error E-42 mean on the laser cutter?" Made-up, illustrative numbers: the manual has 60 pages and 24,000 tokens. Instructions, tool list and question add up to 1,040 tokens, as in Section 1.

  1. Split the manual into 300-token chunks: 24,000 / 300 = 80 chunks. Do this ahead of time, so single pieces can be fetched later.
  2. Label each chunk with its machine, section and page, so it still makes sense alone. A chunk's text might start "Laser cutter, Troubleshooting, page 41".
  3. Search by exact words for "error E-42", because a code should match letter for letter. This toy code is far simpler than real search: 
    def search_manual(chunks, query, top=3):
    words = query.lower().split()
    def score(chunk):      # how many query words appear
        text = chunk["text"].lower()
        return sum(word in text for word in words)
    return sorted(chunks, key=score, reverse=True)[:top]
    words becomes ["error", "e-42"]. score counts how many of them appear in one chunk. The last line returns the three highest scorers.
  4. Add those 3 chunks: 3 x 300 = 900 tokens, so the input is 1,040 + 900 = 1,940. With the whole manual it would be 25,040.
  5. Check the result: does a chunk contain E-42 and name this machine? The code returns three chunks even when none is a good match.
  6. If the check fails, search again with other words. For a description such as "the beam keeps cutting out", try search by meaning, since the manual may word it differently.

Takeaway: retrieval keeps the long manual outside the context and brings in only the pieces this question needs.

A common mix-up

"Search by meaning is the smart one, so it always finds the right page." It is tempting because it can match a passage even when the wording differs. But a meaning search for "error E-42" might return a general page on error codes and miss the one line that mentions E-42. For an exact code or part number, search by exact words.

6. Put it together 4 min

For each piece of information, ask two questions. When is it needed? How fast does it change? Then give it a place.

Main worked example: Jordan comes back

Jordan asks, "What settings do I use for 3 mm acrylic, and can I have the laser on Friday?" Made-up, illustrative numbers: the window is 20,000 tokens, with 500 kept for the reply. Standing instructions are 600 tokens, the tool list 400, Jordan's note 50, the question 40, Friday's calendar listing 200, and the full manual 24,000, split into 300-token chunks.

  1. Instructions (600) and tool list (400): every call. The assistant needs its rules and its list of tools each time.
  2. Jordan's note (50): load at the start. It is small and needed. Once loaded, it goes along with each call.
  3. Question (40): into the history. The starting input is 600 + 400 + 50 + 40 = 1,090.
  4. Manual: fetch when needed. Retrieve 3 chunks on acrylic settings, 900 tokens, instead of all 24,000.
  5. Friday's calendar (200): fetch fresh. Slots change, so keep them out of the note. Clear the listing once it is no longer needed.
  6. Check the size: 1,090 + 900 + 200 = 2,190 input tokens, or 2,690 with reply room, so it fits. With the whole manual instead, the input would be 1,090 + 24,000 + 200 = 25,290, which does not.
  7. If the visit runs long: clear used results first. If it is still crowded, compact, keeping the chosen settings and any unfinished booking.
  8. End of visit: save only lasting changes. A Friday booking lives in the booking calendar, so the note need not copy it. If nothing lasting changed, the note stays as it is.

If you missed an item, ask "When is it needed, and how fast does it change?" and sort it again.

Summary 3 min with next steps

  • Everything the model reads and writes in a call must fit the context window, counted in tokens.
  • Between steps, the history is sent again, so the input grows and so does the cost.
  • A crowded context hurts recall: clear used results first, then summarize and check the summary.
  • In a new session, count on earlier information only if your system saved it and loads it back. A good note is small, useful and slow to change.
  • Long material stays outside and is retrieved in pieces, unless putting it all in is simpler, fits and is affordable.
