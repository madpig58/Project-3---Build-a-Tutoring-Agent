# Plan: lesson 0001, Context and memory in an agent (O3), 30 minutes, 4500 words

Win: By the end of this lesson you can decide, for the makerspace assistant, what stays in the model's context during a request, what is fetched from the manuals on demand, and what is saved between visits, and give a cost-and-quality reason for each choice.

Starts from:
- Record 0001: a model maps text in to text out, and knows only its training plus the text it is given. This is the floor: context and memory are both about what text is given. Tokens came up only in passing.
- Record 0002: Riley can trace the loop ("Is the laser cutter free on Friday?"). Not yet checked: that the program (not the model) runs each tool and that each step is a separate model call. Section 2 builds this in gently, as a reveal inside a trace Riley already knows, not as a correction.
- NOTES: Python-comfortable (lists, dicts, JSON, one web API call); has heard "token" and "context window" but cannot say what they limit or why they cost; no ML background; small model budget.
- Likely misconceptions: (a) the model remembers earlier steps by itself; (b) a bigger window means it uses everything perfectly; (c) memory means the model "learns" the student.
- Preferences applied: concrete example first, then the general idea; short paragraphs; one idea at a time; each term defined at first use; code and game-engine analogies; direct feedback. No prices quoted; use made-up round numbers labelled as illustrative.

Learning objectives:
1. You can say what a token and the context window are, and what the window limits.
2. You can explain what is kept between the steps of one loop: the program re-sends the growing transcript, and the model itself keeps nothing.
3. You can explain why context size drives cost and answer quality, and name two ways to shrink it (clearing old tool results, compaction).
4. You can explain how retrieval finds the right manual pages instead of loading whole manuals, and when loading everything is fine.
5. You can explain how notes saved in files give memory between sessions, and who runs the save and load.

## Section 1: Tokens and the context window (600 words)
- Objective 1.
- New terms: token (a chunk of text, often a word or part of a word, that the model reads and writes as one unit); context window (the most tokens the model can take in and produce in one call, counting everything it is given).
- Opening example: a game-engine analogy, a fixed-size frame or render budget: the engine can draw only so much per frame, so you choose what goes in. Then the concrete: the bandsaw manual is 120 pages; a short question plus the manual may not fit in one call.
- Worked example (illustrative numbers, stated as such): split "Can I book the laser cutter on Friday?" into tokens by hand (about 8 tokens, "Friday" maybe 1 or 2), then the rule of thumb of roughly 3/4 of a word per token in English, so a 300-word manual page is about 400 tokens and a 120-page manual about 48,000 tokens. Steps: 1. Count words on one page. 2. Convert to tokens. 3. Multiply by pages. 4. Compare with a window size given as a made-up round number (e.g. 32,000) and see it does not fit. 5. Note that the system prompt, the tool descriptions and the answer also use window space. Optionally a 6-line Python snippet estimating tokens as `len(text.split()) * 4 // 3`, clearly labelled a rough estimate, not a real tokenizer.
- Practice: "A manual is 30,000 words and the window is 32,000 tokens. Does it fit with room for a question and answer?" Tempting wrong answer: "Yes, 30,000 is less than 32,000", because it treats words as tokens and forgets the prompt and answer also need space (30,000 words is about 40,000 tokens).
- Misconception: "The context window is the model's memory of the student." It is only the input and output of one call.
- Citations: context is the set of tokens included when sampling from the model, and is a finite resource - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents. The 3/4 word per token figure is a rule of thumb: state as approximate, uncited.

## Section 2: Between steps: the transcript is re-sent (600 words)
- Objective 2.
- New terms: transcript (the list of all messages so far in this request: the question, each tool call, each result); stateless (the model keeps nothing from one call to the next).
- Opening example: Riley's own traced request from record 0002, now shown as Python: a `messages` list and a `while` loop. Each pass calls `call_model(messages)`, the model returns either a tool request or a final answer, the program runs the tool, appends the result, and loops. Pseudocode, no vendor API, about 10 lines.
- Worked example: trace "Is the laser cutter free on Friday?" call by call. Call 1 receives [question]; returns "request check_calendar(laser, Friday)". The program (not the model) runs it. Call 2 receives [question, tool request, result]; returns the final answer. Steps: 1. Show what call 1 receives. 2. Show the model's output is only a request. 3. Show the program running the tool and appending. 4. Show call 2 receives the whole list again, longer. 5. Ask what call 2 would see if the program forgot to append: the model would ask again, forever. Riley learns two facts from this: each step is a separate model call, and the program runs the tool.
- Practice: "In call 3 of a loop, where does the model get the result of call 1's tool?" Options built to equal length. Tempting wrong answer: "It remembers it from call 1", because it feels like a conversation with one continuing mind; correct: the program put it in the transcript sent with call 3.
- Misconception: the model remembers earlier steps. Feedback includes the one-line consequence: this is why the transcript grows each step.
- Citations: the loop re-sends context each turn and the agent runs tools in a loop - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents (cited for "agents running in a loop generate more data that could be relevant for the next turn"; keep the claim to that).

## Section 3: Why size costs money and quality (600 words)
- Objective 3.
- New terms: context rot (answers get less reliable at recalling details as the context fills); compaction (summarizing a long transcript and starting a fresh one with the summary).
- Opening example: a 10-step request where each tool result is a 2,000-token manual page. Because the transcript is re-sent in full, step 10 sends about 20,000 tokens of old pages.
- Worked example (illustrative numbers): cost counted in tokens sent, over steps. Steps: 1. Each step adds 2,000 tokens. 2. Tokens sent at step n is about 2,000 x n. 3. Sum over 10 steps = 2,000 x 55 = 110,000 input tokens, not 20,000. 4. Cost is roughly proportional to tokens, so doubling steps roughly quadruples input. 5. Now clear the page text after the model has used it, keeping a one-line note "read bandsaw p.14: blade change steps" - input falls to about a fraction (compute with the learner). 6. Quality: older text still competes for the model's attention; relevance matters, not only fit.
- Practice: "Your budget is tight. Which change cuts input tokens most: (a) shorter final answers, (b) clearing old tool results after use, (c) a smaller tool description?" Tempting wrong answer: (a), because output is visible and feels expensive, but the re-sent transcript dominates over a many-step request. Equal-length options, correct not first.
- Misconception: "A bigger window means the model uses all of it perfectly." Context rot: accuracy drops as tokens increase, with diminishing returns.
- Citations: finite resource, diminishing returns, context rot, attention budget, compaction and clearing tool results as the lightest form - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents; context editing clears stale tool results near limits - https://www.anthropic.com/news/context-management. The pricing proportionality claim is general: state without a price and without citation.

## Section 4: Retrieval: fetching the right manual pages (600 words)
- Objective 4.
- New terms: retrieval (finding the few relevant pieces of a large text and adding only them to the prompt); chunk (one piece of the manual, such as a section or a page).
- Opening example: a game with a huge asset library: you do not load every texture at level start, you keep a list of names and load what the level needs. Same for manuals: keep an index, load the page.
- Worked example: question "How do I change the bandsaw blade?" Steps: 1. Pre-split the manuals into chunks with an ID like `bandsaw/p14`. 2. Search the chunks (plain keyword match is enough to show the idea: score chunks by shared words with the question, in a few lines of Python, no embeddings). 3. Put the top 2 chunks into the prompt, about 800 tokens instead of 48,000. 4. Show the failure: a chunk that says "Remove it before step 3" with no machine name; the chunk lacks its context, so add a short header "Bandsaw manual, blade change:" to each chunk. 5. Show the just-in-time variant: the agent keeps only chunk IDs and calls a `read_page(id)` tool, so it loads text only when needed. Mention hybrid is common.
- Practice: decision question: "The makerspace has one 40-page safety sheet of about 20,000 tokens, read in nearly every request, and 30 long manuals. What do you retrieve and what do you load always?" Tempting wrong answer: retrieve everything, because retrieval sounds more advanced; but a short, always-needed document is cheaper and safer to load whole (and, if the whole knowledge base is small, about 200,000 tokens or less, you can skip retrieval). Note the cost side: always-loaded text is paid for every step, so 20,000 tokens is a real trade-off. Let the answer be nuanced: load the one-page rules, retrieve the rest.
- Misconception: "Retrieval makes the model know the manual." It only places chosen text in this call's input; a bad search means the right page never arrives.
- Citations: RAG fetches relevant chunks and adds them to the prompt; chunks can lack context; knowledge bases under about 200,000 tokens can go in the prompt whole - https://anthropic.com/research/contextual-retrieval. Just-in-time retrieval with lightweight identifiers, hybrid recommended - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents.

## Section 5: Notes as memory between sessions (600 words)
- Objective 5.
- New terms: session (one conversation or visit, which ends when the program stops sending the transcript); memory store (files the program keeps outside the context window and loads again later).
- Opening example: a save file in a game. The game does not keep your progress in RAM after you quit; it writes a file and loads it next launch. Student training status works the same way.
- Worked example: student 4417 visits Monday, completes the laser cutter training. Steps: 1. The model, during the loop, requests a file operation, e.g. create `/memories/students/4417.md` with "laser cutter: trained 2026-11-24; bandsaw: not trained". 2. The program (not the model) checks the path, applies a size cap and writes the file. 3. Visit ends; the transcript is thrown away. 4. Next visit, a new session starts with an empty transcript. 5. The program views the file (or loads it at start) and puts its text in the context; the model answers "You're cleared for the laser cutter, not the bandsaw." 6. Show a sketch of the six operations (view, create, str_replace, insert, delete, rename) as plain verbs, with only create, view and str_replace used. Point out the app is responsible for safety and size, and that a real training record may belong in the makerspace's own database, with the model reading it by a tool, since notes can be wrong or stale. Keep this to one sentence, as a design tension for later.
- Practice: "A student says 'I finished bandsaw training yesterday'. Should the assistant write that to the memory file?" Tempting wrong answer: "Yes, remembering what users say is the point", because memory seems to mean store everything; correct: not without a check against the official record; notes are text the model writes, so they can hold unverified claims.
- Misconception: memory means the model learns or changes. The model is unchanged; only the files persist.
- Citations: memory tool stores files under /memories that persist across conversations; the model requests operations, the application runs them and handles path checks and size caps - https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool; memory outside the window - https://www.anthropic.com/news/context-management; structured note-taking persisted outside the context window, NOTES.md or to-do list - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents.

## Section 6: Main worked example and faded decision exercise (600 words)
- Objectives 1-5 together.
- Worked example (about 300 words): request "Can I use the bandsaw tomorrow afternoon, and how do I swap the blade?" from a returning student. Walk through a table with columns: what, which timescale, where it lives. Steps: 1. Session start: the program loads the student's note (memory, between sessions). 2. Call 1 gets system prompt, tool descriptions, the note, the question (context window). 3. Model requests `check_training` or reads the note: not trained on the bandsaw, so it stops booking and says so. 4. For the blade question, it requests `search_manual`; the program runs it, appends 2 chunks (between steps, transcript). 5. Before the final call, old tool results are cleared if the loop was long. 6. Final answer; the program updates the note with "asked about bandsaw blade, not yet trained". Totals the rough tokens at each call using the earlier made-up numbers, ending near a few thousand, versus tens of thousands if the manual were preloaded.
- Faded practice (about 300 words): a similar request, "Book me the 3D printer Friday and tell me the filament temperature", with steps faded: step 1 given; steps 2 and 3 as prompts ("what is in the transcript now?"); steps 4 and 5 left blank for the learner to fill in decisions (what to retrieve, what to save, what to clear). Solution on demand. Direct feedback checklist: did they put the manual in as retrieved chunks, did they say who runs each tool, did they save only the verified fact.
