Context and memory in an agent: what it sees, what it keeps, what it saves

By the end of this lesson you can decide, for the makerspace assistant, what stays in the model's context during a request, what is fetched from the manuals on demand, and what is saved between visits, and give a cost-and-quality reason for each choice.

Why this matters for you

Your mission says you must decide what the assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual. Those are exactly the three choices in this lesson, and each one moves your model budget.

Warm-up 3 min

Picture a student at the makerspace asking: "How do I change the blade on the bandsaw, and am I cleared to use it?"

To answer, the assistant must read a long manual, check the student's training status, and still know that student next week. That is three different time spans: inside one model call, between the steps of one request, and between visits. This lesson takes them one at a time.

First, two questions from earlier sessions. Answer from memory before you open the answers.

Recall 1

For "Is the laser cutter free on Friday?", list the four beats of the agent loop in order.

Check your answer

1. The model asks for an action, such as check_calendar(laser, Friday). 2. The program carries it out. 3. The result goes back to the model. 4. The model either asks for another action or writes the final answer.

Beat 3 is the one people skip. "Ask, run, answer" sounds complete, but the final answer depends on the result, so something has to put the result in front of the model. Who does that, and how, is the heart of this lesson.

Recall 2

Why can a chatbot state an outdated fact with confidence?

Check your answer

The model knows only what it learned in training plus the text it is given. Training stops at some date, and the model writes plausible text whether or not it is true.

A plain chatbot does not look anything up. Today is about the second half of that sentence: the text it is given.

Tokens and the context window 4 min

Think of a game engine drawing a frame. It has a fixed budget per frame, so you choose what goes on screen. A model call works the same way: there is a fixed amount of text it can take in at once, and you choose what goes in.

A token is a chunk of text, often a whole word or part of one, that the model reads and writes as one unit. The context window is the most tokens one model call can take in and produce, counting everything it is given plus the answer. Anthropic describes context as "the set of tokens included when sampling" from the model, and as a finite resource (Effective context engineering for AI agents).

All numbers in this lesson are illustrative round numbers, not figures for any real model. The rule of thumb that English averages about 3/4 of a word per token is also only a rough guide.

Worked example: does the bandsaw manual fit?

The bandsaw manual is 120 pages of about 300 words each. Assume a 32,000-token window.

  1. Tiny split by hand: "Can I book the laser cutter on Friday?" is 8 words. One plausible split is Can I book the laser cutter on Friday ?, which is 9 tokens. A real tokenizer may cut "Friday" or "laser" differently.
  2. Words on one page: 300.
  3. Convert to tokens. Dividing by 3/4 is the same as multiplying by 4/3: 300 × 4/3 = 400 tokens per page.
  4. Multiply by pages: 400 × 120 = 48,000 tokens for the whole manual.
  5. Compare with the window: 48,000 is more than 32,000, so it is 16,000 tokens over. It does not fit.
  6. The window counts everything. If the system prompt and tool descriptions take 1,000 tokens and the answer needs 500, then 32,000 − 1,000 − 500 = 30,500 tokens remain. At 400 per page that holds 76 pages at most.

A rough estimator in Python (a guess, not a real tokenizer):

def est_tokens(text):
    return len(text.split()) * 4 // 3   # words x 4/3

The function splits the text into words and scales by 4/3, which is how we got from 300 words to 400 tokens.

A common mix-up

"The context window is the model's memory of the student." The word "context" sounds like a running memory, which makes this tempting. But the window is only the input and output of one call. If call A says "I'm Riley, trained on the laser cutter" and a separate call B asks "What's my training status?", call B cannot know, because call A's text was never sent with it.

Check yourself

A manual is 30,000 words and the window is 32,000 tokens. Does it fit, with room for a question and an answer?

Show the answer

The second option. Words convert to more tokens (× 4/3), so 30,000 words is about 40,000 tokens, over the 32,000 window.

Your turn

Your 3D printer manual has 60 pages of 250 words each. Estimate its size in tokens, then say whether it fits in the 32,000-token window with 1,500 tokens reserved for the prompt, tools and answer.

Show a solution

60 × 250 = 15,000 words. 15,000 × 4/3 = 20,000 tokens. The room left is 32,000 − 1,500 = 30,500 tokens, and 20,000 is less than that, so it fits once. Whether you should load it every time is a different question, which the next two sections answer.

Between steps: the transcript is re-sent 4 min

Now take the request you already traced, "Is the laser cutter free on Friday?", and look at it as code. Two new terms first. The transcript is the list of all messages so far in this request: the question, each tool request, each result. A model is stateless when it keeps nothing from one call to the next.

Here is the loop as pseudocode, with no real vendor API:

messages = [{"role": "user", "text": question}]
while True:
    reply = call_model(messages)          # one separate model call
    messages.append(reply)
    if reply["type"] == "final":
        break
    result = run_tool(reply["tool"], reply["args"])   # the PROGRAM runs it
    messages.append({"role": "tool", "text": result})

Two things to notice in the code. Every pass through the while loop is its own call to call_model. And run_tool is ordinary program code: the model only asked for it.

Worked example: two calls, token by token

Token counts are illustrative and the system prompt is left out.

  1. Call 1 receives [question], about 12 tokens.
  2. The model's output is only a request: check_calendar(laser, Friday), about 20 tokens. It cannot run anything.
  3. The program runs the tool and gets "free 12:00-17:00", about 30 tokens. It appends both the request and the result to messages.
  4. Call 2 receives [question, request, result]: 12 + 20 + 30 = 62 tokens. The whole list goes again, longer.
  5. Suppose the program forgot to append. Call 2 would receive [question] again, the model would make the same request, and the loop would never end.

So: each step is a separate model call, the program runs the tools, and the only thing carried between steps is the transcript the program re-sends.

A common mix-up

"The model remembers the earlier steps by itself." The loop feels like a conversation with one continuing mind, so this is tempting. Delete the append lines from the code above and the agent forgets every result. One consequence: because everything is re-sent, the transcript grows every step. The next section shows why that costs money.

Why size costs money and quality 4 min

Providers charge by tokens, so what you send each call matters. Cost is roughly proportional to the input tokens sent, plus output tokens. Because the transcript is re-sent in full, old text is paid for again at every later step. The figures below assume no caching discount, so check your provider's pricing.

There is a second price, which is quality. Context rot is the finding that as the number of tokens in the context grows, the model's accuracy at recalling details from it falls. Anthropic calls context "a finite resource with diminishing marginal returns" (Effective context engineering for AI agents). Bigger is not better; relevant is better.

Worked example: a 10-step request

Each step fetches one manual page of 2,000 tokens. To keep the arithmetic simple, count call n as sending n pages and ignore the question and system prompt.

  1. Each step adds 2,000 tokens to the transcript.
  2. The transcript is re-sent in full, so call n sends about 2,000 × n tokens: 2,000, 4,000, and so on up to 20,000.
  3. Sum over 10 steps: 2,000 × (1 + 2 + ... + 10) = 2,000 × 55 = 110,000 input tokens, not 20,000.
  4. Double the steps to 20: 2,000 × 210 = 420,000. That is about 3.8 times more, so doubling the steps roughly quadruples the input.
  5. Now clear each page's text after the model has used it, keeping a 30-token note such as "read bandsaw p.14: blade change steps". Call n sends 2,000 for the new page plus 30 for each earlier note: 2,000 × 10 + 30 × (0 + 1 + ... + 9) = 20,000 + 30 × 45 = 21,350 tokens.
  6. Compare: 110,000 / 21,350 is about 5. Input falls to about one fifth, and the model has less old text competing with the page it needs now.

This is the idea behind two ways to shrink the context. Compaction means summarizing a long transcript and starting a fresh context with the summary; the lightest form is clearing old tool results, which is what step 5 did (Anthropic). Anthropic's platform can do the clearing for you when a request nears its token limit (context management).

A common mix-up

"A bigger window means the model uses everything in it perfectly." If it fits, it seems like it should be used. But recall gets less reliable as the context fills. Picture a blade-change instruction on page 2, buried under nine other pages. It fits, yet the model is more likely to miss it than if only that page were present.

Check yourself

A booking agent runs 8 steps. Each step the calendar tool returns a 1,500-token listing, the tool description is 300 tokens and re-sent every call, and the final answer is 200 tokens. Budget is tight. Which change cuts the most input tokens?

Replacing used listings with notes. Re-sent old results are the biggest part of the input: 54,000 tokens versus 12,560 with notes.

Your turn

A 6-step request fetches a 1,000-token page at each step and keeps all of them. Compute the total input tokens. First step given: call n sends 1,000 × n tokens.

Show a solution

The sum is 1,000 × (1 + 2 + 3 + 4 + 5 + 6) = 1,000 × 21 = 21,000 input tokens. The last page alone is only 1,000, yet the total is 21 times that. With 15-token notes in place of used pages it would be 1,000 × 6 + 15 × (0 + 1 + ... + 5) = 6,000 + 225 = 6,225.

Retrieval: fetching the right manual pages 4 min

A game does not load every texture when a level starts. It keeps a list of asset names and loads what the level needs. The assistant can treat manuals the same way.

Retrieval means finding the few relevant pieces of a large text and adding only those to the prompt. A chunk is one piece of the manual, such as a page. This approach is often called retrieval-augmented generation, and Anthropic describes it as fetching relevant chunks and adding them to the model's prompt (Contextual Retrieval).

Worked example: "How do I change the bandsaw blade?" 
chunks = {
 "bandsaw/p14": "Bandsaw manual, blade change: unplug the machine, open the wheel cover, release the tension and slip the old blade off.",
 "bandsaw/p15": "Bandsaw manual, blade tension: after fitting, set the tension knob to the mark for the blade width.",
 "laser/p07":   "Laser cutter manual, lens care: wipe the lens, and change the filter each month.",
}
STOP = {"how", "do", "i", "the", "a", "to", "it", "and"}
def words(t): return {w.strip(",.:?").lower() for w in t.split()} - STOP
def top_chunks(question, k=2):
    q = words(question)
    scored = [(len(q & words(t)), cid) for cid, t in chunks.items()]
    return sorted(scored, reverse=True)[:k]
  1. Split the manuals into chunks with IDs such as bandsaw/p14. The dictionary above does that.
  2. Score each chunk by the words it shares with the question. Without the stop words, the question is {change, bandsaw, blade}. Page 14 shares all 3, page 15 shares 2 (bandsaw, blade), and the laser page shares 1 (change).
  3. top_chunks(...) returns [(3, 'bandsaw/p14'), (2, 'bandsaw/p15')]. Put those two chunks in the prompt: about 400 tokens each, 800 in total, instead of 48,000. That is 60 times fewer.
  4. A failure to expect: a chunk that reads only "Remove it before step 3" does not say which machine. So each chunk above starts with a short header, "Bandsaw manual, blade change:".
  5. A just-in-time variant: keep only the chunk IDs in context and give the agent a read_page(id) tool, so text loads only when needed. Anthropic describes this as keeping "lightweight identifiers" and loading data at runtime, and notes that many systems mix both styles (Effective context engineering).

Plain word counting is enough to show the idea. Real systems score more cleverly, which is for a later lesson.

A common mix-up

"Retrieval makes the model know the manual." After retrieval the answer is right, so it feels like the model knows. In fact retrieval only places chosen text in this call's input. If the search returned laser/p07 for a blade question, the right page would never arrive and the model would have nothing correct to work from.

Check yourself

The makerspace has a 40-page safety sheet of about 20,000 tokens, with key rules that fit on one page and are needed in almost every request, plus 30 long manuals of about 48,000 tokens each. What do you do?

The first option. Always-needed short text is loaded whole; large reference text is retrieved on demand. Anthropic also notes that if your whole knowledge base is under about 200,000 tokens, you can skip retrieval and put it all in the prompt (Contextual Retrieval).

Notes as memory between sessions 4 min

A game does not keep your progress in memory after you quit. It writes a save file and loads it next launch. The same idea works for a student's training status.

A session is one visit, ending when the program stops sending the transcript. A memory store is files the program keeps outside the context window and loads again later. Anthropic's memory tool works this way: the model can create, read, update and delete files under a /memories directory, and they persist between sessions (Memory tool docs). The announcement describes it as storing and consulting information "outside the context window" (context management).

One thing matters most for your design: the model only requests memory operations, and your application runs each one. Your program also decides where files live and handles checks such as path safety and size caps (Memory tool docs). Writing notes outside the window is also a general technique, which Anthropic calls structured note-taking, such as keeping a NOTES.md file (Effective context engineering).

Worked example: student 4417 finishes laser cutter training
  1. During the loop the model requests: create /memories/students/4417.md with "laser cutter: trained 2026-11-24; bandsaw: not trained". It only requests.
  2. The program checks that the path is under /memories, applies a size cap and writes the file.
  3. The visit ends and the transcript is thrown away.
  4. At the next visit a new session starts with an empty transcript. The model knows nothing about 4417.
  5. The program views the file and puts its text in the context. The model now answers "You're cleared for the laser cutter, not the bandsaw."
  6. Only three memory operations appear in this sketch:
def run_memory(cmd):                       # the PROGRAM runs this
    path = check_path(cmd["path"])         # must be inside /memories
    if cmd["op"] == "view":        return read(path)
    if cmd["op"] == "create":      write(path, cmd["text"][:MAX_BYTES])
    if cmd["op"] == "str_replace": replace(path, cmd["old"], cmd["new"])

Notice that check_path and the size cap live in your code, not in the model.

A design tension for your review: notes can be wrong or stale, so an official training record may belong in the makerspace's own database, which the model reads through a tool. Storing student data also raises privacy questions, which come later.
A common mix-up

"Memory means the model learns or changes." "Remembers you" sounds like the model itself has changed. But delete /memories/students/4417.md and the assistant forgets student 4417 at once, though nothing else changed. Everything it knew was in the file, and the model is exactly as it was.

Worked example and practice 4 min

Now all five ideas at once. Numbers are illustrative: system prompt plus tool descriptions 800 tokens, the student's note 60 tokens, the question 25 tokens, each retrieved chunk about 400 tokens, and the 32,000-token window from section 1.

Worked example: a returning student

Student 5108 asks "Can I use the bandsaw tomorrow afternoon, and how do I swap the blade?" Their note says "laser cutter: trained; bandsaw: not trained".

WhatTimescaleWhere it lives
System prompt, tools, note, questionone callthe context window
Request and result so farbetween stepsthe transcript, re-sent by the program
Training statusbetween sessionsa file in the memory store
Manual pagesfetched when neededthe chunk index
  1. Session start: the program loads student 5108's note (memory between sessions).
  2. Call 1 receives system prompt, tools, note and question: 800 + 60 + 25 = 885 tokens.
  3. The model sees "bandsaw: not trained", so it will not book the bandsaw and will say why. For the blade question it requests search_manual("bandsaw blade change"), about 30 tokens.
  4. The program runs the search and appends the top 2 chunks, 2 × 400 = 800 tokens. Call 2 receives 885 + 30 + 800 = 1,715 tokens. The model requests a note update, "asked about bandsaw blade, not yet trained" (about 40 tokens), and the program writes it.
  5. Clearing old tool results is not needed for a loop this short. In a 10-step loop it would be, as in section 3.
  6. Call 3 receives 1,715 + 40 + 20 (the "ok" result) = 1,775 tokens. The model gives the final answer: "Not booked: you aren't trained on the bandsaw. Please take training first; the blade steps are on bandsaw/p14 of the manual."

Total input: 885 + 1,715 + 1,775 = 4,375 tokens, about 4,400. If the 48,000-token manual were preloaded, every call would carry it: at least 3 × 48,000 = 144,000 tokens, and it would not fit in the window at all. Each piece went where it is cheapest and safest.

Your turn

Show a solution

2. System prompt and tools, the note and the question: 800 + 50 + 20 = 870 tokens.

3. The program runs it. It appends the request and the calendar result (about 100 tokens), so the next call receives about 870 + 30 + 100 = 1,000 tokens.

4. Retrieve only the top 2 chunks that mention filament, with a header naming the machine: 2 × 400 = 800 tokens. Do not load the whole manual.

Check yourself against this list

Did you put the manual in as retrieved chunks? A whole manual (about 48,000 tokens) would not fit and would be re-sent every step. Did you say the program runs each tool? The model only requests. Did you save only the verified fact? Notes can carry unchecked claims. Did you count tokens as a sum over calls? Each call re-sends the transcript.

Summary 3 min

  • The context window limits what one call can take in and produce, and you pay per token sent.
  • The model is stateless: the program re-sends the transcript each step, so it grows and old text is paid for again.
  • Clear old tool results or compact to save cost, and because a fuller context recalls details less reliably.
  • Retrieve the few manual pages you need; load short always-needed text whole.
  • The only memory between sessions is files your program saves and loads, so verify what you save.

Compare with a model answer

Each model call sees only the text sent with it, and the model keeps nothing afterward. Within one request the program re-sends the transcript, and between visits the program saves notes in a file and loads them into the next call. So "memory" is something we build, and we choose what to save and what to leave out.
