Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable store, and say why.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three problems are the same problem: what does the model see on each call, and what does it cost to put it there?

Warm-up 2 min

Recall

From your agent-loop session: a student asks, "Is the laser cutter free on Friday?" The model decides to check the calendar. In your own words, what happens next, and who actually runs the calendar tool? Say it before you look.

Check your answer

The model writes a request naming the tool and its arguments. The program around the model runs the tool, puts the result back into the conversation, and calls the model again. The model never runs anything itself. Today's question is about that last step: what exactly does the program send on the next call?

The context window 5 min

Start with an everyday example. You are doing a group project and you can only think about what is on your desk right now. Anything in your notebook at home, or in last week's meeting, does not exist for you until someone puts it on the desk. A language model is like that, and the desk is small and you pay by the item.

The context is all the text the model is given on one call. The context window is the limit on how much text that can be: the model can use everything inside it and nothing outside it. The Claude documentation calls it a "working memory" and is explicit that it is different from the large body of data the model was trained on (Claude Platform Docs, Context windows).

Text is counted in tokens: small chunks of text, often a short word or part of a longer one. A rough rule for English is that one token is about three quarters of a word, so a page of a manual is a few hundred tokens. Tokens matter twice: they fill the window, and the provider bills per token.

What is in the context of one call? Everything the model is sent:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Never book a machine without checking training.");
  • the tool definitions: the names and descriptions of check_calendar, search_manuals and the rest;
  • the messages so far: the student's questions, the model's earlier replies, and every tool result.

The docs say it plainly: everything in the request counts toward the window, including tool results and tool definitions, and the output the model generates counts too (Context windows). Anthropic's engineers put it as a general definition: context is "the set of tokens included when sampling" from the model (Effective context engineering for AI agents).

A common mix-up

"The model has read our manuals, so it knows them." Tempting, because chatbots do seem to know a lot. But what a model learned in training is a blur of general patterns, and it may be out of date, which you have already seen when a chatbot stated an old fact with confidence. Your makerspace's manuals were never in training. Unless the page is in the context, the model cannot quote it, and a model that lacks the page will often guess fluently instead of saying so.

Check yourself

Which of these is part of the context on a model call?

Show the answer

The tool descriptions. Only text the program sends in this request is in the context; files on a server and old chats are not, unless they are sent.

What is kept between steps 6 min

Here is the idea that surprises most people: the model keeps nothing between calls. Each model call starts from zero. The program is what remembers, by sending the whole conversation again every time. The Claude docs describe each turn as an input phase that "contains all previous conversation history plus the current user message", and the model's reply then becomes part of the input for the next turn (Context windows).

In your agent loop, every step is a separate model call, and every call carries everything that came before. So the context only grows during a run, and so does the bill. Here is a worked example with illustrative numbers.

Worked example: counting input tokens

A student asks: "Is the laser cutter free tomorrow at 3 pm, and how thick can I cut acrylic?" Assume the system prompt plus tool definitions are 2,000 tokens, the question is 50, each tool request the model writes is 50, and the results are: calendar 300, manual page 3,000. The model makes three calls: calendar, manual, final answer.

  1. Call 1 sends system + tools + question: 2,000 + 50 = 2,050 tokens. The model asks for the calendar.
  2. Call 2 sends all of that, plus the model's request (50) and the calendar result (300): 2,050 + 50 + 300 = 2,400. The model asks for the manual.
  3. Call 3 sends everything again, plus the request (50) and the manual page (3,000): 2,400 + 50 + 3,000 = 5,450. The model writes the answer.
  4. Total input over the run: 2,050 + 2,400 + 5,450 = 9,900 tokens, though only 3,350 tokens of new material was ever added beyond the fixed 2,000 and the question.

Two lessons for your budget. First, a long run costs more than the sum of its steps, because early material is paid for again on every later call. Second, a big tool result is expensive twice: once when it arrives and again on every call after. (Providers offer prompt caching, which lowers the price of re-sent text that has not changed, but cached text still occupies the window, as the docs note.)

The numbers are made up to show the pattern; real token counts depend on the text. The API reports the true count in each response, and a token counting tool can estimate before you send.
A common mix-up

"The model remembers the first tool result because it saw it." It remembers only because the program sent it again. If your program forgot to include the calendar result in call 3, the model would behave as if it never looked. When your assistant seems to forget something mid-run, check what the program put in the request.

Check yourself

An agent run makes five model calls. Which statement about the first tool result is true?

Show the answer

It is re-sent and counted again on each later call. The model remembers nothing; the program carries the history, and you pay for it every time.

When the window fills up 5 min

Even with a window of up to a million tokens, available on current Claude models (Context windows), "more room" is not the answer. There are two reasons.

Cost. As you just saw, every token in the window is paid for on every call.

Quality. The docs warn that "as token count grows, accuracy and recall degrade", a phenomenon called context rot, so curating what is in the context matters as much as how much space there is. Anthropic's engineers explain that the model has a finite "attention budget" and that the goal is "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome" (Effective context engineering). Think of a desk piled with every handout you have ever received: the one page you need is somewhere on it, and you get slower and more error-prone at finding it.

So a good agent program manages its context. Three tools, from lightest to heaviest:

TechniqueWhat it doesMakerspace example
Clearing old tool resultsDrops the bulky output of tool calls the model has already used.Delete the 3,000-token manual page once the answer is written down.
TrimmingDrops the oldest messages and keeps the recent ones.In a long chat, keep the last ten messages and the system prompt.
CompactionHas the model summarize the conversation, then starts a fresh window from the summary."Student wants to cut 6 mm acrylic on the laser; booked Friday 3 pm; still needs training."

Anthropic describes compaction as summarizing the context near its limit and reinitiating a new window with the summary, keeping key decisions and unresolved problems while discarding redundant tool output. Clearing old tool results is "one of the safest, lightest touch forms of compaction" (Effective context engineering). The Claude platform offers both tool-result clearing and server-side compaction as built-in options (Context windows). The trade-off is that anything dropped is gone from the model's view, so the question is always: what will the model need later?

A common mix-up

"Buy a bigger window and the memory problem goes away." A bigger window delays the overflow, but it does not stop cost from growing on every call, and it does not stop recall from getting worse as it fills. It also does nothing for the next session, which starts with an empty window however large.

Check yourself

Your assistant fetched a 4,000-token safety sheet to answer one question, then the student chats on for twenty more messages. What is the cheapest sensible fix for the rising cost?

Show the answer

Clear the used tool result. Telling the model to ignore text does not remove it from the request, so you still pay for it.

Between sessions: notes as memory 6 min

Now the second kind of "between". A student trains on the laser cutter on Monday and comes back on Thursday. When the Thursday session starts, the window is empty. The model knows nothing about Monday, because nothing from Monday is in the request.

The fix is the same as with a notebook at home: write things down, outside the window, and bring them back when needed. Agent frameworks call the first kind short-term memory: the conversation history inside one thread or session. The second kind, long-term memory, persists across sessions and threads, and in LangChain's framework it is stored as JSON documents under a namespace and a key, much like files in folders (LangChain docs, Memory). You already know how to do this in Python: a dict saved as JSON.

Anthropic calls the pattern structured note-taking, or agentic memory: the agent regularly writes notes that are persisted outside the context window, and pulls them back in later. Their example is Claude playing Pokemon, which keeps tallies and maps across thousands of steps, and after a context reset reads its own notes and carries on (Effective context engineering). This workspace works the same way: NOTES.md is how your tutor remembers you between sessions.

For the makerspace, a note is a small record per student:

{
  "student_id": "s1042",
  "trained_on": ["laser_cutter"],
  "training_date": "2026-11-09",
  "pending": ["3d_printer safety quiz"]
}

Notice the design choices. The note is short and structured, so loading it costs a few dozen tokens, not a whole transcript. It holds facts the assistant will need again, not everything that was said. And it is read at the start of a session (or on demand through a tool such as get_student_record) and written when something changes, such as after a training is logged.

A common mix-up

"The assistant will just remember the student." Chat products sometimes feel that way because they save and reload things behind the scenes. In your assistant nobody does that unless you build it. Remembering is a feature you design: what to write, when to write it, and when to load it.

Check yourself

Which fact is worth saving as a note for the next session?

Show the answer

The training status. It is short, it will matter again, and it exists nowhere else. The quoted paragraph can be looked up again from the manual.

Retrieval: finding the right page 5 min

Notes solve "remember the student". The manuals are a different problem: they are too long to put in the window, and most of any manual is irrelevant to one question. Suppose the laser cutter manual is 120 pages at about 300 tokens a page, 36,000 tokens. Pasting it into every call would add 36,000 tokens to each of the calls in a run, which is wasteful and invites context rot.

Retrieval means searching a store outside the window and loading only the few passages that match the question. The usual setup splits each manual into chunks (a page or a section), builds an index so they can be searched, and exposes a tool such as search_manuals(query) that returns the best two or three chunks. That tool is just another tool in your agent loop, and its result goes into the context like any tool result.

There are two timings. Anthropic contrasts them: up-front retrieval loads relevant data into the context before the model starts, and just-in-time retrieval keeps lightweight identifiers (file paths, stored queries, links) and lets the agent load data through tools when it needs it. The trade-off: just-in-time is more flexible, but slower, and the article suggests a hybrid is often best (Effective context engineering). For the makerspace, a hybrid might be: load the student's small record up front, and let the model call search_manuals only when a question needs the manual.

Context windowSaved notesSearchable store
HoldsThis run's working materialSmall facts to carry forwardLarge reference material
SizeSmall, costlySmallLarge, cheap to keep
LastsOne runAcross sessionsUntil the manuals change
Model sees itAlwaysWhen loadedOnly the retrieved chunks
How the search itself works (keyword search, or comparing embeddings) is a later lesson. For now, treat it as a tool that returns the best-matching chunks, and remember it can return the wrong ones.
A common mix-up

"Retrieval makes the answer correct." Retrieval only decides what the model gets to read. If the search returns the wrong page, the model may answer confidently from it. The quality of your chunks and descriptions decides a lot, so you test retrieval separately by asking whether the right page came back.

Check yourself

A run makes four model calls. At call 2 the model requests a search, and the search returns three chunks of 500 tokens. The chunks are first sent to the model on call 3. How many tokens do the chunks add to the run's total input?

Show the answer

3,000 tokens: the chunks are in the input of calls 3 and 4, 1,500 tokens each time. Count one copy for every call after the result arrives.

Worked example and practice 8 min

Worked example: sorting what the assistant knows

For each item, ask three questions in order: Is it needed on every call? Does it need to survive past the session? Is it big?

  1. "You are the makerspace assistant. Rules..." Needed on every call: it goes in the system prompt, in the context. Keep it short, because you pay for it every call.
  2. Student s1042's training status. Must survive between sessions and is tiny: saved note. Load it at the start, or through a tool.
  3. The 3D printer manual. Big, and only a few pages matter per question: searchable store, retrieved on demand.
  4. Tomorrow's laser cutter bookings. Changes constantly and has its own source of truth: a tool call each time, never a stored copy that could go stale. It enters the context as a tool result, and can be cleared once used.
Your turn

Sort these four items into context only, saved note, or searchable store, and say how each one is loaded. The first is done: "The student's preferred name" is a saved note, loaded at the start of the session because it is small and will matter next visit.

  1. The student's question in this chat, "Can I use the CNC router tonight?"
  2. The 80-page CNC router manual.
  3. A summary at the end of a long chat of what was decided and what is still open.
  4. The list of which students are cleared to use the CNC router.
Show a solution
  1. Context only. It is this run's working material and is useless next session.
  2. Searchable store. Too big for every call. Chunk it and let search_manuals load a few pages when a question needs it.
  3. Saved note, if the work continues next session; otherwise a compaction summary within the session. Either way it is a summary that replaces a long history. Where it goes depends on whether it must outlive the session.
  4. Not a copy at all: a tool call to the records, or a note per student. The decisive question is who owns the truth. If the records change, a stale copy could let an untrained student onto a machine, so read it through a tool at the moment you need it.

Notice item 4. Memory has a risk that the context window does not: a note can go out of date. Decide, for each saved fact, who updates it and what happens when it is wrong.

Summary 3 min

  • The context is everything sent on one call: system prompt, tool definitions, messages and tool results. The window limits it, and every token costs money.
  • The model keeps nothing between calls. The program re-sends the history each step, so context and cost grow through a run.
  • A full or cluttered window hurts cost and quality (context rot). Clear old tool results, trim, or compact.
  • Between sessions, memory is what you save outside the window: short structured notes, loaded when needed.
  • Big reference material goes in a searchable store, and retrieval loads only the few matching chunks.

Say it in your own words: without looking, explain to a teammate why the assistant will not remember a student from last week unless you build that, and name two things you would save and one you would retrieve.
