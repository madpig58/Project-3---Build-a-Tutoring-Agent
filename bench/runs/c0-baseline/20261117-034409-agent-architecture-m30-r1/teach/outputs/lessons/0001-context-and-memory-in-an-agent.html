Context and memory in an agent

By the end of this lesson you can say what your makerspace assistant's model sees at each step, what the program keeps between steps and between sessions, and choose retrieval or notes for each thing the assistant needs to remember.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Both come down to one question you will have to defend at your design review: what goes in the model's context, and what lives somewhere else?

Check your answer

The model outputs a request: the tool's name and its arguments, as text. The program around the model runs the tool, then gives the result back to the model on the next call. Today's question is what the model sees on that next call, and what happens to everything else.

The context window: all the model sees 5 min

Start with a concrete case. A student types: "Is the laser cutter free Friday?" The program sends the model some text, and the model writes back a request to call check_calendar. What exactly was in the text that was sent?

Anthropic defines context as the set of tokens included when sampling from a language model (Anthropic, Effective context engineering for AI agents). A token is a small chunk of text, often a word or part of a word. The context window is the limit on how many tokens the model can take in at once for one call.

For the makerspace assistant, the context on that first call holds four things:

  • the system prompt: your instructions about the assistant's role and rules;
  • the tool descriptions: the names and descriptions of check_calendar, search_manuals and the rest;
  • the conversation so far: here, just the student's question;
  • any tool results that have come back: none yet.

That is the whole input. The model has nothing else to go on: no memory of yesterday, no view of your files, no access to the booking system. If a fact is not in the context, or baked into the model's training, the model cannot use it.

A common mix-up

"The model remembers the conversation." It feels true, because a chat app shows you a continuous thread. But each model call is separate, and the model keeps nothing from the previous one. The program resends the conversation each time. The memory you experience is the program pasting earlier messages into the new context. That is also why context is a design choice: you decide what gets pasted.

Between steps: the context grows 5 min

Now follow one request through the loop and watch the context. Each step, the program appends what just happened and calls the model again with the longer text. What the program keeps between steps is exactly this growing list, sometimes called the message history.

Worked example: the context after each step

Student: "Is the laser cutter free Friday at 3 pm, and what does the manual say about acrylic?" The sizes are invented for illustration, to show the shape of the growth.

  1. Call 1. Context: system prompt (500 tokens) + tool descriptions (800) + question (30) = 1,330. The model requests check_calendar.
  2. Call 2. The program ran the tool. Context now adds the model's request (40) and the calendar result (200) = 1,570. The model requests search_manuals.
  3. Call 3. Adds that request (40) and three manual passages (1,500) = 3,110. The model writes the final answer.

Total tokens the model read across the three calls: 1,330 + 1,570 + 3,110 = 6,010, even though the longest context is only 3,110. The system prompt and tool descriptions were read three times.

This is why context affects cost. Model usage is typically billed by tokens, and every call re-reads the whole context. Long histories make every later step more expensive. Your small budget is a reason to keep the context lean, not only a reason to worry about the window limit. (Check your provider's pricing page for exact rates; they differ and change.)

Too much context: cost and clutter 4 min

A bigger window does not mean "put everything in." Anthropic's engineers describe context rot: as the number of tokens grows, the model's ability to recall information from the context drops, gradually rather than at a sharp cliff. They treat context as a limited "attention budget", and aim for the smallest set of high-signal tokens that makes the right outcome likely (Anthropic).

So an agent that runs for many steps needs a way to shed context. Two ways from the same source:

  • Clearing old tool results. After the model has used 1,500 tokens of manual passages to answer, the passages can be dropped from later calls. This is the lightest option.
  • Compaction. When the conversation nears the limit, the model summarizes it and a new context starts with that summary. The source's coding example keeps architectural decisions and unresolved bugs, and drops redundant tool output.

Both lose something. A summary can drop a detail that turns out to matter. Anthropic suggests tuning for keeping everything important first, then trimming what is superfluous.

For a makerspace chat, most requests finish in a few steps, so clutter matters less than for a long coding task. The pressure on your assistant is more likely to be the manual passages: three pages of retrieved text cost far more than the question.
Check yourself

The assistant has answered the acrylic question and the student now asks about booking. The 1,500 tokens of manual passages are still in context. Which is the best action?

Show the answer

Clear them. Room in the window does not make text free: it costs on every call and competes for attention.

Between sessions: notes as memory 6 min

Everything so far lives inside one request or conversation. Now the harder case: a student trained on the laser cutter last Tuesday and comes back this Monday. When the new session starts, the context is empty. The assistant has no idea who they are.

The fix is external memory: information saved outside the context window, in a file or database, and loaded back when needed. Anthropic calls one pattern structured note-taking: the agent writes notes to storage outside the context window and reads them back later. Their examples include a to-do list and a NOTES.md file (Anthropic).

The model still has no memory of its own. The program does the remembering, in three steps:

  1. Save. When something worth keeping happens, a tool such as save_note writes it to storage. Or your own code writes it, with no model involved.
  2. Store. The note sits in a file or database between sessions.
  3. Load. At the next session, the program reads the student's record and puts the relevant part into the context.
A common mix-up

"A bigger context window gives the assistant memory." A larger window holds more text in one session, but when the session ends, the window is empty again. Remembering between visits needs storage outside the window. Also, a record that should be exact, like "trained on the laser cutter, signed off Oct 14", belongs in a database your code reads, not in text the model must recall.

What to save

Save little, and save what is stable and useful later: training status, preferences the student stated, and unresolved requests. Do not save whole transcripts: reloading them recreates the clutter problem. Anthropic notes that note-taking suits iterative work with clear milestones, while compaction suits long back-and-forth conversation (Anthropic). A makerspace visit is short, so notes about the student are the right fit.

Check yourself

The first option. The program, not the model, carries state between sessions: it loads the saved record into the context.

Retrieval: finding the right page 6 min

The second memory problem is size. The laser cutter manual may be 80 pages. You cannot put all the manuals in context: it would cost a lot on every call and hurt recall. Instead you keep the manuals outside and bring in only the relevant pages. This is retrieval: finding the few pieces of stored text relevant to the current question and adding them to the context.

A common version splits each manual into passages (chunks) and uses embeddings to find the ones closest in meaning to the question. Anthropic describes this as retrieval done up front, before the model runs. The other approach is just-in-time retrieval: the agent holds light references, such as file names or saved queries, and loads data through tools while working (Anthropic). For the building-block view, see the "augmented LLM" idea in Building effective agents, where a model is given retrieval, tools and memory.

Up-front retrievalJust-in-time retrieval
HowSearch runs before the model call; results are put in contextThe model calls a search tool when it decides it needs a page
StrengthFast; one model callFetches only what is needed; can search again
WeaknessMight fetch the wrong pages and can't retrySlower; extra calls cost tokens
FitsEvery question needs manualsMany questions need no manual (a booking)

The source notes that runtime exploration is slower than precomputed retrieval and needs good heuristics, and that a hybrid is common: some data loaded up front, the rest fetched on demand (Anthropic).

A common mix-up

"Retrieval makes the answer correct." It only makes the right page available. If search returns the wrong chunk, the model may answer confidently from it, or ignore it. So test retrieval on its own: for ten real student questions, did the right page come back? Fix that before you adjust prompts.

Worked example and practice 5 min

Worked example: where does each thing live?

For each item the assistant needs, decide: in the context every call, retrieved when needed, or saved between sessions.

  1. Role and rules ("be brief, never book without confirming"). Needed on every call, and short: in the system prompt.
  2. The 80-page laser cutter manual. Too big, and needed only sometimes: retrieved a few pages at a time.
  3. "This student is trained on the laser cutter." Must survive between visits and be exact: saved in a database, loaded at session start.
  4. The calendar result for Friday. Needed for this request only: in context during the request, then cleared or dropped.
Your turn

Place these three using the same method. The first is done: "the student's earlier message in this chat" goes in context, because the program resends the conversation. Now decide: (a) the 3D printer's filament-change steps, a 6-page document; (b) "this student prefers email reminders"; (c) a policy that every booking needs a safety check, which applies to every request.

Show a solution

(a) Retrieved when a question needs it, or in context if the assistant mostly answers about that printer; either is defensible, but at 6 pages retrieval keeps the cost of unrelated requests down. (b) Saved between sessions and loaded at the start, as a short note. (c) The system prompt: short, applies to every call. If it were a hard rule, enforce it in code too, so it does not depend on the model remembering.

Summary 2 min

  • The model sees only its context window: system prompt, tool descriptions, conversation and tool results. Each call is separate; the program resends the history.
  • Between steps the context grows, and every call re-reads it, so long contexts cost more and can reduce recall. Clear or summarize what is no longer needed.
  • Between sessions only saved data survives: notes or records the program writes outside the window and loads back.
  • Retrieval brings the few relevant pages of a big document into context, either up front or just in time through a tool.
