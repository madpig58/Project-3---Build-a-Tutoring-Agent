Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a library the assistant searches, and give the reason.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one skill: choosing what the model sees at each step. This is the decision you will defend at your design review.

What the model sees: the context window 4 min

Start with a concrete case. A student types, "How do I change the blade on the bandsaw?" Your program calls the model. What exactly does it send?

Not just the question. It sends a bundle of text:

  1. the system prompt, your standing instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  2. the tool definitions, the name, description and parameters of each tool (you met these last time);
  3. the messages so far: the student's question, and later the model's earlier requests and the tool results.

All of that, plus the reply the model writes, is the context: "the set of tokens included when sampling" from the model (Anthropic, Effective context engineering). The context window is the limit on how much of it fits. A token is the chunk of text, roughly a short word or word piece, that the model reads and writes; sizes, limits and prices are all counted in tokens.

Anthropic's documentation describes the context window as the model's "working memory" and says everything in the request counts toward it: the system prompt, every message including tool results, and your tool definitions (Claude docs, Context windows).

The last point is the one to keep: the model sees only what is in the box. It cannot look at the manuals on your disk, the booking system or last week's chat unless the program puts text from them into the box. This is why the context is the single most important thing you design.

What is kept between steps 5 min

Now the surprise. A model call has no memory of its own. Each call starts fresh, and the only thing that links step 2 to step 1 is that your program sends step 1 again.

Anthropic's documentation says it plainly: each turn's input "contains all previous conversation history plus the current user message," and the model's output "becomes part of the input for the next turn" (Claude docs). In your agent loop, tool requests and tool results are part of that history too.

Here is the laser-cutter request again, with made-up round numbers so you can count. Say the system prompt and tool definitions take 2,000 tokens, the question 50, each tool request 100, and each tool result 1,500.

The conversation itself holds only 6,850 tokens of content, yet the model read 17,800 tokens of input, because the early steps are re-sent every time. That is the link to your budget: cost grows with how much context you carry and for how many steps. Every tool result you add is paid for again on every later call.

Prompt caching can make repeated, unchanged text cheaper to re-send, but the docs are explicit that it "changes what you pay for those tokens, not whether they count" toward the window (Claude docs). Treat it as a later optimisation, not a reason to ignore context size.
A common mix-up (M8)

"The model remembers what happened earlier in the task." It feels true because the assistant sounds continuous. But nothing is stored inside the model between calls. What looks like memory is your program re-sending the history. If the program drops a tool result from the next call, the model has no idea it ever happened.

Why more context is not better 4 min

Models now have very large windows, up to a million tokens on many current ones (Claude docs). So why not paste every manual into every call and stop worrying?

Two reasons.

Cost. You saw above that every token is re-read on every call. A 72,000-token manual set carried through a four-call request is 288,000 tokens of input for that material alone.

Quality. The docs say that "more context isn't automatically better": as the token count grows, "accuracy and recall degrade," a phenomenon called context rot. Anthropic's engineering team explains that context is "a finite resource with diminishing marginal returns," and recommends finding "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome" (Effective context engineering).

So the design question is never "what can fit?" It is "what does the model need right now to take the next step?" The job of choosing that, every call, is called context engineering.

A common mix-up (M7)

"A bigger window means I can stop curating." Tempting, because a bigger window removes the hard error when you run out of room. But the window is the ceiling, not the target. A large, cluttered context costs more and can make the model worse at finding the one sentence it needs. Earlier in this lesson you saw that carrying 72,000 tokens through four calls costs 288,000; the model would also have to find one temperature in all of it.

Tools are context too

Tool definitions and tool results sit in the box, so they cost tokens on every call. Two rules follow, both from Anthropic's guidance: keep tool results small and useful, and keep the tool set clear, because "if a human can't tell which tool to use, neither can the agent" (Effective context engineering). A check_calendar that returns a whole month of bookings when the student asked about Friday wastes budget on every later call. Return Friday.

What is kept between sessions 4 min

A session here means one conversation: a student opens the assistant, asks things, and leaves. When the session ends, the context is gone. The next session starts with an empty box.

That is a problem for your assistant. On Monday Sam completes bandsaw training and the assistant says so. On Thursday Sam asks to book the bandsaw. Unless something is saved, the assistant has no idea Sam is trained.

A common mix-up (M3)

"The assistant automatically remembers earlier conversations." It does not, and this is the same mix-up that appeared in quiz 0001. The model's weights do not change as you talk to it, and a new session starts with a new context. Memory across sessions exists only if you build it: something is written down at the end of one session and put back into the context at the start of the next.

So memory in an agent is an ordinary engineering pattern with two halves:

  • Write: save a fact somewhere outside the context, such as a file, a database row or a note.
  • Read: at the right moment, load it back into the context.

Anthropic's engineering team calls the model-driven version structured note-taking, also called agentic memory: "the agent regularly writes notes persisted to memory outside of the context window," and these are pulled back in later. Their examples include a to-do list and a NOTES.md file, and a Pokémon-playing agent that kept notes across more than 1,200 steps and resumed from them after its context was reset (Effective context engineering). Anthropic's API also offers a file-based memory tool for this pattern; its docs describe a design for agents that span multiple sessions (Claude docs).

For a makerspace, a training status like "Sam: bandsaw trained, 12 Oct" is better in an ordinary database or file than in a free-text note, because it must be exact and your code can look it up by name. That is still memory in this lesson's sense: saved outside the context, loaded back when needed. Choose the storage that fits the fact, and then have the program, or a tool such as check_training_record, load only the facts the current question needs.

Retrieval: finding the right page 5 min

Your second problem: a manual set too large to fit in the context, or too costly to carry. The answer is retrieval: search the library and put only the few relevant passages into the context.

Anthropic's guide on building agents treats retrieval, tools and memory as the augmentations that turn a bare model into the basic unit of an agent, and notes that current models can "generat[e] their own search queries" and decide "what information to retain" (Building effective agents).

Two ways to retrieve

Anthropic describes two patterns (Effective context engineering):

  • Up-front retrieval: before the model is called, the program searches (often with an embedding-based search that matches meaning, not just words) and puts the best passages into the context.
  • Just-in-time retrieval: the agent keeps light references, such as file names, page titles or stored queries, and loads the content itself with a tool when it needs it.

Take the question "How do I change the bandsaw blade?"

Up-frontJust-in-time

Anthropic notes that just-in-time exploration is slower than retrieving up front, and that without good guidance an agent can waste context. A common hybrid loads a small amount up front and lets the agent explore further; Claude Code, for instance, loads a CLAUDE.md file up front and then uses search tools as it works (Effective context engineering).

A common mix-up (M9)

"Retrieval means the model reads the manuals." The model reads only what retrieval hands it. If the search returns the wrong pages, the model will either answer from them or say it does not know. A confident, wrong answer comes from the wrong pages in the context, and a smarter model cannot fix that. Retrieval quality is a design problem you own.

One more design lever comes from the same source: the names and structure of what you retrieve carry information. A page titled "Bandsaw: blade replacement" tells the agent what it holds before it spends tokens reading it, much as a file called test_utils.py in a tests folder signals its purpose (Effective context engineering). Good page titles in your manual index are free context engineering.

When one session is too long 2 min

Even inside one session, a long task fills the window. Anthropic describes three techniques for long tasks (Effective context engineering):

  • Compaction: summarise the conversation when it nears the limit and restart with the summary. A light version, tool result clearing, simply removes old raw tool outputs deep in the history.
  • Notes, as you saw: write progress to a file and reload it.
  • Sub-agents: a helper works in its own clean context and returns only a short summary. You will weigh when this pays off in a later lesson.

A makerspace chat is short, so your assistant will rarely need these. Keep them in mind for a long booking-and-troubleshooting conversation; the cheapest fix is often tool result clearing.

Worked example and practice 8 min

Worked example

A student writes: "I'm Priya. Can I use the vinyl cutter Saturday morning, and how do I load the roll?" Decide, for each piece of information, where it lives, and estimate the input for the one-question request.

  1. List what the answer needs. Three things: Priya's training status, Saturday's calendar for the vinyl cutter, and the roll-loading steps.
  2. Place each one. Training status is per-student and must survive between sessions, so it goes in the saved record and is read with check_training_record("Priya", "vinyl cutter"). Saturday's slots are live data in the calendar, read by check_calendar("vinyl cutter", "Saturday") and not saved. The loading steps sit in the manual library and arrive through search_manuals("vinyl cutter load roll").
  3. Keep results small. Ask the calendar for Saturday only. Return the top two manual pages, not the whole manual. Use the training tool's one-line answer, such as "trained, 3 Mar".
  4. Count the calls. Three tool requests plus the final answer is four model calls. Assume 2,500 fixed tokens, a 60-token question, 100 per request, and results of 150 (training), 300 (calendar) and 1,200 (manual pages). Call 1 reads 2,560. Call 2 adds 100 and 150: 2,810. Call 3 adds 100 and 300: 3,210. Call 4 adds 100 and 1,200: 4,510.
  5. Total input: 13,090 tokens. Order matters: put the large manual search last. If the 1,200-token result came first, it would be re-read on three calls instead of one.

The order saves 1,700 tokens, because the biggest result is re-read on one call instead of three. Note the model chooses the order, so you influence it with tool descriptions and instructions rather than controlling it.

Summary 2 min

  • The context is everything sent on one model call: system prompt, tool definitions, messages and tool results. The model sees only that.
  • Nothing is kept inside the model. Between steps, your program re-sends the history, so cost grows with every step and every large tool result, and a bigger window is a ceiling, not a goal.
  • Between sessions, nothing is kept unless you write it down and read it back. Save what is per-user, needed later and stored nowhere else.
  • Retrieval searches a library and puts only the relevant passages in context, either up front or just-in-time. The model can only be as right as the pages it receives.
