Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a document that is retrieved only when needed.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those are three separate memory problems, and at your design review you will need to say which tool solves which.

Warm-up 2 min

Recall

From memory: in the agent loop, who actually runs a tool, the model or the program around it? And what happens to the tool's result afterwards?

Check your answer

The program runs the tool. The model only writes a structured request naming the tool and its arguments. The program then sends the result back to the model as part of its next input and calls the model again. Today's whole lesson is about that phrase, "part of its next input": that input is the context.

The context window: what the model sees 6 min

Start with an everyday case. You hire a helper for one afternoon and give them a single desk. They can only work with what is lying on the desk right now. Anything in the filing cabinet down the hall does not exist for them until someone brings it over, and when they go home the desk is cleared.

A language model works like that helper. Its desk is the context window: all the text the model can refer to when it writes a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and distinguishes it from the large body of data the model was trained on (Claude docs: Context windows). The unit that fills the desk is the token, a chunk of text a bit shorter than a word on average. The context window is measured in tokens, and so is what you pay for.

What is on the desk? More than the user's message. Everything in a request counts: the system prompt, every message so far, the tool results, any images or documents, your tool definitions, and the model's own output for the turn (Claude docs).

Two facts about the desk matter for your design.

It has a size limit. Current Claude models list windows of up to 1M tokens, depending on the model, and the API returns an error if the input alone is larger (Claude docs). A limit this large sounds like it solves everything. It does not, because of the second fact.

More is not better. As the token count grows, accuracy and recall degrade. Anthropic calls this context rot and treats context as a finite resource with diminishing returns: the goal is the smallest set of high-signal tokens that still gets the job done (Anthropic: Effective context engineering). The same page also notes that tools should return token-efficient information.

Cost follows too. You are billed for the tokens you send, and as the next section shows, an agent sends the same earlier tokens again on every step. Your sponsor's budget is a context budget.
A common mix-up

"The context window is how much the model knows." It is tempting because a bigger number sounds like a smarter model. In fact, what the model learned in training is a separate thing. The window is only the text it can look at right now. A model with a huge window still knows nothing about your makerspace's machines unless the relevant text is put on the desk.

What is kept between steps 6 min

Here is the surprise that links to your agent loop. A model call has no memory of its own. Between calls, the model keeps nothing. What gives the illusion of continuity is that the program sends the whole conversation again each time. In Anthropic's description, each turn's input is all previous history plus the new message, and the model's output becomes part of the input of the next turn (Claude docs).

Follow one student request through your loop. Suppose a student asks, "Can I use the laser cutter Friday afternoon and how thick can the plywood be?" A rough token tally might look like this. The numbers are made up for illustration, but the pattern is real.

StepWhat the model readsTokens sent (example)
1. Choose a toolSystem prompt, tool definitions, the question1,500
2. Read calendar resultAll of step 1, plus its tool request and the calendar result (300)1,900
3. Read manual pageAll of step 2, plus a tool request and a manual page (2,000)4,000
4. Final answerAll of step 3, plus nothing new4,000
Total billed input11,400

The 2,000-token manual page was only fetched once, but you pay for it in step 3 and again in step 4. The conversation grows by every tool result, and each step re-sends everything. So the cost of an agent grows faster than the number of steps. The longer the loop, the more it pays to keep big results out of the context or clear them once used.

That is why the main techniques in this area all do one of two things: shrink what is on the desk, or move information off the desk and bring it back only when needed. Two ways to shrink:

  • Clearing old tool results. Once the agent has used the manual page, remove it from later calls. Anthropic describes this as a light form of compaction (Anthropic) and offers it as "tool result clearing" in its API (Claude docs).
  • Compaction. When a conversation nears the limit, summarize it and start a fresh window from the summary. Anthropic advises first making sure the summary keeps everything important, and only then trimming it (Anthropic).

What is kept between sessions: nothing, by default 4 min

A session is one run of the assistant for one conversation. When it ends, the context window is gone. The next time a student opens the assistant, the model starts with an empty desk plus the system prompt. It does not remember that this student completed the laser cutter training last week.

A common mix-up

"The assistant will remember the student next time, like a person would." It is tempting because chat products sometimes do seem to remember you, but that is a feature the product builders added. The model itself keeps nothing between calls, let alone between sessions. If your assistant should remember a student's training status, you have to save it somewhere and put it back on the desk at the start of the next session.

So there are two kinds of memory in an agent, and they sit in different places.

In contextOutside context

Retrieval and notes: memory you build 7 min

Two simple patterns put information outside the context and bring it back when it is useful.

Retrieval: finding the right page

Retrieval means looking something up in a large store and putting only the relevant piece on the desk. Anthropic describes the approach as "just-in-time" context: instead of loading everything up front, the agent keeps lightweight references, such as file paths, stored queries or links, and uses tools to load the content when it needs it (Anthropic). For the makerspace, the references are the names of the manuals and their sections. A search_manual tool takes a query like "laser focus height" and returns the two or three best-matching passages, not the whole manual. That is the answer to your mission question about finding the right page in a long manual.

In the loop you already know, retrieval is just another tool call. Only the tool's job is special: find a few relevant passages. The model decides when to call it; the program runs it.

Notes: saving what to remember

Structured note-taking means the agent writes notes to storage outside the context and reads them back later. Anthropic gives an example of an agent playing a game over many steps: after its context was reset, it read its own notes and carried on (Anthropic). Anthropic's memory tool applies the idea to files: the model asks to view, create or change files in a memory folder, and your application carries out those operations, so you control where the data lives (Claude docs: Memory tool). It is, again, tool calling.

For the makerspace, a notes file per student could hold training status. At the start of a session the program loads that one small file into the context. Whenever something changes, say a student passes the 3D printer safety check, the agent writes a line. The next session starts with the line in context.

A common mix-up

"With a window this big, I can skip retrieval and just paste all the manuals in." It is tempting because it is the simplest design. But context rot makes recall worse as the window fills, and you pay for every one of those tokens on every call, as Figure 2 showed. Retrieval keeps the desk small, so it is usually both cheaper and more accurate for a large library.

Worked example and practice 4 min

Worked example

Sort these four things for the makerspace assistant: (a) the rules for how the assistant should behave, (b) the full 60-page vinyl cutter manual, (c) the fact that Sam is certified on the vinyl cutter, (d) the booking calendar result for Friday.

  1. Ask: is it needed on every call, in every session? The behavior rules (a) are, so they go in the system prompt. They are small and fixed.
  2. Ask: is it large and mostly irrelevant to any one question? The manual (b) is. It goes in a searchable store, and a search tool returns a few passages when asked.
  3. Ask: is it a small fact that must outlive the session? Sam's certification (c) is. It goes in Sam's notes file, loaded at session start.
  4. Ask: is it only useful right now? The calendar result (d) is. It enters the context as a tool result and can be cleared once the booking is made. It is not saved.
Your turn

Sort these three the same way: (e) a student's preference for being addressed as "Sam", mentioned in one visit and wanted at every visit; (f) the 20 pages of safety rules for the metal lathe; (g) the student's question typed a moment ago. Start by asking the first question: is it needed on every call, in every session?

Show a solution

(e) is a small fact that must outlive the session, so it goes in the student's notes file. (f) is large and relevant only to some questions, so it goes in the searchable store. (g) is needed only in this session, so it stays in the context and is not saved, although its content may later be summarized into notes if it matters.

Summary 1 min

  • The context window is everything the model can see in one call, and it costs tokens on every call.
  • Between steps, the program re-sends the whole context. Nothing survives between sessions unless you save it.
  • More context is not better: it costs more and recall degrades (context rot).
  • Retrieval brings a few relevant passages from a big store; notes save small facts that must outlive a session.

Say it in your own words: without looking, explain to a teammate why the assistant needs both a manual search tool and a notes file, and what each one keeps off the desk.
