Context and memory: what an agent sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in your makerspace assistant, whether it goes in the context, in saved notes, or in a manual that gets searched.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, and it must remember each student's training status between visits. Both are memory problems, and both cost money: every token the model reads is billed. This lesson gives you the vocabulary and the three-way decision you will defend at your design review.

Warm-up 2 min

Before new material, pull something from memory. It is harder than rereading, and that is why it sticks.

Recall

In the agent loop, a tool has just run. Without looking back: what does the program do with the tool's result, and who actually runs the tool, the model or the program?

Check your answer

The program runs the tool. It then sends the result back to the model as part of the model's next input and calls the model again. That "next input" is exactly what this lesson is about: what does it contain, and how big does it get?

Recall

A student asks, "Is the laser cutter free tomorrow, and do I need training?" The model calls check_calendar, then check_training_record, then answers. How many times is the model called?

Check your answer

Three. Each call ends with one tool request or the final answer: two tool requests plus the answer. Every one of those calls is a separate trip to the model, and each trip carries an input. Keep that picture; we will count what is in those inputs.

The context window 5 min

Start with a game. Imagine an NPC (a non-player character) that can only act on what is on a single sheet of paper in front of it. It has no other knowledge of the game world in the moment it acts. Whatever you want it to use, you must write on the sheet. If the sheet is full, something has to come off.

A language model works like that NPC. The context window is all the text the model can reference when it writes a response, including the response itself. Anthropic's docs call it a "working memory" for the model, and say it is different from the large body of data the model was trained on (Claude docs: context windows).

The window is measured in tokens, the small pieces of text a model reads and writes. A token is roughly a short word or a part of a longer one. You do not need exact counts, only the idea that more text means more tokens, and more tokens means more cost and less room.

What is on the sheet? More than the student's question. The docs list everything that counts toward the window: the system prompt, every message including tool results, images and documents, and your tool definitions. The text the model writes counts too (Claude docs).

Worked example: what is on the sheet?

A student writes: "Is the laser cutter free tomorrow at 3 pm?" The first model call goes out. List what the model sees.

  1. The system prompt: "You are the makerspace assistant. Be concise. Only book machines the student is trained on." Say 600 tokens, because real prompts carry many rules.
  2. The tool definitions: check_calendar, search_manuals, check_training_record and book_machine, each with a description and its parameters. Say 900 tokens in all. The model needs these to know the tools exist (you saw this in quiz 0001).
  3. The student's message: about 30 tokens.
  4. That is about 1,530 tokens before the model has said a word. The model has no hidden extra knowledge about your makerspace: if the opening hours are not on the sheet, it cannot know them.

The numbers are illustrative; your real counts will differ, and the API reports exact usage on every response.

Check yourself

Your team wants the assistant to follow a rule: "never book the 3D printer for more than 4 hours." Where must the rule be for the model to follow it on a given call?

Show the answer

The third option. Rules the model should follow must be in the context of the call, for example in the system prompt. (Code can also enforce a rule, such as rejecting an over-long booking, but that is a different mechanism from the model following it.)

What is kept between steps 6 min

Here is the surprise. The model itself keeps nothing from one call to the next. Each call starts blank: the model reads the whole sheet and writes the next piece. The agent program is what keeps things, by writing the earlier steps back onto the sheet each time.

The docs describe it this way: as the conversation advances, each user message and assistant response accumulates in the context window and previous turns are preserved completely; each turn's input is all the previous history plus the new message (Claude docs). We say the call is stateless: the model holds no state between calls, so everything it should "remember" must be sent again.

In your loop, that means a tool result does not just get used once. It is added to the history and re-read on every later call.

Worked example: counting a four-call run

Same fixed start as before: 1,530 tokens of system prompt, tool definitions and question. The assistant makes three tool calls and then answers. Each tool request the model writes is about 40 tokens. The calendar result is 300 tokens, the manual page 1,200, the training record 100, and the final answer 120.

  1. Call 1 reads 1,530 tokens and writes a 40-token request for check_calendar.
  2. The program runs the tool and adds the 40-token request and the 300-token result. Call 2 reads 1,530 + 40 + 300 = 1,870 and requests search_manuals (40 tokens).
  3. The manual page adds 1,200. Call 3 reads 1,870 + 40 + 1,200 = 3,110 and requests check_training_record (40 tokens).
  4. The record adds 100. Call 4 reads 3,110 + 40 + 100 = 3,250 and writes the 120-token answer.
  5. Total input read: 1,530 + 1,870 + 3,110 + 3,250 = 9,760 tokens. Total written: 40 + 40 + 40 + 120 = 240.
  6. The lesson for your budget: the 1,200-token manual page is paid for in call 3 and again in call 4. Big tool results are expensive twice, and in a longer run, many times.
Prompt caching can lower the price of repeated text, but the docs are clear that cached tokens still count toward the window: caching changes what you pay, not whether they count (Claude docs).
A common mix-up

"The model remembers the earlier steps on its own." It is tempting because a chat feels like a conversation with someone who remembers. But in your agent, step 3 only "knows" step 1 because the program wrote step 1 back into the input. Leave a tool result out of the list you send, and the model has no trace that it ever happened.

Check yourself

Your program has a bug: for call 2 it sends only the system prompt, the tool definitions and the student's question. It leaves out both the model's check_calendar request and the calendar result. What happens in call 2?

Show the answer

The third option. Calls are stateless, so anything not in the input is invisible to the model. Here the run would loop, paying for the same tool call again and again.

When the context gets too full 5 min

The sheet is not infinite, and a bigger sheet is not automatically better. Current Claude models list windows up to 1M tokens, but Anthropic's docs warn that as token count grows, accuracy and recall degrade, a phenomenon known as context rot. So curating what is in context matters as much as how much space is available (Claude docs).

Anthropic's engineering team calls context "a finite resource with diminishing marginal returns" (Effective context engineering for AI agents). For you, this has two consequences at once: a long context costs more, and it can also make answers worse.

What do you do when a run gets long? The same article names a technique called compaction: summarize the conversation when it nears the limit and start a fresh window with the summary. Its lightest form is clearing old tool results that the agent no longer needs.

Worked example: trimming a long booking chat

A student spends 25 turns rebooking three machines. The history now holds three calendar dumps of about 2,000 tokens each, and the student's latest message asks, "So what did we finally book?"

  1. Spot the dead weight. The calendar dumps were needed to choose a slot, but once the booking is made, only the outcome matters.
  2. Clear the old tool results. Replace each 2,000-token dump with a stub such as "calendar checked for laser cutter, Fri" (about 10 tokens). That frees roughly 5,970 tokens.
  3. Keep what the future needs: the three confirmed bookings, with machine, day and time, and the student's preferences. These are small and high value.
  4. If the history is still long, compact: ask the model to write a short summary of the 25 turns, then start the next call with the system prompt, tool definitions and that summary.
  5. Check the risk. A summary can drop a detail that later matters, such as "student is only allowed 2 hours". Rules that must never be lost belong in the system prompt, not the summary.
A common mix-up

"A bigger window means I can stop worrying about what goes in." It is tempting because the limit sounds like the only problem. But recall degrades as context grows, and you pay for every token on every call. A 1M-token window is a ceiling, not a target.

Check yourself

Your assistant is slow and costly, and every call carries ten old manual pages that no longer matter to the student's current question. What is the best fix?

Show the answer

The second option. The tokens are the cost, so remove them. Ignoring them in the prompt leaves them on the sheet, still billed and still competing for attention.

What is kept between sessions: notes 6 min

Everything so far lives and dies with one run. When the student closes the chat and returns next week, the new run starts with a blank sheet: the system prompt, the tools, and the new message. The assistant does not know the student passed laser cutter training. This is the point where a new idea is needed: memory in an agent means information saved outside the context window, which the agent can load back in when it needs it.

The most direct form is notes. Anthropic's engineering article calls it structured note-taking: the agent regularly writes notes to storage outside the context window and reads them back later. Its example is an agent playing Pokémon, which kept notes such as how many steps it had spent training on Route 1, and after a context reset it read its notes and carried on (Effective context engineering).

For you, "notes" can be very plain: a record per student in a file or table, such as {"student": "s1042", "trained": ["laser_cutter"]}. The agent reads it with a tool and updates it with another. Anthropic also offers a memory tool for this pattern (memory tool docs), but the idea works in plain Python.

Worked example: remembering a student's training

On Monday a student, s1042, finishes laser cutter training with a staff member. On the following Tuesday they ask the assistant to book the laser cutter.

  1. Monday: a staff-facing tool or the assistant calls record_training("s1042", "laser_cutter"). The program writes the entry to a file. The context of that run is then discarded.
  2. Tuesday: a new run begins with a blank sheet. The student identifies themselves, and the model sees only the system prompt, the tools and their message.
  3. The model requests check_training_record("s1042"). The program reads the stored note and returns {"trained": ["laser_cutter"]}.
  4. That result lands in the context, so the model can now go ahead and book.
  5. Notice the shape: save outside, load on demand. Putting every student's record in the system prompt would be wasteful and would not scale, so only the one record is loaded.
A common mix-up

"The assistant automatically remembers past conversations." A chat product may do that for you, but in your own agent nothing is saved unless you write it. Next week's blank sheet is blank by design. You choose what to save, in what shape, and when to load it.

Check yourself

Which of these is best saved as a note between sessions, rather than left in a single run's context?

Show the answer

The third option. Good notes are small, stable and costly to rediscover. Training status passes all three. The calendar changes by the hour and has its own tool.

Retrieval: finding the right page 6 min

Notes cover short facts about a student. Machine manuals are a different problem: they are long, they rarely change and the student needs one page out of hundreds. Anthropic's contextual retrieval article says that if your knowledge base is smaller than about 200,000 tokens (roughly 500 pages), you can simply put all of it in the prompt (Contextual Retrieval). Check this against your manuals first: it is the simplest design.

If the manuals are bigger, or cost matters, you use retrieval: before or during a call, search the manuals and put only the few best-matching pieces in the context. Each piece is a chunk, a section of a document, usually no more than a few hundred tokens.

How does the search find the right chunk? There are two plain kinds. A search by meaning finds chunks that talk about the same thing as the question, even in different words. A search by exact words finds chunks that contain the very same string.

Here is why you want both. A student asks about error code "TS-999". A meaning search may return general pages about error codes, because the code itself carries little meaning. An exact-word search finds the one page with that string. Anthropic recommends combining the two (Contextual Retrieval).

Retrieval can also be a tool the agent calls for itself, instead of something done before the model runs. In your assistant, search_manuals is exactly that: the model requests a search, and the matching chunks land on the sheet.

Worked example: "What speed do I use for 3 mm acrylic?"

The laser cutter manual is 300 pages. A student asks about cutting 3 mm acrylic.

  1. Before launch (done once): split the manual into chunks of a few hundred tokens and index them, so that each can be searched by meaning and by exact words.
  2. The model decides this needs the manual and requests search_manuals("laser cutter", "3 mm acrylic speed").
  3. The program searches the index and returns the top three chunks: the material settings table, a safety note on acrylic fumes and the focus-height section. About 900 tokens.
  4. Those chunks join the context. The model reads them and answers, citing the settings table.
  5. The cost comparison: pasting all 300 pages would be about 120,000 tokens on every call, using Anthropic's rule of thumb that 200,000 tokens is about 500 pages. Retrieval reads about 900. That is a gap of more than 100 times, and it is why retrieval pays off for a big manual even though a small one could simply be pasted. The risk is that the search returns the wrong chunks, and then the model answers from the wrong page, so retrieval quality is the thing you measure.
A common mix-up

"Retrieval means the model reads the whole manual and picks the page." It is tempting because the answer seems to come from the manual. But the model only ever reads the chunks the search returned. If the right page is not among them, the model never sees it, and it may answer from a nearby page, or from guesswork, without knowing anything is missing.

Check yourself

A student asks about error code "E-417" on the vinyl cutter. The search by meaning returns pages about cutter errors in general, but not the E-417 page. Which change is most likely to help?

Show the answer

The third option. Codes and part numbers are exact strings, and exact-word matching is built for them. Combining it with the meaning search covers both kinds of question.

Worked example and practice 7 min

Now put the three places together. Your decision rule: context for what this run needs now, notes for small facts that must survive between sessions, retrieval for large material that rarely changes.

Worked example: sorting four items

For each item in the assistant, choose a place and give the reason.

  1. "Never book more than 4 hours." This is needed on every call and is short, so it goes in the context, in the system prompt. Anything the model must obey on every call cannot be left to a search that might miss it.
  2. The band saw's blade-change procedure, page 212 of a 400-page manual. Large, stable, needed rarely, so retrieval. Loading it each call would pay for 400 pages to use 1.
  3. "Student s1042 completed laser training on 3 March." Small, personal, must survive between sessions, so notes. It is loaded by a tool when this student shows up.
  4. The laser cutter's booking calendar for Friday. It changes by the hour, so a saved note would go stale. It stays behind its own tool, and the result goes in the context for that run only, then gets cleared when it is no longer needed.
Your turn

Sort these three items the same way. The first is done for you: "Be concise and friendly" goes in the context (system prompt), because it applies to every call and is short. Now do: (a) the list of which students are banned from the 3D printers for misuse; (b) the 120-page 3D printer manual; (c) the answer to the question the student asked a minute ago in this same chat. For each, name the place and the reason.

Show a solution

(a) Notes. It is a small fact about specific people that must survive between sessions and be read by a tool whenever someone asks to book, so the program (not only the model's goodwill) can check it. (b) Retrieval, or the whole manual in the prompt if everything you own fits in about 200,000 tokens and the cost is acceptable. Check the size and the budget first. (c) Context. It is already in the conversation history for this run; saving it as a note would waste space, because it will not matter next week.

Worked example: a second cost count

Redo the four-call run from the section on steps, but with a larger manual result.

  1. Suppose the retrieved manual page is 2,500 tokens instead of 1,200. Everything else stays the same.
  2. Call 1 and call 2 are unchanged: 1,530 and 1,870.
  3. Call 3 reads 1,870 + 40 + 2,500 = 4,410.
  4. Call 4 reads 4,410 + 40 + 100 = 4,550.
  5. Total: 1,530 + 1,870 + 4,410 + 4,550 = 12,360 input tokens, up from 9,760. A 1,300-token larger result added 2,600, since it was read twice.
Your turn, faded

Now the retrieved page is 800 tokens, and a fifth call is added: after the training record, the model requests book_machine (40 tokens), the result is 60 tokens, and the model writes a 120-token final answer. Keep the other numbers. Step one is done: call 1 reads 1,530. Work out what calls 2 to 5 read, and the total.

Show a solution

Call 2 reads 1,530 + 40 + 300 = 1,870. Call 3 reads 1,870 + 40 + 800 = 2,710. Call 4 reads 2,710 + 40 + 100 = 2,850 and requests book_machine. Call 5 reads 2,850 + 40 + 60 = 2,950 and writes the answer. Total: 1,530 + 1,870 + 2,710 + 2,850 + 2,950 = 11,910 input tokens. Each added step re-reads everything before it, so a longer chain of steps costs more than a longer single result.

Summary 2 min

  • The context window is all the text the model can use on a call: system prompt, tool definitions, history, tool results and its own reply.
  • Each call is stateless. The program keeps the steps by sending the growing history back each time, so big tool results are paid for again on every later call.
  • A fuller window is not a better one: recall degrades as it grows. Clear old tool results and compact when runs get long.
  • Between sessions the window is gone. Anything to remember must be saved outside it as notes and loaded by a tool.
  • Long manuals are handled by retrieval: search outside, bring only the best chunks in. Check first whether everything simply fits.

Say it in your own words: without looking up, explain to a teammate why the assistant forgets a student's training status next week, and name the two places you could put it so that it does not.

Go further

Read next: Effective context engineering for AI agents (Anthropic Engineering), the best single source here. It covers context rot, compaction, notes and just-in-time retrieval in one article, from the team that builds agents.

  • Claude docs: context windows: what counts toward the window, and how turns accumulate.
  • Contextual Retrieval: how chunks are searched by meaning (embeddings) and by exact words (BM25). In Anthropic's tests, adding context to each chunk and combining both searches cut the share of relevant chunks missed in the top 20 from 5.7% to 2.9%, and a reranking step brought it to 1.9%. That is one company's benchmark, not a promise for your manuals.
  • In the same engineering article, "just-in-time retrieval" is the name for an agent that keeps lightweight identifiers such as file paths or stored queries and loads data through tools when it needs it.
  • Memory tool docs: a ready-made way to save and load notes across sessions.
