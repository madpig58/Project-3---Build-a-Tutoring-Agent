Context and memory in an agent

By the end of this lesson you can say what is in your makerspace assistant's context at each step, what survives between steps and between sessions, and where retrieval and notes fit.

Objective O3: context and memory in an agent About 10 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Both come down to what you put in context and what you store outside it.

Warm-up 1 min

Recall

From the agent loop: when the model asks for a tool, who runs it, and what happens to the result?

Check your answer

The program around the model runs the tool, then sends the result back to the model as input for its next call. That "sent back" part is exactly what fills the context, which is today's topic.

The context window 2 min

Start with a game: an NPC that talks to you. The game engine does not "remember" the chat by itself. Each time the NPC speaks, the engine builds a text blob of its personality, the dialogue so far and your new line, and hands the whole blob to the model.

Agents work the same way. The context window is all the text the model can see when it writes a response, including the response itself; it works like the model's working memory, not like what it learned in training (Claude docs: context windows). It holds the system prompt, every message so far, tool results and tool definitions.

A token is the small chunk of text (a word or part of one) that models count. The window is measured in tokens, and you pay per token.

Worked example: one makerspace question, three model calls

Student: "Does the laser cutter need training, and is it free Friday?" The numbers are invented and rounded.

  1. Call 1 input: system prompt plus tool definitions (about 1,500 tokens) and the question (50). Total about 1,550. The model asks for search_manuals.
  2. The program runs the search and appends a 1,200-token manual page.
  3. Call 2 input: everything from call 1, plus the request, plus the page. About 2,800. The model asks for check_calendar.
  4. The calendar result adds about 150 tokens. Call 3 input is about 3,000, and the model writes the answer.
  5. Billed input: 1,550 + 2,800 + 3,000 = 7,350 tokens, though the question was only 50. Each call re-sends everything.
A common mix-up

"A bigger window means I can stuff in everything." It is tempting because windows now reach about a million tokens. But recall gets worse as the context fills, an effect called context rot, so Anthropic advises the smallest set of high-signal tokens (Anthropic engineering). Stuffing also multiplies cost, as the 7,350 above showed.

Check yourself

In the example, the manual page is 1,200 tokens. Roughly how many times is it paid for as input?

Show the answer

Twice: the page enters after call 1, so it is part of the input of calls 2 and 3.

Between steps and between sessions 2 min

Between steps of one run, your program keeps the message list and sends it again. The model keeps nothing itself. Between sessions (a new conversation tomorrow), the list is gone unless you saved something. The API does not carry it over for you.

Worked example: Priya's training status
  1. Monday: Priya finishes laser training. The assistant tells her so, and the run ends. The context is discarded.
  2. Wednesday: she asks to book the laser. A fresh run starts with an empty message list.
  3. Without storage, the model cannot know about Monday. It might ask again, or wrongly refuse.
  4. With storage, your program writes "Priya: laser trained, Monday" to a store, and a tool reads it on Wednesday.
A common mix-up

"The assistant automatically remembers earlier conversations." It feels true because chat apps often do, but that is extra machinery someone built. In your own agent, memory exists only if you build it.

Retrieval 2 min

Retrieval means fetching only the relevant piece of a large body of text into context when it is needed. Instead of loading all machine manuals up front, an agent can keep light pointers (file paths, stored queries) and load content with tools at the moment it needs it. Anthropic calls this just-in-time retrieval. Its cost is speed, since each lookup is an extra step (Anthropic engineering).

Worked example: the 3D printer manual

Question: "What nozzle temperature for PETG?" The manual is 80,000 tokens.

  1. Loading the whole manual would cost 80,000 input tokens on every call, and the answer would sit in a sea of unrelated text.
  2. Instead, the model calls search_manuals("PETG nozzle temperature", machine="3d_printer").
  3. The program returns the best-matching page, about 900 tokens.
  4. The model answers from that page. Context grew by 900, not 80,000.
  5. If the search returns the wrong page, the model can search again; that is why retrieval is a tool in the loop.
Check yourself

Your assistant retrieves the wrong page for a question. Which fix targets the cause?

Show the answer

Improve how the search finds pages. The failure is in the search, not in the window.

Notes as memory 1.5 min

The second kind of memory is notes: the agent writes facts to storage outside the window and reads them back later. Anthropic's memory tool lets Claude create, read, update and delete files that persist between sessions, but it is client-side: Claude only requests an operation, and your application runs it against storage you control (Claude docs: memory tool). Same loop as any tool.

Notes also help inside a long run. In Anthropic's Claude-plays-Pokémon example, the agent kept notes over thousands of steps and, after its context was reset, read them to carry on (Anthropic engineering).

Worked example: a note for Priya
  1. Priya finishes training. The model requests a create on /memories/priya.txt with "laser: trained Mon".
  2. Your program checks the path stays inside /memories (required for safety), writes the file and returns "File created".
  3. Wednesday: the model first requests a view of /memories, sees priya.txt, opens it and books the laser.
  4. Cost: a few hundred tokens of notes, instead of replaying Monday's whole conversation.
Keep notes short and curated. A notes file that only grows eventually fills the context itself.

Your turn 1 min

Sort it

For each item, say: keep in context, retrieve on demand, or save in notes. First step done for you: "The 60-page bandsaw manual" is retrieve on demand, because it is large and only one page matters per question. Now sort: (a) the student's current question; (b) "Priya is trained on the laser"; (c) the full text of every machine manual.

Show a solution

(a) keep in context: it is small and needed now. (b) save in notes: it must survive to the next session. (c) retrieve on demand: it is far too big to load every call.

Summary 0.5 min

  • Context is everything the model sees in one call, and each step re-sends it all, so it costs tokens every time.
  • More context is not better: recall degrades as it fills.
  • Nothing survives a session unless your program stores it outside the window.
  • Retrieval pulls the relevant page in when needed; notes carry facts forward.

Say it in your own words: where does Priya's training status live on Wednesday, and how does the model get it?
