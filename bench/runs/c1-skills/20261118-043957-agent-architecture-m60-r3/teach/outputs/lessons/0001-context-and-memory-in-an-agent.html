Today you will find out what that growing context holds, why it matters for your budget, and what you can do about it.

The context window: what the model sees 10 min

Start with a game. Imagine a game engine that renders a scene, but it can only draw what is inside the camera's view. Anything outside the frame does not exist for that frame. A language model works like that camera.

The context window is all the text the model can look at when it writes its next piece of output, including the output it has written so far. Anthropic's docs call it a "working memory" for the model, and say it is different from the training data the model learned from (Claude docs: Context windows).

It is measured in tokens: the small chunks of text the model reads and writes. A token is often a short word or part of a word. You do not need exact counts yet; you need the idea that every piece of text costs some tokens, and the window has a maximum.

What is in the window

The docs list what counts: the system prompt, every message in the conversation (including tool results, images and documents), the tool definitions, and the output the model generates for the turn (Claude docs).

For your assistant, that means:

  • the system prompt: the standing instructions ("You are the makerspace assistant. Only book machines the student is trained on.");
  • the tool definitions: the name and description of each tool, such as check_calendar;
  • the messages so far: the student's questions, the model's replies, every tool request, and every tool result.

If it is not in the window, the model cannot use it. This is the most useful sentence in the lesson, so here is a version to remember: the model only knows what is in front of it right now.

The model does not remember; the program re-sends

Here is the idea that surprises most people. The model keeps nothing from one call to the next. Each call starts blank. What looks like memory is the program sending the whole conversation again each time. The docs describe it this way: each turn's input contains all previous conversation history plus the new message, and the model's output becomes part of the input for the next turn (Claude docs).

In Python, the loop you saw earlier has a list that does this job. Here is the important part, in the style of the Anthropic API (names simplified):

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system=SYSTEM_PROMPT,   # sent every call
                       tools=TOOLS,            # sent every call
                       messages=messages)      # the whole list, every call
    messages.append(reply)                     # keep what the model said
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)      # the program runs the tool
    messages.append(result)                    # keep the result

Read the three append-style lines. The list messages is the agent's short-term memory. If you stopped appending, the model would forget what it had just done. If you never trimmed the list, it would grow forever.

Worked example: what is in the window at each call

The student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Track the messages list.

  1. Call 1. The window holds the system prompt, the tool definitions and one message: the question. The model replies with a request: check_calendar("laser cutter", "tomorrow").
  2. Program step. The program runs the tool. The calendar returns "free 2 pm to 5 pm". The program appends the model's request and this result to the list.
  3. Call 2. The window now holds the fixed part, the question, the model's request, and the calendar result. The model can see the calendar answer only because the program put it there. It requests search_manuals("laser cutter training").
  4. Call 3. The window holds everything from call 2 plus the manual excerpt, which might be 800 words. The model requests check_training_record(student).
  5. Call 4. The window holds all of it plus the training record. The model writes the final answer, which is also added to the list.
  6. After the answer. If the program ends here and starts fresh for the next question, all of this is gone. The model never "knew" the student; it only saw text for four calls.
A common mix-up

"The model remembers our earlier chat, like a person would." It feels true because chat apps show your whole history and replies refer back to it. But the app is re-sending that history each time. If the program does not re-send something, the model has no access to it. This is why "memory" in an agent is something you build, not something you get.

Check yourself

Your program makes call 3 but accidentally sends only the system prompt and the newest tool result, leaving out the earlier messages. What happens?

Show the answer

The third option. The model has no memory between calls, so what is not sent is not known. It would probably write something confused, because it would not even see the student's question.

Worked example: spotting what the model cannot know

A student writes, "Book it for the same time as last week." The assistant has no notes and no history tool. What does the model do, and why?

  1. List what is in the window: the system prompt, the tool definitions, and this one message.
  2. Ask whether "last week's time" appears anywhere in that list. It does not.
  3. So the model has two honest options: ask the student, or call a tool that can look it up (for example a get_booking_history tool you would have to build).
  4. The model cannot reach into last week's session. That session's context is gone unless your program saved it somewhere.
  5. Design lesson: whatever the assistant must know that is not in the current window needs a place to live (notes or a database) and a way to get into the window (a tool or the program loading it).

Why context costs money and can hurt answers 10 min

Your sponsor gave you a small model budget. That makes the size of the window more than a technical detail. It is a cost line.

You pay for the whole window on every call

Because the program re-sends the whole messages list each call, the input for call 4 includes everything in calls 1 to 3. Model usage is generally billed by the tokens sent and received, so the same manual excerpt is paid for again in every later call of the same request. (Claude docs note that prompt caching changes what you pay for repeated tokens, not whether they count toward the window.)

A consequence: a big tool result early in a long run is expensive, because it is re-sent at every later step. A small result is cheap in the same way.

Worked example: cost of one request (invented numbers)

These numbers are made up for the arithmetic; use your real prices later. Suppose the system prompt plus tool definitions are 1,000 tokens, the question is 50 tokens, each tool request plus a small result is 150 tokens, and the manual excerpt is 2,000 tokens. Four calls happen, with the manual excerpt arriving after call 2.

  1. Call 1 input: 1,000 fixed + 50 question = 1,050 tokens.
  2. Call 2 input: 1,050 + 150 (calendar request and result) = 1,200 tokens.
  3. Call 3 input: 1,200 + 2,000 (manual excerpt and request) = 3,200 tokens.
  4. Call 4 input: 3,200 + 150 (training record) = 3,350 tokens.
  5. Total input tokens billed: 1,050 + 1,200 + 3,200 + 3,350 = 8,800 tokens, even though the "new" content is only about 2,350 tokens.
  6. Where the money went: the 2,000-token manual excerpt is paid for twice (calls 3 and 4 both include it), and the 1,000-token fixed part is paid for four times.

If the excerpt had been 500 tokens, calls 3 and 4 would have been 1,700 and 1,850 tokens, and the total 5,800: a one-third saving from sending less.

More context is not always better

There is a second cost, and it is about quality. Anthropic's docs say that as the token count grows, accuracy and recall degrade, which they call context rot, and that this makes curating what is in context as important as how much space is available (Claude docs). Anthropic's engineering team describes context as a finite resource with an "attention budget": each added token uses some of it (Effective context engineering for AI agents).

A research paper found a related pattern. When relevant information sat in the middle of a long input, models did worse than when it sat at the start or end (Liu et al., "Lost in the Middle"). The exact numbers vary by model, so treat this as a warning about long contexts, not a law.

For you the rule is: aim for the smallest set of useful tokens, not the biggest window you can afford. Anthropic's post states the same goal: the smallest possible set of high-signal tokens that gives the outcome you want.

A common mix-up

"Pick a model with a huge window and paste the whole manual in." It is tempting because it is simple: no search code to write. It fails for two reasons you now know. You pay for the whole manual on every call of every request, and a long, crowded context can make the model worse at finding the one line that matters. The window size is a limit on what can fit, not a target for what should.

Check yourself

Your assistant answers a question in six model calls. A 3,000-token tool result arrives after call 2. Roughly how many times is that result paid for as input, if nothing is trimmed?

Show the answer

Four times. The result exists from call 3 onward, and each later call re-sends it. This is why trimming big old results saves real money.

Worked example: choosing between two designs

Design A pastes a 30,000-token laser cutter manual into the system prompt. Design B searches and sends only a 1,500-token excerpt. A typical request takes 4 calls. Compare input tokens from the manual alone.

  1. Design A: the manual is in the fixed part, so it is in all 4 calls: 4 × 30,000 = 120,000 tokens.
  2. Design B: the excerpt arrives after call 2, so it is in calls 3 and 4: 2 × 1,500 = 3,000 tokens.
  3. Ratio: 120,000 / 3,000 = 40 times as many manual tokens for Design A.
  4. Quality: Design A also puts the one relevant paragraph among 30,000 tokens of other text, where it can get lost. Design B puts it nearly alone.
  5. Counterpoint, to be fair: Design B needs search code that can miss the right page. We deal with that in the retrieval section.

What is kept between steps 10 min

Now go one level deeper. Between the steps of a single request, the thing that is kept is the messages list. The question is what to do when it gets big. There are three standard moves, from lightest to heaviest.

1. Keep it all (the default)

For a short request like the laser cutter question, do nothing. Everything stays. The list is small, and the model benefits from seeing every step.

2. Clear old tool results

Tool results are usually the biggest items and the least useful after the model has used them. Anthropic's post calls clearing old tool results "one of the safest, lightest-touch forms" of compaction (Effective context engineering), and the API docs list it as a context-editing strategy (Claude docs).

In your own program this can be a few lines: replace an old, large result with a short placeholder.

def trim_old_results(messages, keep_last=2):
    results = [m for m in messages if m["role"] == "tool_result"]
    for m in results[:-keep_last]:            # all but the newest two
        m["content"] = "[old result removed]"  # keep the slot, drop the text

Notice the trade: you save tokens, and you lose the ability to look at that result again. Only clear results the model will not need, or that it can fetch again with the same tool.

3. Compact: summarize and start fresh

Compaction means that when the conversation nears the limit, you ask the model to summarize it, then start a new window containing the summary. Anthropic's post says Claude Code keeps things like architectural decisions and unresolved bugs, and drops redundant tool output (Effective context engineering). The platform also offers server-side compaction for long conversations (Claude docs).

The risk is that a summary can drop a detail that turns out to matter later. The post advises tuning for recall first (keep everything that might matter), then trimming for precision.

Worked example: a booking conversation that gets long

A student spends 25 messages with the assistant comparing three machines, checking times and asking about safety rules. By message 25 the list holds six manual excerpts of about 1,500 tokens each, and is near 14,000 tokens.

  1. Identify the heavy items: the six manual excerpts are 9,000 of the 14,000 tokens.
  2. Ask which are still needed. The student has decided on the laser cutter, so the 3D printer and CNC excerpts are no longer needed.
  3. Try the light move first: clear the four unused excerpts. That saves 4 × 1,500 = 6,000 tokens, leaving about 8,000.
  4. Keep the facts that matter in plain text: "Student chose the laser cutter; wants Friday after 2 pm." These are short and worth keeping verbatim.
  5. If the list still grows after another 20 messages, then compact: summarize decisions made, bookings made, and open questions, and start a new window from that summary.
  6. Check the risk: does the summary still contain the booking ID? If not, the assistant could later try to book twice. Put the booking ID in the summary prompt as a must-keep item.
Check yourself

A request makes eight calls, and one 4,000-token tool result is large but fully used in the very next step. Which is the lightest sensible move?

Show the answer

Clear the used result. It is the lightest move and removes the biggest cost without losing anything the model still needs.

Worked example: deciding what the assistant must keep verbatim

Mark each item as keep verbatim, summarize, or drop when the window gets crowded.

  1. The system prompt and tool definitions. Keep verbatim: they define the assistant and are re-sent anyway.
  2. The student's current goal ("laser cutter, Friday after 2 pm"). Keep verbatim: short, and the model must not lose it.
  3. A booking ID returned by book_machine. Keep verbatim: short, and an error to repeat it would cost a double booking.
  4. A 1,500-token manual excerpt already answered. Drop (or replace with "laser cutter: min. power 10% for acrylic"): the model has already used it.
  5. Chit-chat ("thanks!"). Drop or summarize in a word.

The pattern: keep short facts that drive future decisions; drop bulky text whose job is done.

What is kept between sessions: notes 10 min

Everything so far lives inside one run. When the run ends and the program exits, the messages list vanishes. A session here means one separate run of the assistant, such as a student visiting on Monday and again on Thursday.

By default, nothing carries over. The Thursday session starts with a blank window. So how does the assistant know on Thursday that the student passed laser cutter training on Monday?

The answer is external memory: information stored outside the context window, in a file or database, that the program can load or the model can look up with a tool. Anthropic's post calls the agent-written version structured note-taking: the agent writes notes to memory outside the context window and pulls them back in later (Effective context engineering).

Two ways to write notes

  • Your program writes them. At the end of a session, or after an event like a passed training, code saves a record. This is the safest for facts you cannot afford to lose, like training status.
  • The model writes them through a tool. You give it, for example, save_note(text) and read_notes(). The model decides what is worth saving. Anthropic's post describes an agent playing a game that kept its own notes and read them back after its context was reset, to continue over thousands of steps (Effective context engineering). Anthropic also documents a memory tool for this (Memory tool docs).

A game analogy helps: think of a save file. The running game is the context window; when you quit, it is gone. The save file is the notes. The game only "remembers" you if it reads your save file at start-up.

Worked example: remembering a student's training status

The goal: on Thursday, the assistant knows Sam passed laser cutter training on Monday. Design it step by step.

  1. Choose what to store. A small record per student: {"student": "sam", "trained": ["laser cutter"], "updated": "2026-11-16"}. Short facts, not whole conversations.
  2. Choose where. A JSON file or a database table keyed by student ID. You already know Python and JSON, so a file is enough to start.
  3. Write on the event. When the training system reports a pass, the program updates the record. This does not depend on the model remembering to do it.
  4. Read at session start. When Sam opens a session, the program loads Sam's record and adds one line to the window: "Sam is trained on: laser cutter."
  5. Or let the model ask. Alternatively, expose check_training_record(student) and let the model call it only when training matters. This keeps the window smaller for visits that never need it.
  6. Check the result. Thursday, the window holds the line (or the tool result). The model answers "You're trained on the laser cutter, so I can book it." It never saw Monday's chat; it saw the note.
A common mix-up

"Just save the whole conversation and load it next time." It sounds like perfect memory. But the old conversation would fill the window with stale chatter, cost tokens on every call, and still be missing the facts that matter, hidden somewhere in the middle. Notes work because they are selected and short: a few lines of facts the assistant will actually need.

Check yourself

The assistant's tool book_machine returns a booking ID. The student returns two days later and asks to cancel "my booking". Where must the booking ID live for the assistant to find it?

Show the answer

In a record outside the model. The booking system itself may already be that record, in which case a lookup tool such as list_bookings(student) is the memory.

The booking calendar is already a memory. When a tool reads a system that persists on its own, you do not need to copy that data into notes. Notes are for facts that no other system holds, such as a student's stated preferences.
Worked example: deciding what goes in notes

Decide for each fact whether it belongs in the notes file, in an existing system, or nowhere.

  1. Sam passed laser cutter training. The training system probably holds this. Read it with a tool; do not duplicate it.
  2. Sam prefers afternoon slots. No other system holds it. Save it as a short note, if Sam agrees to be remembered.
  3. Sam asked what the laser cutter's bed size is. The manual holds the answer; nothing to save.
  4. Sam's student ID. Probably the key for lookups, and personal data. Store it only where your team's privacy rules allow.
  5. The small talk. Nowhere.

Each saved fact has a cost: it must be kept correct. A stale note ("trained on CNC" after the training expired) is worse than no note, so give notes dates.

Retrieval: finding the right page 10 min

The second job of your assistant is answering from long machine manuals. A manual might be 200 pages; the window should hold only a page or two. Retrieval is the step that finds the few relevant pieces and puts only those into the window.

Retrieval is a kind of memory too: the manuals are the assistant's long-term knowledge store, and retrieval is how it recalls from it.

The steps

  1. Chunk. Split each manual into pieces, such as a section or a few paragraphs. A chunk is one such piece.
  2. Index. Prepare the chunks so they can be searched. Two common ways: keyword matching (such as BM25, a standard keyword-ranking method) and embeddings (numeric representations that put similar meanings close together). Anthropic's retrieval write-up describes using both together (Contextual Retrieval).
  3. Search. At question time, find the top few chunks for the question.
  4. Insert. Put those chunks into the window, ideally tagged with their source (manual name and page), so the model can cite them and the student can check.

Chunks can lose their context

A chunk that reads "The minimum is 10%." tells you nothing alone. Which machine? Which setting? Anthropic's contextual retrieval idea is to add a short explanation of where the chunk comes from before indexing it. The company reports that this cut failed retrievals substantially, and more when combined with keyword search and reranking (Contextual Retrieval). The cheap version for you: begin every chunk with its manual title and section heading.

Two ways to put retrieval in the loop

  • Retrieve first. The program searches before the first model call and adds the chunks to the window. Simple and cheap, but it searches even when the question needs no manual.
  • Retrieval as a tool. You give the model search_manuals(query), as in your loop. The model decides when to search and can search again with a better query. Anthropic's post calls loading data only when needed "just in time" retrieval and notes the trade-off: it is slower, and needs good guidance so the agent does not waste context (Effective context engineering).
Worked example: chunking and retrieving for the laser cutter manual

Question: "What speed should I use to cut 3 mm acrylic?"

  1. Chunk the manual by section. You get chunks such as "Laser cutter / Materials / Acrylic", "Laser cutter / Safety / Fire", and "Laser cutter / Maintenance / Lens cleaning".
  2. Prefix each chunk with its path. The acrylic chunk now begins "Laser cutter > Materials > Acrylic:", so its text stands alone.
  3. Search with the question. A keyword search matches "acrylic" and "3 mm"; an embedding search would also match a chunk phrased "PMMA sheet settings".
  4. Take the top three chunks. Say: the acrylic chunk, the "Speed and power" chunk and the fire-safety chunk. About 1,500 tokens in total.
  5. Insert them with their sources in the tool result. The model reads them and answers with the setting, citing "Laser cutter > Materials > Acrylic".
  6. Check the miss case. If the model's answer says "the manual doesn't say", the search may have missed it. A better design lets the model rephrase and search again, rather than guess.
A common mix-up

"Retrieval means the model looks things up by itself." It feels that way when it works. But the model only reads what the search returns. If chunking splits the answer in half, or the search ranks the right chunk fifth and you keep only three, the model never sees it, and it may answer from guesswork anyway. Most wrong answers in retrieval systems start in the search, not the model.

Check yourself

Your assistant answers "What is the maximum stock thickness for the bandsaw?" wrongly, though the manual states it clearly. Where should you look first?

Show the answer

Print the retrieved chunks. Separate "was the right text in the window?" from "did the model use it well?", and debug the first before the second.

Worked example: sizing chunks

Your manual has a table of speed settings spanning 600 tokens. Should chunks be 200 tokens or 800 tokens?

  1. Try 200 tokens. The table is cut into three chunks. A search might return the middle one: numbers with no header saying what they mean.
  2. Try 800 tokens. The whole table fits in one chunk, with its header and the sentence before it.
  3. Check the cost side: 800-token chunks, three returned, add 2,400 tokens per search, against 600 for 200-token chunks.
  4. Pick by content, not by a fixed number: split on section and table boundaries, so each chunk is one meaningful unit.
  5. Test with five real questions from students and see which chunk sizes return the right text. Keep the smallest size that does.

Worked example: one request, every memory in play

Thursday, Sam says: "Book the laser cutter for Friday at 3 pm, same as I like."

  1. Session start. The program loads Sam's note into the window: "Sam: trained on laser cutter. Prefers afternoons." That is notes, from Monday, via the program.
  2. Call 1. The model reads the question and the note. It requests check_calendar("laser cutter", "Friday"). That is a tool reaching another system.
  3. Call 2. The result shows 3 pm free. The model needs the booking rules, so it requests search_manuals("laser cutter booking limit"). That is retrieval.
  4. Call 3. Chunks return: sessions are max 2 hours. The model requests book_machine(...).
  5. Call 4. The booking ID returns. The model writes the final answer with the ID. All of this lived in the window: the messages list.
  6. Session end. The window is discarded. The booking ID is already in the booking system. The program does not need to save anything else.
Worked example: choosing under a budget

Your sponsor's budget is small. You can afford to cut about half the tokens per request. Where do you look first?

  1. List the biggest consumers: the fixed prompt and tool definitions (paid every call), retrieved chunks (paid from arrival onward), and old tool results.
  2. Fixed part first: shorten the system prompt and write brief, clear tool descriptions. Every token saved is saved on every call.
  3. Retrieved chunks next: return the top three, not ten, and prefer small, well-cut chunks.
  4. Then clear used results, as in the booking-conversation example.
  5. Last, consider caching the fixed part; the docs say prompt caching changes what you pay for these tokens, not whether they count toward the window (Claude docs). Check current prices before relying on it.
  6. Measure before and after on a handful of real questions, so the claim in your design review is a number, not a feeling.

Worked example and practice 8 min

Worked example: draw the memory plan for a new feature

Your team adds a feature: the assistant should warn a student if a machine they booked is under maintenance, and remember if the student turned warnings off.

  1. List the facts. (a) Which machines are under maintenance. (b) The student's booking. (c) Whether warnings are on or off.
  2. Assign homes. (a) changes daily and belongs to a maintenance schedule: a tool reads it. (b) lives in the booking system: a tool reads it. (c) is a personal preference no other system holds: it goes in the student's notes.
  3. Decide how each reaches the window. (c) is loaded at session start (it is tiny, and needed every time). (a) and (b) are fetched by tools only when relevant.
  4. Decide what to write back. If the student says "stop the warnings", the program or a save_note tool updates the note. Test it by starting a new session and checking the setting is read.
  5. Check cost. The note adds about 20 tokens per call. Tools add tokens only on requests that need them.

More practice for your design review 12 min

Skills stick through effortful practice, so here are three more cases. Each has a worked example first, then a task where you do more of the steps yourself.

Case 1: write the compaction instruction

If you compact, the summary is only as good as the instruction that asks for it. The instruction is a piece of design you can defend in review.

Worked example: a compaction prompt for the booking assistant

A long conversation is about to be summarized. Write the instruction so the summary keeps what matters.

  1. List what must survive. The student's current goal, any booking made (with its ID), anything the student told the assistant to avoid, and open questions.
  2. Say it in the instruction. "Summarize this conversation. Always keep: the student's goal, every booking ID and its machine and time, stated preferences, and unanswered questions."
  3. List what can go. Raw manual excerpts already used, greetings, and repeated calendar results. Add: "Drop raw tool output; keep only conclusions drawn from it."
  4. Test it on a real transcript. Run the instruction on a saved 25-message conversation and read the summary.
  5. Check for the costly misses. Is every booking ID still there? Is the chosen machine named? If an ID is missing, the assistant could double-book later, so add a stronger line about IDs.
  6. Prefer recall first. Anthropic's post suggests making sure the summary captures everything relevant before tightening it to save tokens (Effective context engineering).

Then ask the assistant a question that depends on a booking (for example, "when is my 3D print?") using only the summary, and see whether it answers correctly.

Case 2: write a retrieval test

A design review will ask, "How do you know the assistant finds the right page?" A small test is the honest answer.

Worked example: a five-question retrieval check

You have the laser cutter manual chunked and indexed. Build a test before you ever call the model.

  1. Collect questions. Write five questions students really ask, such as "What is the maximum material thickness?" or "How do I clean the lens?"
  2. Mark the right chunk. For each question, find by hand the chunk that holds the answer and note its heading.
  3. Run the search only. For each question, print the top three chunk headings returned. No model is involved yet, so this is free.
  4. Score. Count a hit when the marked chunk is among the three. Suppose you get four of five.
  5. Study the miss. Look at the fifth: the manual says "kerf" and the student wrote "cut width". A keyword search misses this; an embedding search or a synonym added to the chunk might fix it.
  6. Re-run after every change. A change that fixes one question but breaks two others is not an improvement, and the test shows it.

2. The chunk (or chunks) that actually contain the answer, found by reading the manual yourself. 3. Whether the marked chunk appears in the top few results, counted over all five questions. 4. It costs no model tokens, so you can run it many times while changing chunk size or search method, and it isolates the search from the model, which tells you where a wrong answer starts.

Case 3: argue the memory design in two minutes

Reviewers like clear reasons. Here is a script you can adapt.

Worked example: a short defense

The reviewer asks, "Why not just give the assistant the full conversation history for every student?"

  1. State the facts. The model forgets between calls; every token in the window is paid for on every call.
  2. Give the cost. A student with ten past sessions of 3,000 tokens each would add 30,000 tokens to every call of every request, which in our four-call example is 120,000 input tokens per question for history alone.
  3. Give the quality risk. Long contexts can reduce recall, and the one fact we need would sit among old chatter.
  4. Offer the alternative. A short note per student with training status and preferences, a few dozen tokens, loaded at session start; bookings read from the booking system by a tool.
  5. Name the trade-off. We might lose a detail that was never saved. We accept that and mitigate it: the model can ask the student, and we can add a field if a gap shows up often.
  6. Close with evidence. We will test with ten sample questions and report accuracy and tokens per request.

One more tool: a clean window for a side task 5 min

Sometimes one step of the work needs lots of reading, but the main conversation only needs the conclusion. You can run that step in a separate model call with its own fresh window, and return only a short summary to the main one. Anthropic's post describes this as a sub-agent: it may use tens of thousands of tokens exploring, then returns a distilled summary, often 1,000 to 2,000 tokens (Effective context engineering).

Here you only need the idea as a memory tool: a side window keeps bulky reading out of the main window. Whether splitting work across agents is worth the extra complexity is a later lesson, so treat this as a preview.

Worked example: a safety check that reads three manuals

A student plans a project using the laser cutter, a heat gun and a soldering station, and asks, "Is there anything I should know before using these together?"

  1. Without a side window. The main window receives three safety chapters of about 3,000 tokens each: 9,000 tokens, re-sent on every later call of the conversation.
  2. With a side window. A separate call reads the three chapters in its own window and writes a 300-token summary of the shared hazards (ventilation, fire, burns).
  3. What returns. Only the 300-token summary enters the main window.
  4. Count the saving. If five more calls follow, the main window carries 300 tokens instead of 9,000 on each: a difference of 8,700 tokens per call.
  5. Name the cost. The side call itself used about 9,300 tokens once, and the summary can omit a detail. It pays off only when the main conversation is long enough to re-send the savings many times.
  6. Decide. For a one-question conversation, just retrieve the top chunks. For a long planning conversation, the side window can pay off.
Check yourself

A side window reads 20,000 tokens and returns a 500-token summary to a conversation that then makes ten more calls. What does the main window carry for this task on those calls?

Show the answer

About 500 tokens per later call. The side window's reading is kept out of the main one; only the summary comes back.

Summary 3 min

  • The context window is everything the model sees on one call: system prompt, tool definitions, messages, results. The model keeps nothing between calls; the program re-sends the list.
  • You pay for the whole window on every call, and a crowded window can hurt accuracy. Aim for the smallest useful context.
  • Between steps, the messages list is the memory: keep it, clear old tool results, or compact it.
  • Between sessions, only what you store outside the window survives: curated notes, records, or other systems reached by tools.
  • Retrieval finds the right chunk of a long manual and puts only that in the window. Check the search first when answers are wrong.
