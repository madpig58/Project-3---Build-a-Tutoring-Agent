Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a note saved between sessions, or in a manual the assistant searches.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Both problems are context and memory problems, and you will have to defend your choices at the design review.

Warm-up 2 min

Recall

From memory: in the agent loop, a tool has just run. Who ran it, the model or the program around it? And what happens to the tool's result next?

Check your answer

The program ran it. The model only wrote a request naming the tool and its arguments. The program then sends the result back to the model in its next input and calls the model again.

Today's question is about that next input: what exactly is in it, how big can it get, and what survives after the loop ends?

The context window 5 min

Start with a game. In a game engine, a frame is drawn from whatever is in memory right now. If a texture is not loaded, it is not on screen. A language model works the same way: it can only use what is in front of it on this call.

That "in front of it" has a name. The context is the set of tokens included when the model is called (Anthropic, context engineering). A token is a small chunk of text, often a word or part of a word. The context window is the maximum number of tokens the model can take in on one call.

The context is more than the student's question. It holds the system prompt, the tool descriptions, any examples, the message history and any data you retrieved. Everything counts toward the window.

Worked example: what is in one call?

A student asks the makerspace assistant, "Is the laser cutter free Friday?" Here is the context for the very first model call.

  1. The program starts with the system prompt: the assistant's role and rules. Say 400 tokens (illustrative numbers, not measurements).
  2. It adds the tool descriptions for check_calendar, search_manuals and book_machine. Say 600 tokens, because each has a name, a purpose and parameters.
  3. It adds the student's question: about 10 tokens.
  4. The model reads all of that, about 1,010 tokens, and writes a request for check_calendar.
  5. Notice what is absent: yesterday's chat, the manuals, the booking system. If it is not in the context, the model does not know it.

Two limits follow from this. The first is a hard one: the context cannot go past the window. The second is soft and matters just as much for you.

Anthropic describes context rot: as the number of tokens grows, the model's ability to recall information from the context decreases. They explain it with an "attention budget" that each extra token draws down. The drop is gradual, not a cliff (Anthropic). So a bigger window does not mean you should fill it.

There is a cost side too. You pay for the tokens you send and the tokens the model writes, so a bloated context makes every call slower and more expensive. For a small budget, the context is the first thing to keep lean.

A common mix-up

"The model remembers the conversation." It is tempting because chat apps feel that way. In fact the model keeps nothing between calls; the program builds the context fresh each time and includes the history. If the program leaves a message out, the model has never heard it. (This is also why automatic memory of earlier conversations does not exist by default.)

What is kept between steps 6 min

Now put the context inside the loop you already know. Each step is one model call, and the program rebuilds the context for it. To let the model build on earlier steps, the program appends each model output and each tool result to the history and sends the whole thing again.

So "kept between steps" means "kept in the history the program resends." It is not the model's memory; it is the program's list.

Worked example: counting what you send

The assistant answers "Is the laser cutter free Friday, and do I need training?" It uses two tools. Illustrative sizes: starting context 1,000 tokens; each model output 100 tokens; each tool result 600 tokens.

  1. Call 1 sends 1,000 tokens. The model asks for check_calendar.
  2. The program runs it and appends the output (100) and the result (600). The history is now 1,700 tokens.
  3. Call 2 sends all 1,700. The model asks for search_manuals.
  4. The program appends 100 and 600 again. The context is now 2,400.
  5. Call 3 sends 2,400 and the model writes the final answer.
  6. Total sent: 1,000 + 1,700 + 2,400 = 5,100 tokens, even though the biggest single context was only 2,400.

This is why a long loop costs more than you might guess: every step pays again for everything before it.

What do you do when the history gets too long? Anthropic names three tools.

  • Clearing old tool results: drop big outputs the model has already used. Anthropic calls this one of the lightest forms of compaction.
  • Compaction: summarise the conversation and start a new context window with the summary (Anthropic). A good summary keeps decisions and open problems and drops redundant output.
  • Sub-agents: a helper explores in its own clean context and hands back a short summary. Anthropic says a helper may use tens of thousands of tokens and return only 1,000 to 2,000. You will meet this in a later lesson.
Worked example: trimming the manual search

In the example above, the 600-token manual result was needed for one decision. Suppose the loop continues for ten more steps.

  1. Without trimming, the 600 tokens ride along in every later call: 10 calls × 600 = 6,000 extra tokens sent.
  2. Instead, after the model writes down the one fact it needs ("laser cutter: training level 2 required"), the program replaces the long result with that line, say 15 tokens.
  3. Now the same ten calls carry 10 × 15 = 150 tokens of that result.
  4. The risk: if the model later needs another detail from the page, it is gone. So Anthropic's advice is to first keep enough to recall everything important, then trim for precision.

What is kept between sessions 5 min

A session is one run of the assistant for one student visit, from the first question to the end. When the session ends, the program stops and the context is gone. Nothing in the model changed.

So by default, the answer to "what is kept between sessions?" is nothing. A student who was told yesterday "you passed laser cutter training" is a stranger to the assistant today.

A video game has the same problem. If you quit without saving, the game does not remember. A save file fixes that: the game writes state to disk, and next launch it reads the file back. Agent memory between sessions is a save file you design.

Worked example: remembering a training status

Riley's assistant must remember that a student passed laser cutter training.

  1. The student finishes training. A person or a tool records it: {"student": "s123", "laser": "passed"} in a file or table.
  2. The Monday session ends. The context disappears; the record stays.
  3. On Friday, the student asks to book the laser cutter. The program looks up s123 and puts one line in the context: "Training: laser passed."
  4. The model books the machine without asking again.
  5. Notice that only a short line was loaded, not the student's whole history. That keeps the context small.

There is a design choice here. Which facts deserve saving? Save what the next session will need and cannot cheaply rediscover: training status, preferences, unfinished bookings. Do not save every message.

A common mix-up

"A bigger context window gives the assistant memory." It is tempting because both are about what the model can see. But a window is per call and disappears with the session. Even a huge window starts empty on Friday. Memory between sessions needs storage outside the window.

Check yourself

You want the assistant to know a student's preferred 3D printer next week. What should you build?

Show the answer

The first option: store it and load it. The window is per call, and the model does not learn from a single chat.

Retrieval: finding the right page 6 min

Back to the manuals. Say the laser cutter manual is 300 pages, roughly 150,000 tokens (an illustrative guess). Pasting it into every call would be slow, costly and, because of context rot, less accurate. So we keep it outside the window and bring in only what a question needs.

Retrieval means searching a collection for the pieces relevant to the current question and putting only those into the context. Anthropic lists retrieval, tools and memory as the augmentations that make up the basic building block of agentic systems (Building effective agents).

A simple retrieval pipeline has three steps. First, split the manual into chunks, small pieces such as a page or a section. Second, when a question arrives, score each chunk for how well it matches. Third, return the top few chunks.

The scoring can be keyword search, like finding exact words, or a meaning-based search that matches "cutting material for acrylic" to a page that says "recommended settings for plastics." Either way, the output is a short list of chunks.

Worked example: one question against the manual

A student asks, "What power setting do I use for 3 mm acrylic on the laser cutter?"

  1. The model decides this needs the manual and calls search_manuals("laser cutter acrylic power setting"). The model writes the query, not the program.
  2. The tool scores the manual's chunks, about 500 tokens each, and returns the top three: the settings table, a safety note on acrylic, and the focus procedure.
  3. The program appends those 1,500 tokens to the context as the tool result.
  4. The model answers from the table and cites the page.
  5. Compare: 1,500 tokens instead of 150,000. That is a hundredth of the input, on a small budget.

Anthropic also describes just-in-time retrieval: the agent keeps light references, such as file paths or links, and loads the content only when needed. Their coding agent loads some files up front and uses search tools to fetch the rest. They note it is slower than precomputed retrieval, so a hybrid is often best (Anthropic).

Worked example: a hybrid for your assistant

You have a short safety sheet that applies to every machine and 12 long manuals.

  1. Put the short sheet in the system prompt. It costs a few hundred tokens every call but is always relevant.
  2. Give the model a list of the 12 manual names as references, a few tokens each.
  3. When a question names a machine, the model calls search_manuals for that manual only.
  4. Trade-off: the search costs one extra model call, but you avoid carrying 12 manuals.
A common mix-up

"Retrieval always finds the right page." It is tempting because search feels reliable. But retrieval can return the wrong chunks, such as the page for a different machine. The model will then answer from them with confidence. Test retrieval on real questions and check what it returns.

Check yourself

The assistant retrieves three chunks for a question about the 3D printer, and the answer cites a page about the CNC router. What is the likeliest cause?

Show the answer

The third option. The model only sees what retrieval puts in, so a wrong page in means a wrong answer out.

Notes as memory 4 min

The third idea joins the last two. Anthropic calls it structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window and reads them back later (Anthropic).

Their example is an agent playing a Pokemon game. Over thousands of steps it kept notes such as how many levels a creature had gained toward a target, and after its context was reset it read the notes and carried on. A game-save analogy fits again, but here the agent decides what to write.

Notes serve two purposes. Within one long task, they let you trim the context without losing progress. Across sessions, they are the save file from the last section.

Worked example: a note during a long booking

A student asks the assistant to find a time when the laser cutter and the vinyl cutter are both free this week.

  1. The assistant checks the laser cutter's calendar: seven days of entries, a large result.
  2. It writes a note: laser free: Tue 2-5, Thu 10-12. The program stores it in a notes file for this task.
  3. The program drops the large calendar result from the context. The context shrinks, and the note keeps the finding.
  4. The assistant checks the vinyl cutter and finds Thu 10-11 free.
  5. It reads its note, finds the overlap (Thu 10-11), and proposes it.

Notes also have risks. A note can be wrong, or stale: the calendar might change after you wrote "free on Thursday." Treat notes about fast-changing facts, like bookings, as hints and re-check the calendar tool before booking.

Defending the choice at your design review 3 min

Your team will ask "why not just paste everything in?" You now have a three-part answer: cost, accuracy and persistence.

Cost: every call resends the history, so extra tokens are paid for on every step. Accuracy: more tokens means a thinner attention budget, so recall of the one page that matters can get worse. Persistence: a window ends with the session, so it cannot hold a training record.

Worked example: two designs compared

Design A pastes all 12 manuals (say 600,000 tokens) into every call. Design B retrieves three 500-token chunks per question. Both use illustrative sizes.

  1. Design A cannot even work if the window is smaller than 600,000 tokens; the request fails before the model answers.
  2. Suppose it did fit. A four-call request resends the manuals four times: 2,400,000 tokens, before counting history.
  3. Design B adds 1,500 tokens of chunks once, and they ride along in later calls: at most 4 × 1,500 = 6,000 tokens.
  4. Design B's risk is retrieval missing the right page, so you test it on 20 real student questions before the review.
  5. Your argument: B costs a fraction, keeps the context short for better recall, and its main risk is testable.
Say it aloud

A teammate says, "Let the assistant remember everything every student ever said." Give two reasons, using this lesson, why that is a poor default.

Show a sample answer

Loading it all grows the context, which raises cost on every call and can lower recall. Much of it is stale or irrelevant, such as old calendar results. Better to save a few durable facts and load only the relevant ones.

Worked example and practice 5 min

Worked example: design one request end to end

Returning student s123 asks, "Book me the laser cutter Friday and remind me how to focus it." Plan the context and memory for this request.

  1. Start of session: the program loads the system prompt and tool descriptions, then looks up s123's record and adds "Training: laser passed." This is the saved-record step.
  2. The model calls check_calendar live, because bookings change fast. The result goes into the history.
  3. The model calls search_manuals("laser cutter focus procedure"). Retrieval returns the focus chunk only, not the manual.
  4. The model calls book_machine, then writes the answer: confirmation plus focus steps.
  5. End of session: the program saves a short note, "Booked laser Friday," if you decide next visit will need it. The rest of the context is thrown away.
  6. Check the cost: four calls, each resending the history. You trim the calendar result after step 2 to keep later calls small.
Your turn

Student s456 asks: "Which vinyl cutter blade do I use for thick vinyl, and can I book it Tuesday?" s456 has not done vinyl cutter training. Plan it. Step 1 is given: at session start the program loads the rules, the tool descriptions and s456's record. Now decide (a) which tool or retrieval fetches each fact, (b) what stays in the context, and (c) what, if anything, to save at the end.

Show a solution

(a) The blade question is answered from the vinyl cutter manual by search_manuals, which returns the blade-settings chunk. The Tuesday availability is checked live with check_calendar. The training status comes from the loaded record, which says not trained.

(b) The context holds the rules, tools, the record line, the retrieved chunk and the calendar result. The model should tell the student training is needed before booking, so it does not call book_machine.

(c) Save a short note such as "Asked about vinyl cutter; needs training," so the next session can offer training. Do not save the calendar result, which will be stale.

Second turn: count the tokens

An agent starts with 2,000 tokens of context. Each model output is 100 tokens and each tool result is 1,000 tokens. It makes three model calls: two tool requests and the final answer. How many tokens in total does it send across the three calls?

Show a solution

Call 1 sends 2,000. Call 2 sends 2,000 + 100 + 1,000 = 3,100. Call 3 sends 3,100 + 1,100 = 4,200. Total: 2,000 + 3,100 + 4,200 = 9,300 tokens.

Summary 2 min

  • The model sees only the context of the current call; the program rebuilds it each time, and a long context costs more and can be recalled less well.
  • Between steps, "memory" is the history the program resends, so trim or summarise it when it grows.
  • Between sessions, nothing is kept unless you save it; a save file you design holds what the next session needs.
  • Retrieval brings only the relevant pieces of a big source into the context; notes let the agent save findings outside it.
