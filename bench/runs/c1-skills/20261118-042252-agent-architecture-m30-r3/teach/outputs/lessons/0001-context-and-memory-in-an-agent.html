Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context at each step, what gets saved between sessions, and how the assistant finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one question: what does the model see, and what does it cost to show it?

This lesson gives you the vocabulary and the numbers to answer that question at your design review.

Warm-up 2 min

Two questions from the agent loop. Answer them in your head first, then open the answers.

Recall 1

The model asks for a tool, and the program has just run it. What does the program do with the result, and why?

Check your answer

It puts the result into the model's next input and calls the model again, so the model can use it to pick its next step or write the final answer.

Today's question is what "the model's next input" really contains, and how it grows.

Recall 2

Who runs the tool: the model or the program around it?

Check your answer

The program. The model only writes a request that names the tool and its arguments. This matters here because the program is also the thing that decides what the model gets to see and what gets saved.

The context window: everything the model sees 6 min

Start with a game. Imagine a non-player character (NPC) in a game engine. Each time the player talks to it, your code builds one block of text and sends it to a language model. The NPC knows only what is in that block. If you leave the shopkeeper's inventory out, it cannot mention the inventory.

That block is the context: all the text the model is given for one call. The context window is the limit on how much text fits in it. Text is measured in tokens, small chunks of text, often a short word or part of a longer one. A rough rule is that one token is about four English characters, or three quarters of a word.

Anthropic describes context as a finite resource: the model's ability to recall information from the context decreases as the number of tokens grows, an effect they call context rot (Anthropic, Effective context engineering for AI agents). So there are two limits. One is hard: the window size. The other is soft: the more you pack in, the less reliably the model uses each piece.

What is inside the context of your assistant

For the makerspace assistant, one call carries these parts:

  • System prompt: your instructions, such as "You are the makerspace assistant. Never book a machine for a student without training."
  • Tool descriptions: the name, purpose and parameters of each tool, from the last lesson on tools.
  • The conversation so far: the student's messages and the assistant's replies.
  • Tool requests and tool results: everything the loop has produced in this request.

The model has no other source. If a fact is not in this list, the model does not have it, except for what it learned in training.

Worked example: counting what one call contains

A student asks, "How do I change the focus lens on the laser cutter?" Count the context of the first model call.

  1. System prompt: 800 tokens. It is written once by you and sent on every call.
  2. Tool descriptions: 600 tokens for three tools (search_manuals, check_calendar, book_machine).
  3. The student's question: about 30 tokens.
  4. No tool results yet, so the first context is 800 + 600 + 30 = 1,430 tokens.
  5. The model answers with a request: search_manuals("laser cutter focus lens"). That is about 50 output tokens.

Notice that before the assistant has done anything, 1,400 of the 1,430 tokens are your own fixed text. Short, clear prompts and tool descriptions save money on every call. This is also why the previous lesson's advice on tool descriptions is a cost topic, not only a quality one.

Anthropic's goal for context is "the smallest set of high-signal tokens" that makes the result you want likely. Treat every token as something you pay for and something the model must read.
A common mix-up

"A bigger context window fixes everything: paste in the whole manual." It is tempting because the window is the hard limit. But a window is a maximum, not a target. Every token you add costs money on every call it is sent, and a fuller context makes recall less reliable. A 400-page manual in every call would be expensive and the answer could still be wrong.

What is kept between steps 6 min

Now put the context inside the agent loop. The key fact, which surprises most people: the model itself keeps nothing between calls. It is a function from text in to text out. Each step is a separate call, as you saw with the four-call count in the last lesson.

So what is kept between steps? Your program keeps a list of messages, and each time it calls the model it sends the whole list again. After each step it appends two things: the model's request, and the tool's result. This list is the agent's short-term memory: what it knows within one task or conversation. (Elastic uses this same split between chat history that fits in the window and long-term memory that is recalled on demand.)

You have already written this in Python. It is a list that grows:

messages = [system_prompt, user_question]
while True:
    reply = call_model(messages, tools)   # the whole list goes in, every time
    messages.append(reply)                # keep the model's request
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request) # the program runs the tool
    messages.append(result)               # keep the tool's result

Each line has a job. call_model(messages, tools) sends the entire history, not just the last item. The two append lines are the memory between steps: remove them and the model would forget what it just asked for. That memory is only a list in your program.

Why this costs money

Model usage is typically billed per token, counting both tokens sent in (input) and tokens written (output). Because the whole list is sent on every call, the input grows with each step. A long loop does not cost "steps times a small amount"; it costs the sum of ever-larger inputs.

Worked example: the bill for one request

Continue the focus-lens request. The first call had 1,430 input tokens and produced a 50-token tool request. The search tool returns one manual page of 3,000 tokens. Then the model asks for check_calendar (50 tokens), which returns 200 tokens. Then the model writes the answer. Find the total input tokens.

  1. Call 1 input: 1,430 tokens.
  2. Call 2 input: the old context plus the model's request plus the page: 1,430 + 50 + 3,000 = 4,480 tokens.
  3. Call 3 input: call 2's input plus the second request plus the calendar result: 4,480 + 50 + 200 = 4,730 tokens.
  4. The model writes the final answer in call 3, so there are three calls.
  5. Total input: 1,430 + 4,480 + 4,730 = 10,640 tokens, for a question whose new information is a 3,200-token page and a calendar.

Now see the effect of one design choice. If the search tool returned only the 800-token paragraph about the lens instead of the whole page, call 2 would be 1,430 + 50 + 800 = 2,280 and call 3 would be 2,280 + 50 + 200 = 2,530. The total would be 1,430 + 2,280 + 2,530 = 6,240 tokens, about 41% less, with the same answer. What a tool returns is a budget decision.

Some providers can discount input that repeats at the start of each call (often called prompt caching). Check your provider's pricing before relying on it; the principle that the whole history is re-sent does not change.
A common mix-up

"The model remembers the earlier steps, so only the new text costs tokens." It feels natural because the conversation seems continuous. But the model has no memory of its own. The program re-sends everything every time, and you are charged for it. A tool that returns 3,000 tokens in step 2 is paid for again in every later step of that request.

Check yourself

A tool result of 2,000 tokens comes back after call 2 of a request that has 6 model calls in all. In how many calls is it part of the input?

Show the answer

The third option. The result enters the list after call 2 and the program sends the list in full on every later call, so calls 3, 4, 5 and 6 all include it: 4 × 2,000 = 8,000 input tokens from one result.

When the context fills up 5 min

Two things push back on a growing list: cost, and the window limit with context rot. An agent that runs for a long time needs a way to shrink its context. Anthropic describes three techniques; here are the two simplest (Anthropic).

Clearing old tool results means replacing a big result you no longer need with a short stub. Anthropic calls it one of the lightest forms of compaction. Compaction means asking the model to summarize the conversation as it nears the limit, then starting a fresh context from the summary. The article says to keep things like decisions and unresolved problems and to drop redundant tool output, and to tune for recall first, then precision.

The third technique, sub-agents, hands a side task to another model call with a clean context that returns a short summary. We come back to it in a later lesson, because it is about when to split work across agents.

Worked example: clearing a stale tool result

A student is booking a 3D printer. The assistant has searched the printer manual (3,000 tokens) and has already told the student the nozzle temperature. Now it moves on to booking. How do you trim the context?

  1. Find what is dead weight. The manual page is no longer needed for booking, but it is still sent on every call.
  2. Replace it with a stub in the list, such as "[search_manuals result cleared; page: Printer, Nozzle temperatures]". That is about 20 tokens.
  3. Keep the pointer. If the model needs the page again, it can call search_manuals with the same query.
  4. Check the saving: 3,000 tokens down to about 20, paid for on each remaining call.

The risk is clearing something the model still needs. That is why Anthropic suggests tuning a summary for recall first: it is cheaper to carry a little extra than to lose the one fact that mattered.

Worked example: compaction by summary

A long chat with a student has 40 messages about a laser-cut enclosure. The window is nearly full. What goes in the summary?

  1. Keep the decisions: "Student chose 3 mm birch plywood; booked laser cutter, Friday 2 pm."
  2. Keep unresolved items: "Student still needs to confirm the file is a vector file."
  3. Drop what repeats: the long manual excerpts and the back-and-forth that led to the choices.
  4. Start a new context with the system prompt, tools and the summary (about 150 tokens instead of thousands).

What is kept between sessions: notes 6 min

Everything so far lives inside one task. A session is one conversation or task from start to finish. When it ends, your program's message list is gone, and the next session starts with an empty list. Nothing carries over automatically, and the model certainly does not remember the student.

To remember between sessions, the program must save something outside the context, then load it into the next one. This is the long-term memory. Anthropic calls one form structured note-taking: the agent writes notes to storage outside the context window and reads them back later. Their examples include a to-do list and a NOTES.md file that tracks progress across many tool calls, and an agent playing Pokémon that kept notes such as how many levels a character had gained toward a target, and used them to carry on after its context was reset (Anthropic).

Think of a game save file. The game does not keep the player's progress in memory when you quit; it writes a save and reads it at the next start.

Worked example: remembering a student's training

On Monday, Priya completes laser cutter safety training. On Wednesday she opens a new chat and asks to book the laser cutter. How does the assistant know?

  1. At the end of training, the program (or a tool, save_note) writes to a store keyed by student ID: {"priya": {"laser_cutter": "trained 2026-11-16"}}. A JSON file is enough to start.
  2. On Wednesday, a new session begins with an empty message list.
  3. The program loads Priya's record and puts it in the context: "Student record: laser_cutter trained 2026-11-16."
  4. She asks to book. The model sees the record and calls book_machine without asking her again.
  5. The record is a few dozen tokens, so remembering costs almost nothing compared with re-sending a manual.

The unit of memory here is a small fact, not a transcript. Saving whole chats and reloading them would fill the window with old text.

Two ways to load notes

You can load notes up front, as above, or give the model a tool such as read_note and let it fetch notes when needed. Claude Code does both: it puts CLAUDE.md files into context at the start and uses search tools to pull in other files as needed (Anthropic). Up front is simple and reliable for small, always-needed facts. On demand saves tokens when notes are large, at the price of an extra step and the risk the model does not look.

Notes about students are personal data. Save only what the assistant needs, such as training status, and ask your university what it requires for storing student records.
A common mix-up

"The assistant will remember Priya because she talked to it before." This is the idea that memory is automatic. It sounds right because people remember conversations. The model starts every call blank, so unless your program saved a note and loaded it, Wednesday's assistant has never met her.

Check yourself

Show the answer

The third option: save a small fact outside the context and load it at the start of the next session.

Retrieval: finding the right page 6 min

Notes are small. A manual is not. The assistant must answer from hundreds of pages, and the context cannot hold them. Retrieval means searching a store of documents for the few pieces that fit the question, and putting only those in the context. It is the same idea as notes, with the difference that the store is large and the program searches it instead of reading all of it. (One survey of agent memory describes retrieval memory as returning only the relevant slice of long-term storage; see Du, Memory for Autonomous LLM Agents.)

A typical setup has three steps. First, split each manual into chunks, pieces of a few hundred tokens, such as one section each. Second, build an index so you can search the chunks. Third, at question time, search the index and return the top few chunks as the tool result.

There are two common ways to search. Keyword search matches words: it finds chunks that contain "focus" and "lens". Embedding search turns each chunk and the question into an embedding, a list of numbers that places texts with similar meaning close together, so "adjust the lens height" can match "change the focal distance". Many systems combine both. Anthropic notes that many applications retrieve with embeddings before the model runs, while agents can also explore just in time with tools like grep, which is slower but needs no pre-built index (Anthropic).

Worked example: keyword retrieval on a tiny manual

A manual has four chunks. The question is "How do I change the focus lens on the laser cutter?" Pick the chunk to return.

  1. Chunk A: "Laser cutter safety: wear goggles, never leave the machine unattended."
  2. Chunk B: "Laser cutter focus lens: remove the nozzle, unscrew the lens holder, seat the new lens, and refocus."
  3. Chunk C: "3D printer nozzle temperatures for PLA and PETG."
  4. Chunk D: "Laser cutter bed: honeycomb cleaning schedule."
  5. Count shared words with the question (ignoring "the", "how", "do", "I"): A shares "laser", "cutter". B shares "focus", "lens", "laser", "cutter" (4). C shares none. D shares "laser", "cutter".
  6. Return chunk B, about 800 tokens in a real manual, not the whole machine's chapter.

Chunk A also matched two words, which shows why one match is not enough. A keyword hit on the machine name alone is a weak signal; hits on the rare words "focus" and "lens" are strong. Real systems weigh rare words more.

Retrieval can fail

Retrieval is a search, and a search can miss. If the chunk was cut so that the steps are split across two chunks, you may return half a procedure. If a student writes "the beam is blurry", a pure keyword search will not match "refocus". Two fixes: cut chunks along section boundaries, and have the tool return the section title and page with each chunk so the assistant can cite it and ask for a neighbor chunk. Test retrieval alone, by looking at what comes back for ten real questions, before you blame the model.

A common mix-up

"Retrieval means the model has learned the manual." It feels like learning because the answers improve. But the model learns nothing. A tool finds text, the program puts it in the context for this one call, and the model reads it like any other text. Next session it must be retrieved again.

Check yourself

The third option. The failure is in the search, so fix the search: embeddings match by meaning where keywords match only by spelling.

Notes, retrieval and context compared 3 min

The three ideas are easy to blur, so set them side by side. Ask of each: who writes it, how big is it, and when does it reach the model?

IdeaWhat it holdsSizeHow it reaches the model
ContextEverything for one callLimited by the window and the budgetIt is the input
NotesSmall facts your assistant learned or was toldDozens of tokens per factLoaded at session start, or read by a tool
RetrievalDocuments written by someone else, like manualsHundreds of pagesA search tool returns the top chunks

A useful rule: if your assistant writes it, it is a note. If someone else wrote it and it is long, it is retrieved. If it is only needed for the next minute, leave it in the context and let it drop.

Worked example: sorting five facts

The team lists five facts the assistant touches. Where does each live?

  1. "Priya finished vinyl cutter training": the assistant records it, it is small and she will need it later. It is a note.
  2. "The laser cutter's maximum material thickness": written by the manufacturer, in the manual, stable. It is retrieved.
  3. "The laser cutter is booked Thursday 2 pm": it changes all day and the calendar is the source of truth. It is not saved at all; the assistant calls check_calendar each time. A saved copy would go stale.
  4. "Priya prefers morning slots": the assistant could write this as a note, but only if students would expect it. This is a design decision about privacy, not a technical one.
  5. "The student's current question": the context only.

Item 3 is the one teams often miss. Not everything should be remembered: a stale memory is worse than a lookup, because the model will trust what it is shown. This is the same reason you noticed that a chatbot can state an outdated fact with confidence.

One more view: the budget

You were given a small model budget, so end this section with the three levers. First, shrink the fixed part: tighten the system prompt and tool descriptions, because they are sent on every call. Second, shrink what tools return: return chunks, not pages, and stubs for old results. Third, cut the number of calls: each extra step re-sends the whole history, so a workflow that needs three calls beats an exploration that needs eight. The next lessons return to the third lever.

Worked example: spending a budget

Suppose a request averages 5,000 input tokens, and you expect 200 requests a week. How much input is that per week, and what does trimming tool output by a third do?

  1. Weekly input: 200 × 5,000 = 1,000,000 tokens.
  2. Suppose half of each request's input is tool output that could be trimmed by a third: 2,500 × 1/3 is about 830 tokens saved per request.
  3. Weekly saving: 200 × 830 is about 166,000 tokens, roughly 17% of the input.
  4. Multiply by your provider's price per million input tokens to see the money. Prices differ by model, so look them up when you choose one.

This is the kind of back-of-the-envelope estimate you can bring to the design review, and the sponsor can check it.

Worked example: planning the request "Can I use the vinyl cutter Thursday?"

Walk the request through the plan and estimate the cost.

  1. New session: the message list starts as the system prompt (800), tools (600) and the question (20). Add the student's record from the notes store, 40 tokens: the first call has 1,460 input tokens.
  2. The model sees "vinyl_cutter: not trained" in the record. It does not need the calendar yet, so it calls search_manuals("vinyl cutter training") (50 output tokens).
  3. Retrieval returns the top two chunks, 600 tokens in total. Call 2 input: 1,460 + 50 + 600 = 2,110.
  4. The model writes the final answer, "You need the vinyl cutter basics session first; here is how to sign up", in call 2. Two calls, total input 1,460 + 2,110 = 3,570 tokens.
  5. Decision check: the assistant avoided a calendar call and avoided the whole manual, because the right fact was in a note and the rest was retrieved narrowly.

Summary 2 min

  • The model sees only the context your program builds for one call. It keeps nothing between calls.
  • Between steps, your program keeps a message list and re-sends all of it each call, so cost grows with every step and every large tool result.
  • When it fills, clear old tool results or compact by summary, keeping decisions and open items.
  • Between sessions, nothing is kept unless you save a small note and load it into the next context.
  • Retrieval searches a big store and puts only the best chunks in the context; it does not teach the model anything.

Say it in your own words: without looking, explain to a teammate why a 400-page manual should not be pasted into every call, and what you would do instead.
