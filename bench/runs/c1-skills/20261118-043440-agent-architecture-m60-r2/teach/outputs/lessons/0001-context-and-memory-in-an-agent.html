Context and memory in an agent: what it sees, what it keeps, what it can look up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note between sessions, or in a manual it looks up on demand, and give the reason.

Objective O3: context and memory in an agent About 60 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant has to answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three problems are the same problem: deciding what the model sees at each step. This lesson gives you the vocabulary and the decision rules to defend your design at the review.

Warm-up 3 min

Before new material, pull two things out of your head from the agent loop. Try to answer each one before you open the answer. Trying first is what makes the answer stick, even when you get it wrong.

Recall 1

A student asks, "Is the laser cutter free on Friday?" Name the steps of the loop that happen between the question and the final answer, in order.

Check your answer

The model is called with the question and the tool descriptions. It replies with a request to call a tool such as check_calendar. The program runs the tool. The program sends the result back to the model, and the model is called again. This repeats until the model writes a final answer or a limit stops it. Today's lesson zooms in on one phrase: "the result goes back to the model." Exactly what goes back, and what happens to it afterwards, is what context and memory are about.

Recall 2

Who runs the tool: the model or the program around it? And how many times is the model called if it asks for two tools one after the other and then answers?

Check your answer

The program runs the tool; the model only writes a request that names the tool and its arguments. Two tool requests and one final answer is three model calls. Keep that number in mind: every one of those calls is separate, and in a moment you will see why that matters for what the model "remembers" and for what you pay.

The context window: everything the model sees 9 min

Start with an example

Imagine you are a game developer, and your game has an AI shopkeeper that talks to the player. Each time the player speaks, your code builds a text block and sends it to a language model. The model sends back the shopkeeper's reply.

What goes in that text block? Probably the shopkeeper's personality, the list of items for sale, and the last few things the player said. If you leave out the item list, the shopkeeper cannot sell anything, because the model has no other way to know what is in the shop. Whatever is in the block is all the model has.

That text block has a name. The context is the set of tokens included when the model is called to produce a response (Anthropic, Effective context engineering for AI agents). A token is a small piece of text, often a short word or part of a word. The context window is the limit on how many tokens the model can take in at once, the input and its own output together.

You met the word "token" in your first session without a precise meaning. For now, think "about three quarters of a word." The exact number does not matter for design decisions; the order of magnitude does.

What is in an agent's context

For the makerspace assistant, the context at any moment is built from a few kinds of text:

  • The system prompt: your standing instructions, such as "You are the makerspace assistant. Never book a machine for a student without training."
  • The tool descriptions: the name, purpose and parameters of each tool, which is how the model knows what it can call.
  • The conversation so far: the student's messages and the assistant's replies.
  • The tool calls the model has made and the tool results that came back, such as calendar entries or a manual page.

All of it is just text, placed one after another. The model does not see your program, your database, or the booking system. It sees this text and nothing else.

Worked example: what is in the box?

A student writes, "Can I use the 3D printer after school today?" List what is in the model's context on the first call, and what is missing.

  1. The system prompt is in, because your program always puts it first. It holds the role and the rules.
  2. The tool descriptions are in, so the model knows check_calendar, search_manuals and book_machine exist.
  3. The student's message is in, as the first item of the conversation.
  4. No tool results yet, because no tool has run.
  5. Missing: today's date, unless your program put it in the prompt. The model cannot look at a clock. If "today" matters, your program must write the date into the context.
  6. Missing: this student's name and training status, unless your program loaded them. The model has no way to find out who is asking.
  7. Missing: the manual for the 3D printer. It is not in the context, so the model would answer from general patterns it learned in training, and that is how a confident but wrong answer happens.

The rule to take from this: anything the model needs must be in the context, or reachable through a tool.

Why the window matters for two reasons

First, the window is a hard limit. If your text does not fit, the call fails or something must be cut. Second, and more useful for your budget: model usage is billed by tokens, and the tokens you send in count, not only the tokens the model writes. A bigger context is a more expensive call. That is why "put everything in" is not a free default.

A common mix-up

"The model remembers what I told it earlier." It is tempting because chat apps feel that way. In truth the model keeps nothing between calls. If a chat seems to remember your first message, it is because the app sent that message again inside the context. Show it by deleting the first message from what you send: the model will have no idea it existed. This idea comes back strongly in the next section, because it explains both the cost and the memory.

Check yourself

Your assistant answers "How do I change the blade on the band saw?" wrongly, with a plausible but made-up procedure. The band saw manual is on your server. What is the most likely cause?

Show the answer

The third option. Information on your server is invisible to the model until your program or a tool puts it into the context.

What is kept between steps 10 min

Start with an example

Think of a text adventure game that you code yourself. The model is the narrator. After every player move, you call the narrator. If you send only the new move, the narrator has no idea where the player is or what they are holding. To keep the story coherent, you send the whole story so far with every new move.

An agent works the same way. In your first lesson you learned that each step of the loop is a separate model call. Now add the consequence: because the model keeps nothing between calls, the program must send the whole growing history each time. The history is the agent's working memory within one task: the context that carries everything that has happened since the task began.

The loop, with the history growing

Here is the loop in Python-style pseudocode, with the part that matters highlighted in comments:

messages = [
    {"role": "user", "content": student_question},
]

while True:
    reply = call_model(system_prompt, tools, messages)   # the WHOLE list goes in
    messages.append(reply)                               # the model's output is kept
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_name, reply.arguments)  # the program runs the tool
    messages.append(tool_result_message(result))         # the result is kept too

Read it line by line. The list messages is the history. Every pass of the loop adds the model's reply and the tool result to it. Every pass also sends the entire list to call_model. The list only grows. Nothing in this loop ever removes anything, unless you write code that does.

Worked example: counting the tokens sent

The student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The numbers below are made up to show the arithmetic. How many input tokens are sent across all calls?

  1. Fixed part: system prompt plus tool descriptions is 1,500 tokens. The question is 50 tokens. Call 1 sends 1,500 + 50 = 1,550 input tokens. The model replies with a request for check_calendar, 60 tokens.
  2. The calendar tool returns 400 tokens. Call 2 sends the earlier 1,550, plus the 60-token request, plus the 400-token result: 1,550 + 60 + 400 = 2,010. The model replies with a request for search_manuals, 80 tokens.
  3. The manual page returned is 3,000 tokens. Call 3 sends 2,010 + 80 + 3,000 = 5,090. The model replies with a request for check_training_record, 60 tokens.
  4. The record is 150 tokens. Call 4 sends 5,090 + 60 + 150 = 5,300. The model writes the final answer, 120 tokens.
  5. Add the inputs: 1,550 + 2,010 + 5,090 + 5,300 = 13,950 input tokens. The final context holds only about 5,420 tokens, yet you were billed for roughly two and a half times that in input, because early content was sent again on every call.

The lesson: the cost of an agent run is not "the size of the final context." It grows faster, because every step pays for everything before it. Long manual pages that stay in the history are paid for again at each later step.

Providers offer a feature called prompt caching, which can make repeated early content cheaper; Anthropic's retrieval article cites it as a way to reduce cost and latency (Contextual Retrieval). It reduces the price of the repeat; it does not remove the context's size limit or its other problems, which come next.

What the program decides to keep

Because the history is just a list that your program holds, you decide what stays in it. That is a design power. Three simple choices exist for each item in the history:

  • Keep it as it is. Safe, but costly if it is large.
  • Shrink it. Replace a big tool result with a short note about what mattered in it.
  • Drop it. Remove it if it will never matter again.

Section 3 shows when to use each.

A common mix-up

"A step in the loop only costs what that step adds." It is tempting because each tool result looks small on its own. But each call re-sends the whole history, so a 3,000-token manual page returned at step 3 is paid for at step 4, step 5 and every step after, for as long as it stays in the list. Check by adding up the input tokens, as above.

Check yourself

Your assistant needs six model calls to book a machine. A search tool returns a 2,000-token manual page at call 2, and the page stays in the history. At which calls is that page sent to the model as part of the input?

Show the answer

Calls 3 to 6: four times, 8,000 input tokens for that single page. The fix, if the page is only needed once, is to shrink or drop it after use.

When the context gets too big 10 min

Start with an example

Picture a game with a long save file. Early in the game the save loads in a blink. After forty hours it holds thousands of items, most of which you never look at, and loading is slow. A good game designer prunes: old quest logs are summarized, dropped items are removed.

An agent's history is a save file that never gets pruned unless you write the pruning. And the problem is worse than speed and cost, because the model itself does worse with a bloated context.

Context rot and the attention budget

Anthropic describes context rot: as the number of tokens in the context grows, the model's ability to accurately recall information from it tends to decrease. The effect is gradual, not a sudden cliff. Anthropic's advice follows from it: treat context as a finite resource with diminishing returns, and aim for the smallest set of high-signal tokens that gets the job done (Anthropic, Effective context engineering).

The article also uses the phrase attention budget: each new token uses up some of the model's limited ability to focus. A useful way to hold it: a bigger window is a bigger desk, but the person at the desk still has only two eyes.

A common mix-up

"If the window is big enough to hold everything, I can stop managing context." It is tempting because a large window sounds like a large memory. But fitting is not the same as working well: recall tends to get worse as the context fills, and every extra token is paid for on every call. A bigger window removes the hard limit; it does not remove the need to choose what goes in.

Three tools for managing the history

The same article describes techniques for tasks that run long. Here are the three that matter for your assistant, from lightest to heaviest.

  1. Clearing old tool results. Once the model has used a tool result, the raw output rarely needs to stay. Anthropic calls tool result clearing one of the lightest forms of compaction.
  2. Trimming old messages. Drop the oldest turns of the conversation and keep the recent ones. LangChain's memory documentation describes trimming or deleting stale messages when a conversation exceeds the window (LangChain, Memory).
  3. Compaction: when the conversation nears the limit, ask the model to summarize it, then start a fresh context that holds the summary. Anthropic says Claude Code keeps the architectural decisions, unresolved bugs and implementation details, and discards redundant tool output.
Worked example: clearing a tool result

Return to the run from section 2. At call 4 the context holds the 3,000-token manual page. Does the model still need the whole page?

  1. Look at what the page was for. The model searched the manuals to learn whether the laser cutter needs training. The answer was one sentence on that page.
  2. Your program replaces the page in the history with a note of about 100 tokens: "Laser cutter manual, p. 14: users must hold safety training level 2 before using the machine."
  3. Call 4 now sends 5,300 − 3,000 + 100 = 2,400 input tokens instead of 5,300. That is a saving of 2,900 tokens on that call alone, and the same saving on every later call.
  4. Is anything lost? Possibly. If the student next asks, "What did the manual say about ventilation?", the page is gone. The model would have to search again. That is the trade: clearing saves tokens and risks losing a detail that matters later.
  5. So decide by asking, "Will the model need the raw text again?" For a page it can fetch again with a tool, clearing is cheap insurance. For something that exists nowhere else, such as what the student said they wanted, keep it or write it down.

Compaction in plain words

Suppose a student chats with the assistant for forty turns while planning a project: choosing a machine, comparing materials, checking times. The context is huge. Compaction replaces those forty turns with a short summary.

Here is what a good summary might hold for this case:

Summary of the conversation so far:
- Student: Priya, wants to laser-cut a 3 mm birch plywood lid.
- Decided: use the laser cutter, not the CNC router.
- Open question: whether she can book Thursday 3-5 pm.
- Constraint she mentioned: she must finish by Friday.

The summary keeps decisions, open questions and constraints, and drops the chit-chat and repeated tool output. Anthropic's tuning advice is to make the summary keep everything relevant first, and trim the extras second; an over-aggressive summary can drop a detail that matters later (Anthropic, Effective context engineering).

Compaction costs a model call of its own, since a model writes the summary. It pays off when the conversation is long; for a short makerspace question it would not be worth it.
Your turn: clearing, with the steps faded

A run sends these input sizes: call 1 is 1,200 tokens; call 2 is 1,800 tokens; call 3 is 4,300 tokens, because a 2,400-token manual page arrived after call 2; call 4 would be 4,500 tokens if nothing were removed. Your code clears the manual page after call 3 and replaces it with a 100-token note. Step one is done: call 4 loses the page, which is 2,400 tokens. Work out how large call 4 is now, and how many tokens the clearing saves over calls 4 and 5, if call 5 would have been 4,700 tokens before clearing.

Show a solution

Call 4 is 4,500 − 2,400 + 100 = 2,200 tokens. Call 5 is 4,700 − 2,400 + 100 = 2,400 tokens. The saving per call is 2,300 tokens (the 2,400-token page minus the 100-token note), so over calls 4 and 5 it is 4,600 tokens. The longer the run goes on, the more a single clear is worth, which is why clearing big, already-used results is the first thing to try.

Choosing among the three

SituationBest first moveWhy
One huge tool result already usedClear it, keep a short noteCheap, no extra model call, and the page can be re-fetched

Between sessions: nothing is kept unless you save it 9 min

Start with an example

When you quit a game without saving, you start from the beginning next time. The game console does not guess what you did. The save file is something the game deliberately wrote to disk and then deliberately read back at launch.

A session is one conversation or task, from the first message to the last. When it ends, the context is gone. The next session starts with an empty context holding only your system prompt and tool descriptions. That is the second thing a language model does not do: it does not carry anything from one session to the next. This matters for your mission, because the assistant has to remember each student's training status between visits.

Two kinds of memory, named

LangChain's memory documentation splits agent memory by how long it lasts (LangChain, Memory):

  • Short-term memory is scoped to one conversation, which they call a thread. It is the message history you met in section 2, saved so that the same conversation can continue.
  • Long-term memory persists across conversations. It stores user-specific or application-level data across sessions, and can be recalled in any later thread.

Notice that neither one lives inside the model. Both are data your program stores, such as a list in a file or a row in a database. Memory in an agent is an engineering feature you build around the model, not something the model grows by itself.

A common mix-up

"The assistant learns from every conversation, so it will remember Priya next week." It is tempting because people learn from conversations, and chatbots use the word "memory." The model's trained knowledge does not change when you talk to it. If Priya is remembered next week, it is only because your program saved something about her and put it back into the context. No saving code, no remembering. This is the same point as the automatic-memory idea in quiz 0001: memory is never automatic.

Three types of long-term memory

The same documentation borrows three names from psychology. They help you decide what to save:

TypeWhat it holdsMakerspace example
SemanticFacts"Priya has completed laser cutter training."
EpisodicPast experiences, often used as examples"Last time a student asked for a two-hour slot on a busy day, this wording worked."
ProceduralRules for how to act"Always confirm the time zone before booking." Often kept in the system prompt.

For the makerspace assistant, semantic memory is the first priority: a few facts per student. Episodic and procedural memory can wait.

Worked example: what to save about a student

Priya finishes a session in which she passed laser cutter training and mentioned she prefers afternoon slots. Decide what to save for next week.

  1. List the candidate facts: "Priya passed laser training," "Priya prefers afternoons," "Priya asked about birch plywood," "Priya said hello."
  2. Ask of each: will it change a future answer? Training status decides whether booking is allowed, so it matters a lot. Afternoon preference changes which slot to suggest, so it matters somewhat. Plywood might matter but is shallow. "Said hello" never matters.
  3. Ask of each: is it a fact that could go stale? Training status can change when a certification expires, so it needs a date. Preferences drift, so they need a date too.
  4. Write the record as structured data your program can read: 
    {"student": "priya",
 "trainings": {"laser_cutter": "2026-11-17"},
 "preferences": {"slots": "afternoon"}}
  5. Next week, at the start of the session, your program loads the record and writes it into the context. Only then can the model "remember" her.

Notice step 4: the saving and the loading are both code you write. The model is not part of either step unless you give it a tool for it.

Check yourself

It is Monday. On Friday, a student told the assistant their major, and today the assistant greets them with it. Which explanation is correct?

Show the answer

The first option. Whatever the assistant knew on Monday, your code put there.

Notes as memory 9 min

Start with an example

In many role-playing games there is a quest journal. The game does not expect you to remember every promise from forty hours ago, so you write them down in the journal and consult it when you need it. The journal is outside your head, but you can read it any time.

Anthropic describes the same idea for agents and calls it structured note-taking: the agent regularly writes notes to storage outside the context window, and reads them back into the context later (Anthropic, Effective context engineering). Their examples include Claude Code writing a to-do list, a custom agent keeping a NOTES.md file, and Claude playing Pokémon, which kept notes on training progress and on maps of places already explored, then read its notes after the context was reset and carried on.

This is the same machine as long-term memory from section 4. A note is simply a saved piece of memory, written in text the model can read.

How an agent uses notes: a tool in each direction

The model cannot touch a file on its own, as you learned from the loop. So notes need two tools, one to write and one to read:

def save_note(student_id: str, note: str) -> str:
    """Save one short fact about a student for future visits.
    Use only for facts that will matter later, like completed training."""
    notes = load_json(f"notes/{student_id}.json", default=[])
    notes.append({"note": note, "date": today()})
    save_json(f"notes/{student_id}.json", notes)
    return "saved"

def read_notes(student_id: str) -> str:
    """Return all saved notes about a student."""
    return str(load_json(f"notes/{student_id}.json", default=[]))

Look at what each important part does. The function name and its docstring are what the model reads when choosing a tool, as you saw in quiz 0001. The body is code your program runs; the model never sees it. The dates are there so the model can judge how old a note is.

There is a second way to use notes that needs no tool: your program loads the student's notes at the start of every session and places them in the system prompt. The model does not choose to read them; they are simply there. For a small number of short notes, this is simpler and more reliable.

Worked example: one student's second visit

Priya returns. Trace what happens, step by step, with notes loaded at session start.

  1. Priya logs in. Your program knows her ID from the login, not from the model.
  2. The program reads notes/priya.json and builds the system prompt: the fixed rules, then a section "What we know about this student: laser cutter training completed 2026-11-17; prefers afternoon slots."
  3. She asks, "Can I book the laser cutter Thursday?" Call 1 sends the system prompt (with her notes), the tools and her question.
  4. The model sees the training note, so it skips asking whether she is trained. It requests check_calendar for Thursday afternoon, using her preference.
  5. The loop continues as before: the result comes back, the model offers a slot, she confirms, and book_machine runs.
  6. At the end, the model calls save_note with "booked laser cutter Thursday 3 pm." The next session will see it.

Compare with no notes: the assistant would ask about training again every visit, which is exactly the kind of waste and annoyance your sponsor would notice.

When to write: during the answer or afterward

LangChain's documentation describes two timings for writing memory (LangChain, Memory):

  • In the hot path: the agent writes the memory while it handles the request. New memory is available immediately, but reasoning about what to save can add delay.
  • In the background: a separate task writes memories after or beside the conversation. It adds no delay to the answer, but updates arrive later, so another conversation may not see them yet.

Pick by asking how soon the fact must be visible. If a student completes training and tries to book a minute later, a background job that runs every night would wrongly refuse them.

A common mix-up

"A saved note is the truth." It is tempting because a note feels official. But a note is a copy: it was true when written, and it can go stale or be wrong. If a student's training expired last month, an old note saying "trained" would let an unsafe booking through. For facts with consequences, such as safety training, keep the authority in your real records and give the model a tool to check them. Use notes for helpful, low-stakes context like preferences. This is a design judgment, and your review will probably ask about it.

Check yourself

Show the answer

Retrieval: finding the right page 10 min

Start with an example

In a big open-world game you do not load the entire world into memory. The game loads the chunk around the player and fetches the next chunk as they move. It keeps a map index so it knows where each chunk is.

Your assistant has the same problem with manuals. They are far too long to put in the context at every step, and most pages are irrelevant to any one question. Retrieval means fetching only the relevant pieces of a large body of text and putting them into the context. When retrieval feeds a model's answer, the pattern is called retrieval-augmented generation, or RAG: retrieve relevant information from a knowledge base and append it to the prompt (Anthropic, Contextual Retrieval).

Step one: should you retrieve at all?

Before building anything, check the size. Anthropic's article says that if the knowledge base is smaller than 200,000 tokens, roughly 500 pages, you can simply include the whole thing in the prompt, and prompt caching can make that faster and cheaper (Contextual Retrieval). Below that size, retrieval may be extra machinery you do not need.

That is about 400 tokens per page by their own figures. Hold on to that rate for the next example.

Worked example: do the manuals need retrieval?

The makerspace has 6 machines, and each manual is about 40 pages. Is retrieval needed, and what does it cost the budget?

  1. Total pages: 6 × 40 = 240 pages.
  2. Total tokens, at about 400 tokens a page: 240 × 400 = 96,000 tokens.
  3. Under 200,000, so the whole set fits. Fitting is not the same as good: recall tends to fall as context grows (section 3), and the cost is paid on every call.
  4. Cost of putting everything in, over a four-call run, without caching: about 4 × 96,000 = 384,000 input tokens for the manuals alone. Caching would cut the price of the repeats, but you would still be tied to the large context.
  5. Cost of retrieval: fetch three pieces of about 400 tokens each, 1,200 tokens, and send them in the calls after they are fetched. That is a few thousand tokens in total.
  6. Decision: for the prototype with one or two manuals, put them straight in the prompt and measure. As the set grows, or if answers drift, add retrieval. State the reason to your team: "the manuals fit, but retrieval is cheaper per request and keeps the context small."

How retrieval works, in four steps

  1. Chunk: split each manual into pieces, usually no more than a few hundred tokens each.
  2. Index: store each chunk so it can be searched.
  3. Search: turn the student's question into a search and find the best-matching chunks.
  4. Place: put the top few chunks into the context, with the source (machine and page), so the model can answer from them and cite them.

How the search finds chunks: two methods

Anthropic's article describes the two common search methods and why they are used together (Contextual Retrieval):

  • Embeddings: a separate embedding model turns each chunk into a list of numbers that encodes its meaning, so the search finds chunks that are about the same thing as the question, even if the words differ. You do not need the math for your design.
  • BM25: a ranking function that uses lexical matching, finding chunks that share the exact words or phrases. It is strong on unique identifiers and technical terms.

Each one misses things the other catches. Embeddings can miss exact matches, such as a specific error code. Combining the two gives better coverage than either alone.

Worked example: which method catches which question?

Two students ask questions. Decide which search method is the safer bet for each.

  1. Question A: "The laser keeps stopping and shows E-42." The key piece is the exact code "E-42." A meaning search might return generic troubleshooting. BM25 matches the exact token, so it is the safer bet.
  2. Question B: "My cut edges look burnt, how do I fix that?" The manual might say "scorching" and "reduce power or increase speed" without the word "burnt." Matching words alone could miss it. An embedding search matches the meaning, so it is the safer bet.
  3. You cannot know in advance which kind of question will come, so a combination is wise: run both searches and merge the results.
  4. Place the top few chunks in the context, labeled "Laser cutter manual, p. 22."

Chunks can lose their context

A chunk is cut out of its page, and can lose what it was about. The article's example is a chunk reading "The company's revenue grew by 3% over the previous quarter," which does not say which company or period. Anthropic's fix, called Contextual Retrieval, adds a short explanation of roughly 50 to 100 tokens to the front of each chunk before indexing; they report that this, with a hybrid of embeddings and BM25, cut failed retrievals by 49%, and by 67% when a reranking step was added (Contextual Retrieval).

You can get most of the benefit for manuals cheaply. A makerspace manual chunk that says "Set power to 60% and speed to 20 mm/s" is useless if it does not say which machine or which material. Put the machine name, the section title and the page number at the front of every chunk when you build the index.

Worked example: labeling a chunk

The CNC router manual contains the sentence "Set the feed rate to 800 mm/min and the spindle to 12,000 rpm." Make this chunk findable and safe to use.

  1. Read the sentence alone. It does not say which machine, which material or which operation, so a search could return it for a laser cutter question, and the model could repeat the numbers for the wrong machine.
  2. Find what the surrounding page says. Suppose the heading is "Cutting 6 mm plywood" in the CNC router manual, page 31.
  3. Write a short label of about one line and put it in front of the chunk: "CNC router manual, p. 31, section: Cutting 6 mm plywood."
  4. Index the labeled chunk. A search for "CNC plywood speed" now matches on words (CNC, plywood) and on meaning.
  5. When the chunk reaches the context, the label travels with it, so the model can cite "CNC router manual, p. 31" and the student can check the page.

Cost: one line of text per chunk, written once when you build the index. Benefit: fewer wrong-machine answers, which in a makerspace are a safety problem, not only an annoyance.

Two ways to retrieve: before the call, or during it

Anthropic contrasts two timings. In pre-inference retrieval, chunks are fetched before the model is called, as above. In just-in-time retrieval, the agent holds light references such as file paths, saved queries or links, and loads data when it needs it, by calling tools; the model can also read folder names and file names as hints. The trade-off they note: just-in-time exploration is slower, and it needs good guidance so the agent does not waste context wandering. Some systems combine the two, loading a small amount up front and exploring the rest on demand (Anthropic, Effective context engineering).

For your assistant, retrieval fits naturally as a tool: search_manuals(machine, question). The model decides when to call it, as in the loop, and the result goes into the context like any tool result. That makes it just-in-time, and then the clearing from section 3 keeps the history small.

Worked example and practice: design the assistant's memory 12 min

Now put the three layers together. You have context (what the model sees now), saved notes (what persists between sessions) and retrieval (what it looks up). The skill is sorting each piece of information into the right place.

The sorting questions

For any piece of information, ask these in order:

  1. Is it needed on every request? Then it goes in the system prompt, as a fixed part of the context.
  2. Is it about this student and needed across sessions? Then it is a saved note, loaded at session start or read by a tool.
  3. Is it a large body of reference text, of which only a small piece matters per question? Then it is retrieved, ideally by a tool.
  4. Is it only needed for this task? Then it stays in the history, and gets cleared or compacted when it is no longer needed.
  5. Does a wrong or stale copy cause harm? Then do not trust a copy: check the real record with a tool.
Worked example: sorting the assistant's information

Sort these five things into the right place and give the reason.

  1. "Never book a machine for an untrained student." Needed on every request, and it is a rule, so it goes in the system prompt (question 1). It costs a few tokens per call, which is cheap for a rule that guards safety.
  2. The laser cutter manual. Large, and only a page or two matters per question, so it is retrieved (question 3), through a search_manuals tool. The results are cleared from the history after use.
  3. "Priya prefers afternoon slots." About a student, across sessions, low stakes: a saved note (question 2), loaded into the prompt at session start.
  4. "Priya is trained on the laser cutter." It is about the student and is needed across sessions, but a wrong copy causes harm if the training has expired, so it is checked with a tool against the real training record (question 5), not trusted from a note.
  5. The calendar result for Thursday. Needed only for this task and it goes stale fast, so it stays in the history only until the booking is made, then it is cleared (question 4). It is never saved as a note, since tomorrow it may be wrong.

Notice that no single place holds everything. A good design puts each piece where it is cheapest and safest.

A second, harder case

Worked example: a long booking chat

A student spends 30 turns booking equipment for a group project: three machines, five people, two days. By turn 30 the context holds about 40,000 tokens, most of it old manual pages and calendar results. What do you do?

  1. Find the biggest items. Manual pages and calendar results are large and already used. Clear them first, leaving one-line notes of what they said. This costs nothing in extra model calls.
  2. Check what is left. The conversation turns hold decisions: which machines, which people, which slots. These matter.
  3. If it is still large, compact: ask the model for a summary of decisions, open questions and constraints, and start a fresh context from it.
  4. Write the final bookings to the real booking system, which is the source of truth, not into a note.
  5. At session end, save one note: "Priya organizes the group project; prefers afternoons." That is what will help next time.
Your turn: faded token count

A short run has these made-up numbers. System prompt plus tools: 1,000 tokens. Question: 100 tokens. The first model reply is a 50-token tool request, and its result is 500 tokens. The second reply is a 50-token tool request, and its result is 2,000 tokens. The third reply is the final answer of 100 tokens. How many input tokens are sent in total? Step one is done: call 1 sends 1,000 + 100 = 1,100.

Show a solution

Call 2 sends 1,100 + 50 + 500 = 1,650. Call 3 sends 1,650 + 50 + 2,000 = 3,700. The total input is 1,100 + 1,650 + 3,700 = 6,450 tokens. If the 2,000-token result had been clearable, but was needed only once, you could not save anything on call 3 (it is the last call and needs the result), but if the run had gone on, each later call would have saved 1,900 tokens by replacing it with a 100-token note.

Summary 3 min

  • The model sees only its context: the system prompt, tool descriptions, history and tool results. It keeps nothing between calls and nothing between sessions.
  • Between steps, your program re-sends the whole history, so cost grows faster than the final context size, and a bloated context makes recall worse. Clear, trim or compact to manage it.
  • Between sessions, memory exists only because your program saves data and loads it back. Notes are that saved data, written at the right time, and not trusted blindly when a stale copy would do harm.
  • Retrieval fetches only the relevant pieces of long text. Chunk with labels, combine meaning search and word search, and skip retrieval if the whole text is small enough.
