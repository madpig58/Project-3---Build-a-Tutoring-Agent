Context and memory in an agent

By the end of this lesson you can look at any piece of information in the makerspace assistant and decide where it lives: in the context window, in a saved note, or in the manuals to be retrieved, and say what each choice costs.

Before new material, pull something out of your own head. Retrieving it is what makes it stick.

Check your answer

The model is given the question and a list of tools. It asks for one action, for example check_calendar for the laser cutter and tomorrow's date. The program runs the tool and sends the result back to the model. The model asks for the next action, perhaps check_training_record. Today we zoom in on one word in that description: "sends the result back". Back into what? That place is the context window, and the whole lesson is about what goes into it and what stays out.

If you could not name the stopping condition, that is worth a second look after this lesson. It comes back in section 2, because a loop that never stops also fills the context window.

The context window: everything the model sees 8 min

A concrete example first

Think of a game engine. A game keeps the current level, the nearby enemies and the player's stats in RAM, the fast working space the game can use right now. Everything else sits on disk until it is needed. If the game tried to load the whole world into RAM at once, it would stall or crash.

A language model has something like RAM too. It is called the context window: all the text the model can look at when it writes a response, including the response itself. Anthropic's documentation describes it as the model's "working memory", and says it is different from the large body of text the model was trained on (Claude docs: Context windows).

The game analogy is ours, not the docs'. It is useful for the shape of the idea, but a model's window is not a literal RAM chip: it is just the text you send in with each request.

What counts as context

Context is measured in tokens: small chunks of text, usually a short word or a piece of a longer one. Very roughly, a page of a manual is somewhere around several hundred tokens. Providers count tokens because the window has a limit, and because usage is billed by the token.

The docs list what counts toward the window. Everything in the request counts: the system prompt, every message including tool results, and your tool definitions. The output the model writes counts too (Claude docs: Context windows).

Notice the tool definitions. The descriptions you write for check_calendar and search_manuals are not free. They ride along in every single request, so a long, wordy tool description costs you on every step.

The model keeps nothing on its own

Here is the idea that most surprises people. Each request to the model starts fresh. The docs describe each turn as an input phase, which contains all previous conversation history plus the new message, followed by an output phase. The reply becomes part of the input for the next turn (Claude docs: Context windows).

So the "memory" of a conversation is not inside the model. It is a list of messages that your program keeps, and resends in full, each time.

A common mix-up

"The model remembers what we said earlier." It is tempting because chat apps feel that way: you say your name, and three messages later it uses it. But the app resent your earlier messages with the new one. Delete the name from the list the program sends, and the model has no trace of it. The model is the same before and after; only the text in front of it changed.

Worked example: a game NPC with no memory

You write a shopkeeper character powered by a model. The player says, "Hi, I'm Mira." The shopkeeper replies, "Welcome, Mira!" The player then says, "What was my name?" Will the shopkeeper know?

  1. Request 1 contains the system prompt (the shopkeeper's personality) and the message "Hi, I'm Mira." The model writes "Welcome, Mira!"
  2. Your program appends both lines to its message list. This is the only place the name is stored.
  3. Request 2 is built from that list: system prompt, "Hi, I'm Mira.", "Welcome, Mira!", then "What was my name?" The model can read the name, so it answers correctly.
  4. Now suppose a bug makes your program send only the newest message: "What was my name?" The model sees no name anywhere, so it can only guess or say it does not know.
  5. Conclusion: the shopkeeper "knew" Mira only because the name was in the context. Memory in an agent means "what the program puts back in front of the model".

More context is not automatically better

If the window can hold up to 1M tokens on many current models, why not put everything in? The same docs warn that more context is not automatically better. As the token count grows, accuracy and recall degrade, a phenomenon they call context rot (Claude docs: Context windows).

Anthropic's engineering team frames context as a finite resource with diminishing returns. Every new token uses up part of an "attention budget". Their goal is the smallest set of high-signal tokens that still gets the job done (Anthropic: Effective context engineering for AI agents).

Think of it as a desk. A bigger desk lets you spread out more papers, but you still find things faster on a clean desk. And in your project there is a second reason to keep it clean: you pay for every token on the desk, at every step.

Worked example: what you pay for a tool description

Your team writes a very long description for each of 6 tools, 300 tokens each. How much of the window do the tool definitions use before any user text arrives?

  1. Multiply: 6 tools × 300 tokens = 1,800 tokens.
  2. These tokens are in the request every time the model is called, not once per conversation.
  3. A request that takes 4 model calls therefore sends them 4 times: 7,200 tokens of tool text, just for one student question.
  4. If a clear 100-token description would do, that is 600 tokens per request, 2,400 over four calls, and 4,800 tokens saved.
  5. Lesson: write tool descriptions that are clear and short, not long. Clear matters most, but trimming the filler is free.
Worked example: will it fit, and is it worth it?

A designer on your team suggests pasting the booking rules (4,000 tokens), a policy handbook (30,000 tokens) and the laser cutter manual (40,000 tokens) into the system prompt "so the model always knows". Test the idea step by step.

  1. Add the pieces: 4,000 + 30,000 + 40,000 = 74,000 tokens before any student has asked anything.
  2. Does it fit? On a model with a 1M-token window, yes, easily. So the limit is not the problem.
  3. Now count the calls. A request with 4 model calls sends the 74,000 tokens 4 times: 296,000 tokens, before the question, tool results or answers.
  4. Ask how much of it a typical question needs. A thickness question needs one paragraph. The other 73,000+ tokens are noise the model must read past, which is what the context-rot warning is about.
  5. Decision: keep the 4,000 tokens of booking rules in the prompt, because every request needs them. Move the handbook and manuals to a searchable library. Fit is not the test; value per token is.
Check yourself

The second option. Every call is a separate request that carries the system prompt, so it occupies the window and counts as input in each of the 5 calls. Prompt caching can change the price, but not the fact that it occupies the window.

What is kept between steps 10 min

The loop adds to the pile

Now put section 1 together with the agent loop. Each step of the loop is a separate call to the model. After each call, the program adds two things to the message list: the model's request for a tool, and the tool's result. Then it calls the model again with the whole list.

That means everything from earlier steps is kept, in order, and every later call re-reads it. The loop does not forget between steps. It also never shrinks by itself.

A worked example with numbers

Let us trace the request "Is the laser cutter free tomorrow, and do I need training?" with invented but plausible sizes. The system prompt, the tool definitions and the question together take 2,550 tokens. Each tool request the model writes takes 60 tokens.

Worked example: adding up the cost of one request

The tools return: check_calendar, 300 tokens; search_manuals, 3,000 tokens (a whole manual page); check_training_record, 100 tokens. The final answer is 150 tokens. How many input tokens does the model read across all four calls?

  1. Call 1 reads the starting text: 2,550 tokens. The model writes a 60-token request for check_calendar.
  2. The calendar result (300 tokens) is added. Call 2 reads 2,550 + 60 + 300 = 2,910 tokens. The model asks for search_manuals (60 tokens).
  3. The manual page (3,000 tokens) is added. Call 3 reads 2,910 + 60 + 3,000 = 5,970 tokens. The model asks for check_training_record (60 tokens).
  4. The training result (100 tokens) is added. Call 4 reads 5,970 + 60 + 100 = 6,130 tokens and writes the 150-token final answer.
  5. Add the inputs: 2,550 + 2,910 + 5,970 + 6,130 = 17,560 tokens read, plus 330 written (60 + 60 + 60 + 150).
  6. Notice the shape: the new information in this request is only about 3,500 tokens, but the model read 17,560, because the big manual page was re-read by call 3 and call 4.
A common mix-up

"A bigger context window fixes this." It is tempting, because a larger window means the pile cannot overflow. But a bigger window does not stop the pile from growing: you still re-read and re-pay for every old token at every step, and the docs warn that recall degrades as the token count rises. Room is not the same as value.

Check yourself

In the trace above, why does call 4 cost more input tokens than call 2, even though the model only asks for a tiny 100-token result before call 4?

Show the answer

Call 4 resends all earlier steps and results. The tiny 100-token result is not the reason; the big manual page from call 3 is still in the list.

Keeping the pile small

Anthropic's engineering post describes the lightest fix as clearing old tool results. Once the agent has acted on a raw result, it rarely needs the raw text again. The next step up is compaction: when a conversation nears the window limit, summarize it and start a fresh window with the summary. Their example keeps architectural decisions and unresolved bugs, and drops redundant tool output (Anthropic: Effective context engineering for AI agents).

The Claude docs offer both as features: server-side compaction for long conversations, and context editing to clear old tool results (Claude docs: Context windows). You can also do a basic version yourself in plain Python, by trimming a result before you append it to the list.

Prompt caching can lower the price you pay for repeated tokens, but the docs say cached prompt prefixes still occupy the context window. Caching changes what you pay, not whether the tokens count.
Worked example: compaction by hand

A coding helper for your booking script has run 40 steps. Its history holds 60,000 tokens, mostly raw test output. You compact it. What goes in the summary?

  1. Start with what the next step needs: the goal ("fix double-booking bug"), the current guess ("the date comparison ignores time zones"), and what was already tried and failed.
  2. Keep key facts: the file names that matter, and the one failing test with its error line.
  3. Drop the raw output: 38 repeats of the same stack trace say nothing new.
  4. Write all this in about 500 tokens. Start a new window with the system prompt, tools and this summary.
  5. Check what you lost. If the model now keeps repeating a failed fix, the summary dropped the "already tried" list. Put it back. Anthropic's advice is to first make sure the summary recalls everything important, then trim it for precision.
Worked example: clearing a result after use

The same request as before, but now your program clears the manual page from the history as soon as the model has read it and written down what it needs. Does this help, and what is the risk?

  1. Call 3 still reads the 3,000-token manual page, because the model has to see it once to use it: 5,970 tokens.
  2. The model then writes its next request, and the program replaces the page with a short stub, for example "[manual page 14 removed: max acrylic 10 mm]", about 30 tokens.
  3. Call 4 reads 2,910 + 60 + 30 + 60 + 100 = 3,160 tokens, instead of 6,130. (The extra 60 is the model's request for the training check, which sits in the history too.)
  4. The saving grows with every later call. In a long task with 20 more calls, that is 20 × roughly 3,000 tokens saved.
  5. The risk: if the model needs the page again, it is gone. The stub must keep the facts that matter, and the model must be able to fetch the page again with the search tool.
Your turn: compare two fixes

Your assistant has used 80,000 tokens of window in a long booking chat, mostly old calendar results. One option is to clear the old results. The other is to summarize the whole chat into 800 tokens and continue. Which loses less detail, which saves more, and when would you choose each?

Show a solution

Clearing old results keeps the conversation and the model's own words, and only removes bulky raw output, so it loses the least. Summarizing saves much more, here about 79,000 tokens, but it can lose details the summary did not mention. Choose clearing when most of the bulk is raw tool output that has already been used. Choose summarizing when the conversation itself is long and the history has become the bulk. Many systems do both, clearing first and compacting only when that is not enough.

Why a step limit still matters

A loop that never stops does two things at once: it burns money and it fills the window. A step limit, which the program enforces, is the safety net. Context tricks make each step cheaper; the limit decides how many steps are allowed.

What is kept between sessions: notes as memory 10 min

The default is nothing

A session here means one conversation: one list of messages, from the first question to the end. When the student closes the chat, your program throws that list away unless you save it. Next week, a new session starts with an empty list.

The model is the same, but the text in front of it is new. Nothing about the earlier visit survives by default.

Save files, as a game does

Back to the game. When you quit a game, RAM is cleared, but the save file on disk stays. Next time, the game loads the save file back into RAM. An agent works the same way. The program writes what matters to storage outside the context window, and loads the relevant part back into the context at the start of the next session.

Anthropic calls one version structured note-taking, or agentic memory: the agent writes notes outside the context window and pulls them back in later. Their example is Claude playing Pokémon: it tracked its progress across thousands of steps, such as levels gained toward a target and which regions it had explored, and could carry on after its context was reset (Anthropic: Effective context engineering for AI agents).

The memory tool: memory as just another tool

You do not need a new idea to build this. Anthropic's memory tool lets the model store and retrieve information across conversations through a directory of memory files. It works like any other tool: the model requests a file operation, and your application runs it. The docs say that the tool operates client-side, so memory lives entirely in your application and you control where it is stored (Claude docs: Memory tool).

When the memory tool is on, the API adds an instruction to the system prompt telling the model to view its memory directory before doing anything else. It also tells the model to assume its context might be reset at any moment, so progress should be recorded as it goes (Claude docs: Memory tool).

A common mix-up

"The model learns from the student and stores it inside itself." It is tempting, because "memory" sounds like something in the model's head. But the model's learned patterns are fixed after training, and a conversation does not change them. What persists is a file or database row that your program wrote, which you can read, edit, expire or delete.

Worked example: remembering a student's training

On Monday Sam completes laser-cutter safety training with a staff member. On Wednesday Sam opens a new chat and asks to book the laser cutter. Trace how the assistant knows.

  1. Monday: the staff member marks Sam as trained. Your program, not the model, writes a note: /memories/sam/training.md containing "Laser cutter: trained 2026-11-16".
  2. Monday's chat ends. Its message list is thrown away. The model has not changed at all.
  3. Wednesday: a new session starts with an empty list. The program identifies Sam and makes the memory tool available.
  4. The model's first action is view /memories/sam. The program reads the folder and returns the file names as a tool result.
  5. The model views training.md, now sees "trained", and goes ahead to check the calendar and book.
  6. Notice what is not there: Monday's whole conversation. Only the note moved across. A small note is much cheaper to reload than a full transcript.
Check yourself

Sam's training note is saved. On Wednesday, which statement is true about where that fact lives and who reads it?

Show the answer

The first option. The note is in storage that your application controls, and the model gets it only when it asks for the file and your program returns the content.

What a notes file looks like

A note is just text. There is no magic format, so make it easy for a model, and for you, to read. Here is a possible file for one student. Look at what each line is for.

# Sam R. (student 4471)
updated: 2026-11-18

## Training
- laser cutter: trained 2026-11-16 (staff: J. Ortiz)
- 3D printer: not yet trained

## Preferences
- prefers room B printer
- usually books afternoons

The header says whose file it is and when it was last updated. Training is separated from preferences, so the model reads the part it needs. Every training line has a date and a source, so a person can check it. If a line may go out of date, the date tells you when to review it.

Worked example: a note that goes stale

Sam's file says "3D printer: not yet trained". On Thursday Sam finishes the printer training. Trace what should happen.

  1. Staff marks the training complete in the booking system. This is the real source of truth.
  2. If the assistant only trusted its notes, on Friday it would still tell Sam "you are not trained". The note is now wrong.
  3. Fix 1: update the note when training changes. The model uses the memory tool's str_replace command to change one line, or your program rewrites the file.
  4. Fix 2: for facts that already have an official system, such as training records, have the assistant call a tool for the record instead of trusting a copy. Use notes for things that have no other home, such as preferences.
  5. Rule: a note is a copy. Decide, for each fact, whether a copy is safe, and how it will be kept up to date.
Check yourself

Which fact is the best candidate for a saved note, rather than a fresh tool call each time?

Show the answer

The last option. A preference has no other system that holds it, it changes slowly, and a stale copy does little harm. The other three are better served by a tool call or the library.

Design questions for any memory

The docs give a few responsibilities that fall on you, because your application runs every operation. Validate every file path so the model cannot reach files outside the memory folder; the docs warn about "path traversal" attacks. Cap how large files can grow. Delete notes that have not been used in a long time. And consider what personal information you are storing, because students' training records are personal (Claude docs: Memory tool).

For your team, the privacy point is a real design-review topic: store the least that you need, such as "laser: trained", and not the whole conversation.

Worked example: choosing what a note should say

Sam spent 20 minutes chatting about a failed print and the settings tried. What should the assistant save for next time?

  1. Ask: will a future session need this to act correctly? Training status: yes, because it decides if booking is allowed.
  2. Ask the same of the 20-minute transcript. Mostly no. Reloading it would add thousands of tokens at every future session.
  3. The useful middle: "Sam prefers the 3D printer in room B; PLA settings that worked: 200 C." Short, specific and checkable.
  4. Skip personal details that no task needs, such as Sam's complaint about a professor.
  5. Write the note as plain text with a date, so it can be updated, or deleted when it goes out of date.

Retrieval: finding the right page in a long manual 10 min

The problem

Your manuals might run to hundreds of pages. A student's question needs two of them. Putting all the pages in the window would be slow, costly, and, by the context-rot idea, would likely make the answer worse. Retrieval means fetching only the pieces relevant to the current question and putting those in the context.

Anthropic's guide on building agents describes the basic building block of an agent as a model enhanced with retrieval, tools and memory. That is the same trio you now have: retrieval for what the world knows, tools for actions, and memory for what the agent has learned (Anthropic: Building effective agents).

Two timings: before the model runs, or while it runs

The engineering post names two patterns. In pre-retrieval, the program searches before calling the model, for example with embedding-based search (matching text by meaning), and places the best passages in the context up front. In just-in-time retrieval, the agent holds light references, such as file paths or stored queries, and loads data with tools when it needs it (Anthropic: Effective context engineering for AI agents).

PatternHow it worksGood forCost to watch
Pre-retrievalProgram searches first, then calls the model with the resultsFast, predictable answers to simple questionsRetrieved text is there even if the model did not need it
Just-in-timeModel calls a search tool when it decides toMessy or multi-step questionsExtra model calls, and a dead end can waste tokens
HybridSome facts up front, the rest on demandMixed needsMore parts to design and test

The post notes that runtime exploration is slower than having data ready, and needs well-designed tools. It also notes that hybrid designs work: Claude Code puts its project instruction files into context at the start, and uses search tools to fetch the rest on demand. Its closing advice is to do the simplest thing that works.

Metadata helps the agent choose

The engineering post points out that names and structure carry meaning. A file called test_utils.py in a tests folder means something different from one in a core-logic folder. Your equivalent: if every manual page is stored with a machine name, a section title and a page number, the model can choose laser_cutter/safety over 3d_printer/safety without opening either.

A common mix-up

"Retrieval means the model reads the entire manual and then picks the part it wants." It is tempting because it sounds like what a person does with a book. But the point of retrieval is that the model never reads the rest. A search step narrows the library to a few passages first; only those enter the window.

Worked example: a search tool for the manuals

A student asks, "What is the thickest acrylic the laser cutter can cut?" Walk through a just-in-time version.

  1. The model sees a tool: search_manuals(query, machine), described as "Find passages in the machine manuals. Returns at most 3 passages with page numbers."
  2. The model requests search_manuals("maximum acrylic thickness", "laser cutter"). Notice that it chose both arguments from the student's words.
  3. The program runs the search and returns 3 passages, about 600 tokens in all, each with its page number.
  4. The model reads the passages. Passage 2 says 10 mm acrylic is the limit.
  5. The model answers "10 mm, see page 14 of the laser cutter manual" and stops. The other 399 pages never entered the window.
  6. The cost of the retrieved text is 600 tokens per later call, not the tens of thousands that the whole manual would be. Return fewer, shorter passages and it falls further.
Check yourself

Which design best fits "a student asks something that needs just one paragraph from a 400-page manual, and the budget is tight"?

Show the answer

The third option. Search narrows the library to the relevant passages, so the window and the budget carry only what the question needs.

Worked example: when retrieval returns the wrong page

The search for "thickness limit" returns the 3D-printer manual because both mention "maximum thickness". Fix it step by step.

  1. Find the cause: the query did not name the machine, so the search matched on words alone.
  2. Add a machine argument to the tool and say in its description that it is required.
  3. Store the machine name as metadata on every passage, and filter by it before ranking.
  4. Return the source with each passage, so the model can see if a result looks off and search again.
  5. Test with five questions whose right page you know. Count how often the right page is in the top three. That count tells you if retrieval works.
Worked example: how big should a passage be?

You split the manuals into pieces to search. Compare pieces of one page and pieces of one paragraph, step by step.

  1. Page-sized pieces, about 500 tokens each: the search returns whole pages. The answer is sure to be in there, but 3 pages are 1,500 tokens, much of it unrelated.
  2. Paragraph-sized pieces, about 100 tokens each: 3 hits are 300 tokens, but a paragraph can lose its context. "10 mm" with no machine name is useless.
  3. The fix: keep paragraph-sized pieces but attach a label to each, such as "Laser cutter, Cutting limits, p. 14".
  4. Test with real student questions and see which size gets the right passage in the top 3 most often.
  5. Pick the smallest size that still passes your tests. Size is a dial you can tune with evidence, not a fact to guess.
Check yourself

Your assistant always searches the manuals before the model runs, using the student's message as the query, even for "hi". Which timing is that, and what is its weakness?

The third option. Searching before the model runs is pre-retrieval, and its weakness is that the text arrives whether or not the question needed it.

Deciding where each thing lives 6 min

You now have three places to put information. The skill for your design review is choosing between them with a reason.

PlaceLives how longCostPut here
Context windowOne session, and only until cleared or compactedPaid at every model callWhat the current step needs: the question, the rules, recent results
Saved notesUntil you delete themPaid only when loadedFacts that must survive: training status, preferences
Searchable libraryPermanent, edited by staffPaid only for retrieved passagesLarge reference text: manuals, policies

A good rule of thumb: ask "how long must this be true?" and "how often is it needed?". A fact needed on every call and short, such as "never book a machine for an untrained student", belongs in the system prompt. A fact needed rarely and large belongs in the library.

Worked example: sorting five items

Place each in the window, notes or library: (1) the safety rule "no booking without training", (2) Sam's training status, (3) the 400-page manuals, (4) the raw calendar result for this question, (5) Sam's printer preference.

  1. Item 1 is short and applies on every call, so it goes in the system prompt, part of the window.
  2. Item 2 must survive between visits and is tiny: saved notes. It enters the window only when the assistant loads it.
  3. Item 3 is huge and needed rarely: the library, reached by retrieval.
  4. Item 4 is needed for this answer only: it is in the window for now, and may be cleared afterwards.
  5. Item 5 must survive, but it matters less: saved notes, loaded when relevant.
Your turn

Place these three items: (a) the tool descriptions, (b) a staff member's update that the laser cutter is out of service until Friday, (c) the text of the last answer the assistant gave in this chat. For each, say window, notes or library, and give one reason.

Show a solution

(a) The tool descriptions go in the window, because the model must see them on every call; that is why they should be short. (b) The out-of-service update goes in the calendar tool or a library entry that staff can change, not in the model's history, so that every student's session sees the same up-to-date fact. It could also be saved as a note that expires on Friday. (c) The last answer is already in the window as history; it does not need to be saved. At the end of the session it is thrown away unless a small fact from it matters later.

Splitting the work across several agents, each with a clean window, is another way to manage context. Anthropic's post describes sub-agents that explore using tens of thousands of tokens and return a summary of around 1,000 to 2,000 tokens. That belongs to a later lesson, when we decide whether your assistant needs more than one agent.

Worked example and practice 7 min

Now combine all the pieces on the makerspace assistant. First watch one full design done step by step. Then redo it yourself with a change.

Worked example: the cost of one request, before and after a design fix

Before: the starting text is 2,550 tokens. search_manuals returns a 3,000-token page. The other two tools return 300 and 100 tokens. We found 17,560 input tokens earlier. Now apply a fix: the program trims the search result to the best 1,000 tokens. How do the numbers change?

  1. Calls 1 and 2 are unchanged: 2,550 and 2,910 tokens, because the search result is not in them yet.
  2. Call 3 reads 2,910 + 60 + 1,000 = 3,970 tokens (it was 5,970).
  3. Call 4 reads 3,970 + 60 + 100 = 4,130 tokens (it was 6,130).
  4. New total: 2,550 + 2,910 + 3,970 + 4,130 = 13,560 tokens.
  5. Saved: 17,560 − 13,560 = 4,000 tokens. That is 2,000 tokens trimmed, times the two calls that would have re-read them.
  6. Check that the fix is safe: does the trimmed passage still hold the answer? Test with known questions before adopting it. Saving tokens is no use if the answer is wrong.
Your turn: faded

Same request, same starting text of 2,550 tokens, same 60-token tool requests. This time the order is changed: the model calls check_training_record first (100 tokens), then check_calendar (300 tokens), then search_manuals trimmed to 1,000 tokens, and writes the answer. Step 1 is done for you: call 1 reads 2,550 tokens. Work out what calls 2, 3 and 4 read, and the total.

Show a solution

Call 2 reads 2,550 + 60 + 100 = 2,710. Call 3 reads 2,710 + 60 + 300 = 3,070. Call 4 reads 3,070 + 60 + 1,000 = 4,130. Total = 2,550 + 2,710 + 3,070 + 4,130 = 12,460 tokens.

The order matters: putting the big result last means it is re-read once, not twice. Our earlier order read it twice. This is a small but real way to save budget, though the model chooses the order, so you would encourage it in the tool descriptions or the workflow rather than command it.

Worked example: spotting the problem in a design

A teammate sketches this design: "Keep every student's full chat history forever, paste the last 50 chats at the start of each session, and the manuals in the system prompt." Review it step by step.

  1. Check the window: 50 old chats could be tens of thousands of tokens, re-sent at every call. Costly, and likely to trigger context rot.
  2. Check the memory: full chats hold things nobody needs, and personal details that should not be kept. A short note per student is cheaper and safer.
  3. Check the manuals: pasting them in costs tokens on every call. A search tool fetches only what a question needs.
  4. Rewrite: system prompt with the short rules, one notes file per student loaded at the start, a search tool for the manuals, a calendar tool for availability, and a step limit.
  5. State the trade-off honestly: retrieval can miss the right page, and notes can go stale. Each needs a test and an update plan.

Putting it together: one full request 5 min

Here is one complete request, with all three places working together. Read it as a story of what is in the window at each step.

Worked example: Sam books the laser cutter on Wednesday
  1. Session start. The program builds the first request: the short system prompt (rules), the tool definitions (calendar, manual search, memory), and Sam's message "Book the laser cutter for Friday at 3". The window holds these, about 2,500 tokens.
  2. Memory first. The model asks to view Sam's folder. The program returns the notes file (about 150 tokens). The window now also holds Sam's note: "laser cutter: trained".
  3. Calendar. The model asks check_calendar("laser cutter", "Friday"). The program returns the free slots. These are fresh facts, so they are fetched by a tool, not remembered.
  4. Manual. Sam also asks which material is allowed. The model calls search_manuals, and 3 short passages (about 600 tokens) are added. The rest of the library stays outside.
  5. Answer. The model writes the confirmation and the material advice, and the loop stops. Total model calls so far: 5, each one re-reading the pile.
  6. Session end. The program throws away the message list. It writes back only what changed: "booked laser cutter Fri 15:00". Everything else is gone, on purpose.

Notice that no step relied on the model remembering anything. Every fact was either put in front of it by the program, fetched by a tool, or retrieved from the library. That is the whole lesson in one picture.

Retrieval practice

Without scrolling up, name the three wrong ideas this lesson corrected, and say in one line what is true instead.

Check your answer

First: "the model remembers earlier messages". In fact the program resends the history each call. Second: "a bigger window fixes the problem". In fact more tokens means more cost and weaker recall, whatever the size. Third: "memory is stored in the model" (and its cousin, "retrieval means reading the whole manual"). In fact memory is files your program writes, and retrieval narrows the library before the model reads.

Summary 3 min

  • The context window is everything the model reads in one request, including tool definitions, plus what it writes. The model keeps nothing between requests; your program resends the list.
  • Between steps, the history only grows, and every call re-reads and re-pays for it. Trim results, compact, and set a step limit.
  • Between sessions, nothing survives unless your program saves it. Notes saved outside the window and loaded on demand are the memory.
  • Retrieval brings only the relevant passages from a long manual into the window, either before the model runs or when it asks.
  • To place a fact, ask how long it must be true and how often it is needed.
