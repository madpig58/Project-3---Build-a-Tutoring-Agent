Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a manual you search, and say why.

Warm-up 2 min

Two quick recalls from the agent loop, before we build on it. Answer in your head first, then check.

Recall 1

When the model decides to use a tool, what does the model itself produce, and who actually runs the tool?

Check your answer

The model produces a request: the tool's name and its arguments, as text. The program around the model runs the tool and sends the result back. This split matters today, because the program is also the thing that decides what goes into the model's input on every call.

Recall 2

Name two things that can end an agent loop.

Check your answer

The model writes a final answer instead of requesting a tool, or the program hits a limit such as a maximum number of steps. Today you will see that a third thing can quietly break a loop: its input growing too large.

The context window: everything the model can see 5 min

Start with a game-engine picture. A renderer draws a frame from the scene description you hand it. It does not remember the last frame; if a tree is not in the description, the tree is not drawn.

A language model call works the same way. The model sees only what is in the request, and it writes its answer from that. The context window is all the text the model can reference when it writes a response, including the response itself, and it works like the model's working memory (Claude Platform docs: Context windows).

It is different from training. What the model learned in training is fixed. What is in the window is what you chose to give it this time.

What is in the window

The docs list it plainly: everything in the request counts, including the system prompt, every message (tool results too), and your tool definitions. The output the model writes counts as well (same page).

Windows are measured in tokens: the small pieces of text a model reads and writes. A short common word is often one token; a long or rare word is several. As a rough feel, a page of a manual is hundreds of tokens, not dozens.

Worked example: what is in the window for one question

A student asks the makerspace assistant: "Is the laser cutter free Friday?" What does the first model call contain?

  1. The program writes the system prompt: who the assistant is and its rules. Say 400 tokens.
  2. It adds the definitions of three tools (check_calendar, search_manuals, check_training_record). Say 1,100 tokens, because each name, description and parameter list is text.
  3. It adds the student's question, about 50 tokens.
  4. The window now holds 400 + 1,100 + 50 = 1,550 tokens, and the model has not written a word yet.
  5. The model writes a 60-token request for check_calendar. Those tokens are part of the window too, so the window is now 1,610.

Notice that 1,100 of the first 1,550 tokens are tool definitions. Long, vague tool descriptions are a cost you pay on every single call.

Some models also receive hidden "thinking" text, which counts toward the window as well. Your first prototype can ignore it; the docs page above explains the details when you need them.
A common mix-up

"The model remembers what I told it earlier, like a person does." It is tempting because chat apps feel that way. In fact the program resends the earlier messages on every call. If the program leaves a message out of the request, the model has no idea it ever existed.

Check yourself

Your program sends a request containing a system prompt, three tool definitions and one question. The model answers. Which of these does the model still hold when you send the next request?

Show the answer

Nothing. A call does not change the model, so the program must put every needed item, including the earlier answer and the tool definitions, into the next request.

What is kept between steps 5 min

Inside one task, the agent loop makes several model calls, one per step. Between those steps, the only thing "kept" is the list of messages your program maintains and resends.

The docs describe the pattern: each turn's input is all the previous history plus the new message, and the model's output becomes part of the input for the next turn (Context windows).

The code that does the remembering

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system=SYSTEM, tools=TOOLS, messages=messages)
    messages.append(reply)               # keep what the model said
    if reply is a final answer:
        break
    result = run_tool(reply)             # the program runs the tool
    messages.append(result)              # keep what came back

The memory between steps is the list messages. Two lines append to it, and the whole list goes into every call. Delete the two appends and the agent forgets what it just did.

Why this drives your cost

Each call is billed for the tokens it contains, so a long history is paid for again on every step. Prompt caching can make repeated parts cheaper to pay for, but cached tokens still take up space in the window (Context windows). Watch the sum of input tokens over all calls, not the size of the last one.

Worked example: add up the input tokens of one request

Same question as before, but now the assistant runs three tools. Each model output is 60 tokens (a tool request) except the last, which is a 100-token answer. Tool results: calendar 300 tokens, check_training_record 150 tokens, search_manuals 2,000 tokens. Order: calendar, then manuals, then training record.

  1. Call 1 input: 1,550 (system prompt, tools, question) as in the last example.
  2. Call 2 input: 1,550 + 60 (the request) + 300 (calendar result) = 1,910.
  3. Call 3 input: 1,910 + 60 + 2,000 (manual excerpts) = 3,970.
  4. Call 4 input: 3,970 + 60 + 150 (training record) = 4,180. The model then writes its 100-token answer.
  5. Total input over the request: 1,550 + 1,910 + 3,970 + 4,180 = 11,610 tokens.

The student's question was 50 tokens, yet you paid for more than eleven thousand input tokens, because the 2,000-token manual excerpt was resent in call 3 and again in call 4.

A common mix-up

"The cost of a request is the length of my prompt plus the length of the answer." It is tempting because that is true for a single call. For an agent, every step resends the growing history, so the cost grows faster than the number of steps.

Check yourself

An agent makes 5 model calls on a task. Which change cuts input cost the most?

Show the answer

Trimming the large tool result. It is resent on every later call, so each token removed is saved several times.

When the window fills up 5 min

Every window has a limit. Current models range up to 1M tokens depending on the model, but the docs warn that more context is not automatically better: as token count grows, accuracy and recall degrade, a phenomenon called context rot (Context windows).

Anthropic's engineering team puts it as an "attention budget": context is a finite resource with diminishing returns, and the goal is the smallest set of high-signal tokens that makes the right outcome likely (Effective context engineering for AI agents).

A game analogy: a level can hold ten thousand props, but the frame rate drops and the player cannot find the door. A window stuffed with everything is the same: it fits, but the important thing gets harder to find.

Three ways to keep the window small

MethodWhat it doesCost
Clear old tool resultsDrops stale tool outputs once they have been usedThe model can no longer see the details
CompactionSummarizes the conversation so far and continues in a fresh windowThe summary may leave out something that turns out to matter
Hand the work to a sub-agentA separate model call with its own clean window does the digging and returns a short summaryExtra calls; covered in a later lesson

The first two are described in the Anthropic post and docs: compaction means summarizing a conversation near its limit and continuing, and clearing old tool results is a light-touch form of it (Anthropic Engineering).

Worked example: clear a tool result after you use it

Using the numbers from the last section, the 2,000-token manual excerpt is only needed to write the answer about training. What if the program replaced it with a one-line note once the model had used it?

  1. The model has just seen the excerpt in call 3 and decided on its next step. After call 3, the program swaps the excerpt for "Manual search done: laser cutter needs level-2 training" (about 20 tokens).
  2. Call 4 input becomes 1,910 + 60 + 20 + 60 + 150 = 2,200, instead of 4,180.
  3. Call 4 saves 1,980 input tokens. With more calls after it, the saving repeats on each of them.
  4. The price: if the student now asks "what was the exact power setting in that manual?", the details are gone. The program must search again.

The trade-off is general: you give up detail to save space and money, and you decide what is safe to forget.

A common mix-up

"A bigger window means I can stop worrying about what I put in it." It is tempting because the limit sounds enormous. But you pay for every token on every call, and recall gets worse as the window fills. A window that can hold a manual is a capacity, not a reason to use it.

Check yourself

Your agent has used 90% of its window on a long task and still has work left. Which choice keeps the task going with the least risk of losing something important?

Show the answer

Summarize progress and clear old raw tool output. The summary carries the goal and decisions forward, and raw output that has been used is the cheapest thing to lose.

Between sessions: notes as memory 6 min

Everything so far lives inside one task. When a session ends, the messages list is gone. The next time a student opens the assistant, the program starts with an empty list, and the model has no idea who they are.

So the assistant needs notes: information the program saves outside the window, in a file or database, and loads into a later window. The notes are the memory. The model does not hold them; the storage does.

Anthropic's memory tool shows the pattern. It is a directory of files the model can create, read, update and delete, and it persists between sessions. It works client-side: the model requests a file operation and your application runs it against storage you control (Claude Platform docs: Memory tool). That is the same split you already know from the agent loop, now applied to memory.

Worked example: a returning student

Jordan finishes laser cutter training on Monday and chats with the assistant. They come back on Thursday. How does the assistant know Jordan is trained?

  1. Monday: the assistant's program provides a save_note(student, text) tool. The model calls it with "Passed laser cutter level 1; prefers evening slots".
  2. The program runs the tool and writes the text to notes/jordan.md. The Monday session ends and its window is discarded.
  3. Thursday: Jordan logs in. The program builds a new window with the system prompt, the tool definitions and a first line it adds itself: the contents of notes/jordan.md. Alternatively the model can call a read_notes tool as its first step, as the memory tool's built-in prompt asks it to.
  4. Jordan asks to book the laser cutter. The model sees "Passed laser cutter level 1" in its window and goes straight to check_calendar, with no retraining question.
  5. At the end, the program asks the model to save any new facts, and the cycle repeats.

The model did not remember Jordan. The program remembered, and put the memory in front of the model.

What deserves a note

Keep notes short and useful: facts that will matter next time and are costly to rediscover. For a long job, the docs suggest a progress log and a checklist that each new session reads first and updates at the end (Memory tool, multisession pattern).

Notes also need care. The docs advise capping file sizes, expiring files that are not used, and keeping all operations inside the memory directory, because your application runs every operation the model asks for. Student records are personal data, so decide what your team is willing to store.

Design judgment, not from the docs: a note can go stale. If the training status lives in the university's database, have the assistant read it with a tool each visit rather than trusting a note from last month. Use notes for things with no other home, such as preferences.
A common mix-up

"The assistant will automatically remember earlier conversations." It is tempting because consumer chatbots do seem to. But an API call has no such feature by default; a system that remembers has a store, code that writes to it and code that reads it back. If you did not build those, the assistant forgets everything at the end of the session.

Check yourself

A student told the assistant on Tuesday that they use a wheelchair, so they need the bench at table height. On Friday the assistant asks them again. What is the most likely cause?

Show the answer

No note was saved or none was loaded. Friday's window started empty, so only a saved and reloaded note could carry Tuesday's fact into it.

Retrieval: finding the right page 6 min

Notes cover what the assistant learns about students. The other memory problem is the manuals: hundreds of pages the assistant did not write and cannot fit in its context for every question, at least not cheaply.

Retrieval means fetching only the relevant pieces from a larger store, at the moment they are needed, and placing them in the window. Anthropic calls the agent version "just in time": the agent keeps lightweight references and loads data when it needs it, instead of loading everything up front (Effective context engineering).

Think of a game that streams in the part of the map near the player instead of loading the whole world. The world is large; the loaded part is small.

How a manual search works

First you cut each manual into chunks: pieces of a page or a section, each with an id such as laser-manual#p14. Then you build an index that can find chunks for a query. There are two common kinds:

  • Keyword search finds chunks that contain the words in the query. It is fast and exact, but misses "cut depth" if the manual says "maximum thickness".
  • Meaning-based search turns each chunk and the query into an embedding, a list of numbers that places similar meanings close together, then returns the nearest chunks. Lilian Weng's overview describes long-term memory as an external vector store with fast retrieval (LLM Powered Autonomous Agents).

Retrieval is exposed to the model as a tool, like search_manuals(query). The model writes the query, your program runs the search, and the top few chunks come back as a tool result. That is the agent loop again.

Worked example: one manual question

A student asks: "How thick can acrylic be on the laser cutter?" The laser cutter manual is 120 pages, split into about 600 chunks.

  1. The model reads the question and decides it needs the manual. It writes a tool request: search_manuals("laser cutter maximum acrylic thickness").
  2. The program runs the search over the index. It returns the three best chunks, each about 300 tokens, with their ids: laser-manual#p14, #p15 and #p31.
  3. The result is added to the window: about 900 tokens, instead of the roughly 60,000 for all 600 chunks at 100 tokens each, a rough figure for illustration.
  4. The model reads chunk p14: "Maximum thickness for cast acrylic: 12 mm". It answers and cites laser-manual#p14, so the student can check.
  5. If chunk p14 had been about a different material, the model could search again with a better query, because retrieval is a tool it can call more than once.

Anthropic notes the trade-off: loading at runtime is slower than precomputing everything, and a hybrid of up-front and on-demand loading often works best (Effective context engineering). For your assistant, put the small, always-needed rules in the system prompt, and retrieve the manual pages.

A common mix-up

"Retrieval means the model searches the manuals by itself." It is tempting because the answer appears to come from the manual. In fact, the model only writes the query. Your program runs the search against your index, and the quality of your chunks and index sets a ceiling on the answer.

Check yourself

The assistant keeps returning the wrong page for "how do I swap the bandsaw blade?" The manual calls it "blade replacement procedure". Which fix attacks the real problem?

Show the answer

Search by meaning (or add alternate terms to the chunks). The failure is that the query words do not match the manual's words, which is a retrieval problem, not a prompt problem.

Worked example and practice: design the memory 5 min

Now combine the three tools: the window, notes and retrieval. For each piece of information, ask: how long must it live, and how big is it?

If the information is...Put it in...
Needed on every call, and smallThe system prompt (context)
Needed only during this taskThe message list (context)
About a person, and useful next visitNotes, loaded at the start
Large, and only a small part is needed per questionAn index, retrieved on demand
A live fact owned by another systemA tool that reads it fresh
Worked example: sort four items

Decide where each of these goes for the makerspace assistant.

  1. "Never book a machine for an untrained student." A rule needed on every call, and short. It goes in the system prompt, about 15 tokens.
  2. The 3D printer manual (80 pages). Large, and each question needs one page. It goes in the index and is retrieved by search_manuals.
  3. "Jordan prefers evening slots." About a person, and useful next visit. It goes in Jordan's notes, loaded at session start.
  4. Whether the laser cutter is free on Friday. A live fact that changes. It goes behind check_calendar, read fresh each time. A note would go stale.

Each answer came from asking how long it lives, how big it is and who owns it.

Your turn

Sort these four items. The first is done for you: "The student's current question" goes in the message list, because it matters only for this task. Now place the other three:

  1. The rule "ask for the student's ID number only when booking, never when answering manual questions".
  2. The fact that a student asked last month about vinyl cutting and likes to work on poster projects.
  3. The 40-page safety handbook, from which one short rule is needed for most questions about a given machine.

Then work out the cost. In the worked example in section 2 the calls had input 1,550, 1,910, 3,970 and 4,180 tokens when the order was calendar, manuals, training. If the order is manuals first (2,000 tokens), then calendar (300), then training (150), with the same 60-token requests, what is the total input across the four calls? Here is the first step: call 1 is 1,550.

Show a solution

Sorting. The ID rule is short and needed on every call, so it goes in the system prompt. The vinyl interest is about a person and useful later, so it goes in notes. The safety handbook is large and needs one rule at a time, so it goes in an index and is retrieved. A note could store "has not completed the safety handbook", but the handbook text itself stays in the index.

Cost. Call 1: 1,550. Call 2: 1,550 + 60 + 2,000 = 3,610. Call 3: 3,610 + 60 + 300 = 3,970. Call 4: 3,970 + 60 + 150 = 4,180. Total: 1,550 + 3,610 + 3,970 + 4,180 = 13,310 tokens, which is 1,700 more than the 11,610 of the other order.

The lesson: calling the tool with the biggest result first means that result is resent in every later call. When you can choose the order, or trim the result, put the big result late or shrink it.

Summary 2 min

  • The context window is everything the model sees in a call: system prompt, tool definitions, messages and tool results. The model keeps nothing between calls.
  • Between steps, the program's message list is the memory, and it is resent in full each call, so cost and clutter grow with every step.
  • When the window fills, clear used tool results, summarize, or hand work to a sub-agent. Bigger windows do not remove context rot.
  • Between sessions, only saved notes carry over, and the program must write and reload them.
  • Retrieval brings only the relevant chunks of a large store into the window, through a search tool.

Say it in your own words: A student returns next week and asks a manual question. Without looking, explain what is in the window at the first call, where the student's history comes from, and how the right manual page gets there.
