Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable manual, and say why.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those are three different memory problems, and at your design review you will need to say which tool solves which.

The context window: all the model sees 6 min

Start with a game. Imagine a non-player character (NPC) in a game, driven by a language model. A player walks up and says, "Where is the blacksmith?" What does the model need to answer well?

It needs to be told who it is ("you are Mira, a villager"), what it knows ("the blacksmith is by the north gate") and what the player just said. Nothing else exists for it. If the player's name is not in that text, the model does not know the name.

The context window is the text the model reads on one call: everything you send it, plus the answer it writes. It has a maximum size, counted in tokens. A token is a small chunk of text, often a short word or part of a word. A page of a manual is typically several hundred tokens.

Anthropic describes the context as everything that is "in" the model at the moment it produces its next output, and treats it as a limited resource with diminishing returns for each token added (Anthropic: Effective context engineering for AI agents).

What goes into the window

For an agent, the window usually holds five kinds of text:

  • The system prompt: standing instructions, such as the assistant's role and rules.
  • The tool descriptions: the names, purposes and parameters of each tool (you met these in the agent loop).
  • The conversation so far: what the student said and what the assistant replied.
  • The tool calls and tool results from earlier steps.
  • Anything retrieved for this request, such as a manual page.
Worked example: what the model sees for one question

A student writes, "How do I change the blade on the band saw?" Here is what the first model call contains.

  1. The program starts with the system prompt: "You are the makerspace assistant. Answer only from the manuals. Be brief." This is always first.
  2. It adds the tool descriptions: search_manuals(query), check_calendar(machine, date), book_slot(machine, date, time). The model needs these to know what it can ask for.
  3. It adds the student's message as the first conversation turn.
  4. The model replies with a tool request: search_manuals("band saw blade change"). That request is now part of the conversation too.
  5. The program runs the search and appends the result, say 400 tokens of manual text. This is the retrieved text.
  6. The program calls the model again. This time the window holds all of steps 1 to 5. The model reads it all and writes the answer using the retrieved text.

Notice that the model never "opened" the manual. The manual text became part of its window because the program put it there.

A common mix-up

"The model remembers what I told it earlier." It feels true because chat apps look continuous. But the model itself keeps nothing between calls. The program re-sends the earlier conversation each time, so it looks like memory. If the program stops sending it, the model has forgotten it entirely.

What is kept between steps 7 min

Now take one request that needs several steps. Inside one request, the loop calls the model repeatedly. What carries from one step to the next?

The answer is the program's list of messages, often called the message history or transcript. After every step, the program appends the model's output and the tool result to this list. Before the next call, it sends the whole list again. So between steps, "memory" is this growing list, and nothing else.

Worked example: counting tokens across three steps

Take a request that needs three model calls. Say the system prompt and tool descriptions together are 1,000 tokens, the student's question is 50, each tool request is 30 and each tool result is 400.

  1. Call 1 sends 1,000 + 50 = 1,050 tokens. The model asks for a tool (30 tokens out).
  2. Call 2 sends the earlier 1,050, plus the 30-token request, plus the 400-token result: 1,480 tokens.
  3. The model asks for a second tool (30 more). Call 3 sends 1,480 + 30 + 400 = 1,910 tokens.
  4. Total sent across the three calls: 1,050 + 1,480 + 1,910 = 4,440 tokens, even though the "new" text was only a little over 900 tokens.

Each step re-reads everything before it. A longer loop therefore costs more than a straight multiple of its steps, and your budget feels this directly. Providers typically charge per token read and written, and some offer caching for repeated prefixes; the lesson to take is that bloated context is paid for again at every step.

What happens when the window fills

Two limits meet here. The window has a hard maximum, and your budget has a soft one. Before you hit the maximum, there is a quieter problem. Anthropic reports that as the number of tokens in the window grows, the model's ability to recall information from it tends to decline, which it calls context rot. The decline is gradual, not a cliff (Anthropic).

So the goal is not to fill the window. The goal, in Anthropic's phrase, is the smallest set of high-signal tokens that makes the right behavior likely.

Three tools help you keep the window small:

  • Return less. A tool should send back only what the model needs, not a whole database row dump.
  • Clear old tool results. After the model has used a 400-token result, the program can replace it with a one-line stub.
  • Compaction: when the conversation nears the limit, summarize it and start a new window with the summary. Anthropic describes Claude Code doing this, keeping key decisions and unresolved bugs while dropping the rest.
Worked example: trimming a window in the booking flow

The assistant has just checked the laser cutter calendar. The tool returned the whole week: 60 time slots, about 900 tokens. The student only wants Friday afternoon.

  1. Spot the waste: 850 of the 900 tokens answer questions nobody asked.
  2. Fix at the source: give check_calendar parameters for date and time range, so it returns four slots, about 60 tokens.
  3. Count the saving across a six-step request: those tokens would otherwise be re-sent on up to five later calls. 840 tokens saved times five is 4,200 tokens, for one change.
  4. Check what you kept: the model still sees what it needs to answer, "Friday 2 to 4 pm is free".

This is the cost lever you can pull before any fancy technique: make tools return less.

A common mix-up

"A bigger context window means I do not need to manage context." A bigger window raises the maximum, but cost still grows with every token re-sent and recall still gets worse as the window fills. A large window is room, not a plan.

The first option. The program re-sends the history, so later steps cost more than early ones.

What is kept between sessions 6 min

A session is one run of the assistant, such as a student's chat on Tuesday. When the session ends, the program ends, and the message history is gone unless the program saved it somewhere. The model itself keeps nothing, as we saw. So by default, nothing is kept between sessions.

That surprises people, because chatbots sometimes seem to remember you. When one does, the product has saved something to disk or a database and loads it into the window at the start of the next session. The memory lives outside the model, in ordinary storage.

This is what Anthropic calls structured note-taking, or agentic memory: the agent writes notes to storage outside the context window and reads them back later. Anthropic's example is Claude playing a Pokémon game, which kept notes on training progress and explored maps and used them to continue after its context was reset (Anthropic).

For a game developer, the picture is familiar: this is a save file. The window is the game's RAM, and a notes file is the save file. When you quit, RAM is cleared; when you load, you read the save file back into RAM.

Worked example: remembering a student's training status

A student, Sam, completes laser cutter safety training on Monday. On Wednesday Sam asks to book the laser cutter. The assistant must know about Monday.

  1. On Monday the program writes a record to storage: {"student": "sam", "trained": ["laser_cutter"], "date": "Mon"}. A small JSON file or database row is enough.
  2. The Monday session ends. The window and message history are discarded.
  3. On Wednesday a new session starts with an empty window. The program identifies Sam from the login.
  4. The program loads Sam's record. Either it puts it in the system prompt up front, or it gives the model a get_training_record(student) tool and lets the model ask.
  5. The model reads "trained: laser_cutter" and goes ahead with the booking.

Which option in step 4? Loading up front costs tokens on every call, even when training is irrelevant. A tool costs tokens only when used, but the model must decide to call it. For a short record that is always needed to book, up front is fine.

A common mix-up

"Agents automatically remember past conversations." They do not. Memory is a feature you design: decide what to save, where, and when to load it. And do not save everything: raw transcripts would fill the next window. Save facts, such as training status, rather than whole chats.

Check yourself

Retrieval: finding the right page 7 min

Third problem: the manuals are long. Say the band saw manual is 80 pages, about 40,000 tokens, and you have a dozen machines. Putting every manual in the window on every call would be expensive and, because of context rot, less accurate.

Retrieval means: keep the manuals outside the window, search them when a question comes in, and put only the best few passages into the window. Put another way, memory by lookup. Combined with a language model, this pattern is commonly called retrieval-augmented generation, or RAG.

Anthropic describes the same idea for agents as just-in-time retrieval: keep lightweight references and load data with tools when needed, instead of loading everything up front (Anthropic).

The steps of retrieval

  1. Prepare once, ahead of time. Split each manual into chunks, passages of a few hundred tokens. Chunk by section, so a chunk is about one topic.
  2. Index the chunks. Build something searchable. Two common kinds: keyword search (such as BM25, which scores chunks by matching words) and embedding search, where each chunk becomes a list of numbers so that chunks with similar meaning sit close together.
  3. At question time, search. Turn the query into a search, take the top few chunks.
  4. Put the chunks in the window, usually as a tool result, so the model answers from them.

The key point for your design: steps 2 and 3 are ordinary programs, not the model's memory. The model's part is deciding to call search_manuals and writing a good query.

Worked example: one question through the retrieval pipeline

A student asks, "What speed should I use to cut aluminum on the band saw?"

  1. Ahead of time, the 80-page band saw manual was split into 200 chunks, each tagged with machine and section, and indexed.
  2. The model calls search_manuals("band saw blade speed aluminum"). Good tool descriptions help it write a query like this, as you saw in the agent loop lesson.
  3. The program searches the index and returns the top 3 chunks, about 300 tokens each: "Blade speeds by material", "Cutting non-ferrous metals", "Lubricant".
  4. The window now holds roughly 900 tokens of manual text, not 40,000.
  5. The model answers from the chunk, and can cite the section so the student can check.

Cost sense: 900 tokens versus 40,000 per call. Over a ten-step request that is the difference between a cheap request and an unaffordable one.

When retrieval misses

Retrieval can fail by returning the wrong chunks. A chunk that says "Set it to 2,500 ft/min" does not say which machine or material it is about, so a search for "aluminum band saw speed" may not find it. Anthropic's Contextual Retrieval fixes this by prepending a short explanation of where the chunk comes from before indexing it; they report this lowers failed retrievals, with the best results combining contextual embeddings, contextual keyword search and reranking (Anthropic: Contextual Retrieval).

You do not need that yet. The cheap version is to include the machine name and section title in every chunk. If the first, simple version fails on real questions, then reach for more.

A common mix-up

"Retrieval means the model has read the manuals." It has not. The model reads only the few chunks the search handed back. If the search returns the wrong pages, the model answers from the wrong pages, or guesses. The quality of the answer is capped by the quality of the search.

Worked example: placing five pieces of information

Place these five items for the makerspace assistant: (1) the rules "never book a machine without training", (2) the manual for the CNC router, (3) Priya's training record, (4) what Priya asked two messages ago, (5) the calendar result for today.

  1. The rules are short and apply to every call. They go in the system prompt, which is always in the window.
  2. The CNC manual is large and needed only for some questions. It goes in the searchable store; chunks enter the window by retrieval.
  3. Priya's record is small, lasting and needed across visits. It goes in saved storage and is loaded when her session starts.
  4. Her question from two messages ago matters only in this session. It stays in the conversation history in the window.
  5. Today's calendar result is accurate only now. It enters the window as a tool result and is dropped or cleared afterwards, never saved.

Each item got a home by answering "how long, how big?", with no special knowledge needed.

Your turn, harder

The sponsor says each request may cost at most about 10,000 input tokens in total, and your typical request has 4 model calls. The system prompt and tools are 1,200 tokens. Roughly how large can the window's growing content be if it averages 2,000 extra tokens per call? Work out the total, then say what you would trim first if it is over budget. First step: total input is the sum of what each call sends.

Show a solution

Each call sends 1,200 plus its extra content. If the extra content averages 2,000, each call is about 3,200 tokens and four calls total about 12,800, which is over 10,000. Trim first the largest item that repeats on every call: oversized tool results and retrieved chunks. Return fewer chunks, shorter results, or clear old results, which attack the repeated part. Shortening the system prompt helps too, since it repeats on all four calls.

One more trace: a request that uses all three 4 min

Before the summary, follow one request from start to finish and watch each kind of memory act in turn. Seeing them work together is what lets you defend the design.

Worked example: "Book me the CNC router Friday at 2"

The student is Priya. It is her first message of a new session.

  1. Session start. The window is empty. The program loads the system prompt and tool descriptions, and fetches Priya's saved record: "trained: laser_cutter, band_saw". This is memory between sessions, now copied into the window.
  2. Call 1. The model reads the record and the request. CNC router is not in her trained list, so it needs the training rules. It requests search_manuals("CNC router training requirement").
  3. Retrieval. The program searches the index and appends two chunks: "The CNC router requires the safety course before first use." This is memory by lookup.
  4. Call 2. The window now holds the record, request, search call and chunks. This is memory between steps. The model decides not to book, since Priya is untrained, and writes: "You need the CNC safety course first. Want me to look up when the next one runs?"
  5. Session end. Priya says no thanks. The window is discarded. The program writes one line to her record: "asked about CNC; not trained". The long chunks and the chat wording are not saved.

Count the memories in play: a saved record, a retrieved page, and the live history. Each had a different lifetime and size, and each was loaded only when needed.

Your turn

Priya comes back next week, after finishing the CNC course. Walk through the first two steps yourself: what is in the window at call 1, and what must have happened to her saved record in between? Step one is given: the window starts empty, because a new session never inherits the old window.

Show a solution

Something must have updated the record, either the training system or the program, to add "cnc_router" to her trained list. This did not happen inside any model; it is a normal write to storage. At call 1 the window holds the system prompt, tool descriptions, the loaded record that now lists the CNC router, and her new request. The model can then go straight to checking the calendar.

Check yourself

The record from last week still says Priya is untrained, though she passed the course yesterday. The assistant refuses to book. Where is the fault?

Show the answer

The third option. Saved notes go stale unless something writes to them, so decide who updates each record and when.

Stale memory is the main risk of saved notes. A good habit is to store a date with each fact, so the model, or you, can tell how old it is.

Summary 2 min

  • The context window is all the text the model reads on one call. The model keeps nothing between calls.
  • Between steps, the program keeps the history and re-sends it, so cost and clutter grow every step. Keep it small.
  • Between sessions, nothing is kept unless the program saves it. Saved notes are storage you design, loaded into the window.
  • For long manuals, retrieval searches outside the window and brings only a few chunks in. Answer quality is capped by search quality.
