Learning objectives:
1. You can explain what the context window is: the tokens the model is given on each call. You can say what limits it and why it drives cost per request.
2. You can explain what the assistant keeps between steps of one request, and how to keep that set small (clearing old tool results, compaction).
3. You can explain what is saved between sessions, and how notes in a file outside the window work as memory.
4. You can explain how retrieval finds the right page in a long manual (chunks, search, loading only the best chunks just in time), and why a chunk needs context of its own.

The main worked example in the frame combines objectives 1 to 4 on the makerspace assistant.

## Section 1: The context window: what the model sees on every call (5 min, 750 words)
- Objective: 1
- New terms (two):
  - token: a small chunk of text (a word or part of a word) that the model reads and writes, and the unit that limits and prices a request.
  - context window: the tokens the model is given on one call, which include the instructions, the conversation, tool results and any pages you add. It has a maximum size.
  Use the Anthropic definition of context: the tokens included when the model samples.
- Opening example (about 100 words): a game engine with a fixed-size frame buffer or RAM budget. Whatever does not fit in the budget cannot be used this frame. The model is the same: it can use only what is in the window on this call. Show a short Python list of messages as the "scene": system instructions, student question, tool result.
- Worked example (about 300 words): count what goes into one call of the makerspace assistant, using made-up round numbers and no real pricing. Steps:
  1. Write the call as a Python list: instructions (about 400 tokens), the student's question (about 20), tool definitions for `search_manual` and `check_calendar` (about 300).
  2. Add the result of `check_calendar`, a calendar dump of about 1,500 tokens. Total: about 2,200 tokens.
  3. Show that the model's whole view is that list. Nothing else exists for it.
  4. Say what a token limit means: if the list is over the maximum, the call fails or must be cut.
  5. Say why cost follows size: a larger list means more tokens in every request, and the budget is counted in tokens. Do not give prices. Point out that Riley can multiply by the number of requests per day to compare designs.
  6. Compare with pasting a 60-page manual (about 40,000 tokens, an invented round figure) into every call, and say this is a design choice to compare, not a rule.
- Practice (about 100 words): "The assistant's context has 2,200 tokens. A student asks a second question. Which of these is true: (a) the model still knows the first answer because it gave it; (b) the model knows it only if the first exchange is included in the second call's text; (c) the model learns from the first answer for later calls; (d) the model keeps the first answer until the window fills." Options are of equal length, and the right answer is in position 2 or 3. Tempting wrong answer: (a) or (d), because a chat feels like a continuous mind. Feedback: each call starts from only the text it is given, and the program decides what to include.
- Misconception: "the model remembers on its own." Heads it off with the call-as-a-list picture. Note that this ties to record 0001's floor.
- Citations:
  - Context is the set of tokens included when sampling from the model - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Context engineering means curating the optimal set of tokens - same source
  - Token counts, window size and per-token cost are explained in plain words only. Do not cite exact limits or prices.

## Section 2: What stays between steps, and what to clear (5 min, 750 words)
- Objective: 2
- New terms (two):
  - context rot: the model gets worse at using information as the window fills with more tokens, so a bigger context is not always better. Source 1 ties this to a finite attention budget.
  - compaction: summarizing a long run when it nears the limit and starting a new window from the summary.
- Opening example (about 100 words): a game's save log. If the game replayed every frame since launch to restore state, it would be slow and full of noise. A good save keeps only state that matters. Then ask: in an agent loop, what is "the whole history"?
- Worked example (about 320 words): one booking request, step by step, with the window growing. Request: "Book the 3D printer for 2 hours Friday afternoon." Steps:
  1. Step 1: the window holds the instructions, tools and the question. The model asks to `check_calendar`.
  2. Step 2: the program runs the tool, then makes a second model call whose text includes everything from step 1 plus the calendar result (a long list). State plainly that each step is a separate call and the program resends the history. This checks the point record 0002 left open.
  3. Step 3: the model asks `search_manual("3D printer booking rules")`. The result is a long page. The window is now the instructions plus the question, the calendar and the page.
  4. Step 4: the model asks `book_slot`. The window now contains three large tool results, yet only one slot from the calendar and one rule from the page are needed.
  5. Clearing: after the model has used a tool result, the program can replace it with a one-line note (for example "calendar checked: Fri 14:00-16:00 free") or drop it. This is context editing.
  6. Compaction: if a conversation runs long, summarize it and continue from the summary. Say which details a summary must keep (the booking, the student's choices) and which it can drop.
  7. State the goal: the smallest set of high-signal tokens that still lets the model do the next step.
- Practice (about 120 words): "After the calendar check, which result should be cleared first: (a) the student's question; (b) the 1,500-token calendar dump; (c) the tool definitions; (d) the instructions." Right answer in position 2 or 3, and options of equal length. Tempting wrong answer: (a), because the question is the oldest item. Feedback: age is not the test. The test is whether the model still needs the tokens for the next step. The question and the instructions are needed, and the dump is not, once its key fact is noted.
- Misconception: "more context always helps, so keep everything." Heads it off with context rot and with the cost of resending the history on every step.
- Citations:
  - Context rot and the finite attention budget; the aim of the smallest set of high-signal tokens - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Compaction: summarize near the limit, clear old tool results - same source
  - Context editing clears stale tool calls and results - https://claude.com/blog/context-management
  - Each step is a separate call, with the history resent. This is the program's behavior in the agent loop, taught from the learning records. Do not cite it.

## Section 3: Between sessions: notes as memory (4 min, 600 words)
- Objective: 3
- New terms (two):
  - session: one conversation from start to end. When it ends, the window is gone.
  - memory: information the assistant saves outside the window, such as a file, and reads back into a later window.
- Opening example (about 90 words): a game save file. Quitting wipes RAM, but the save file keeps your progress, so the next launch loads it. Likewise a new session starts with an empty window. Ask what the assistant has to write down so that Thursday's session knows what Monday's learned.
- Worked example (about 280 words): Riley's student-status memory. Steps:
  1. Monday session: student "Sam" completes laser cutter training. At the end, the model asks a `save_note` tool to write a line in `students/sam.md`: "laser cutter training: done, Mon".
  2. The session ends. The window is discarded. Show that nothing remains inside the model.
  3. Thursday: a new session starts empty. The program first reads `students/sam.md` and puts it in the window, or the model asks a `read_note` tool for it.
  4. The model now answers "Can I use the laser cutter?" correctly.
  5. Say who runs it: the developer (Riley's team) writes the tool code and the storage. The model only asks. This is the agent loop again, with files as the tool. Mention that the memory tool described in the Anthropic post works this way, as a file-based store outside the window that persists across conversations, which the developer runs.
  6. The Pokemon example from source 1: an agent keeps notes (maps, goals, progress) outside the window and reads them after a reset, so it can continue over thousands of steps. Use as a two-sentence aside only.
  7. What to save: facts that will matter next time and that are costly to rediscover (training done, preferences, open bookings). What not to save: raw tool output, whole chats. Save small.
- Practice (about 100 words): "Which should the assistant save between sessions: (a) the full 60-page manual text; (b) each student's training status; (c) the calendar result from today; (d) every message from the chat." Right answer in position 2 or 4, and options of equal length. Tempting wrong answer: (d), because more detail feels safer. Feedback: the manual already lives in the documents (see section 4), the calendar changes by the hour, and a whole chat adds tokens to every later window. Training status is small, stable and costly to rediscover.
- Misconception: "memory means the model is retrained or learns." It is a file the program reads back. This keeps training and fine-tuning out of scope.
- Citations:
  - The memory tool is a file-based store outside the context window that persists across conversations, and the developer runs the backend through client-side tool calls - https://claude.com/blog/context-management
  - Structured note-taking, with notes kept outside the window and read back after resets, including the Pokemon example - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Section 4: Retrieval: finding the right page in a long manual (5 min, 750 words)
- Objective: 4
- New terms (two):
  - chunk: a short piece of a long document (for example one section of a manual), cut so it can be searched and loaded on its own.
  - retrieval: finding the few chunks that best match a question and putting only those in the window.
- Opening example (about 100 words): a game engine's documentation. You do not read all of it to learn one function. You search, open one page, and read it. Ask how the assistant can do the same with a 60-page laser cutter manual without loading it on every call.
- Worked example (about 330 words): the question "Why does the laser cutter show an air-assist error?" Steps:
  1. Prepare once, ahead of time: split the manual into chunks (about 200 words each, an invented size) and store them in a searchable index.
  2. The model asks `search_manual("air assist error")`. This is a lightweight reference, a query, rather than the whole document.
  3. The search returns the top three chunks. Only these go into the window (for example 600 tokens, not 40,000). Compare the cost with section 1's paste-it-all design.
  4. The model answers from the chunk and cites the page.
  5. Show the failure: a chunk reads "Check that it is connected before starting." The word "it" and the machine are in other chunks, so the chunk matches too many questions or none. Chunks lose context.
  6. The fix: prepend a short line of context to each chunk before indexing, such as "Laser cutter manual, Troubleshooting, Air assist". Describe it as written from the whole document. Retrieval then finds the chunk more reliably.
  7. Just in time versus up front: the assistant keeps small references (manual names, section titles) and loads pages only when needed. Some things, such as the safety rules, are cheap and always needed, so they can be loaded up front. This is a hybrid.
- Practice (about 120 words): "A chunk says 'Replace the filter every 50 hours.' Which fix helps retrieval most: (a) make the chunk shorter; (b) prepend 'Laser cutter manual, Maintenance, exhaust filter'; (c) load the whole manual instead; (d) repeat the sentence twice." Right answer in position 2 or 4, and options of equal length. Tempting wrong answer: (c), because it removes the chance of missing the page. Feedback: it brings back the cost and context rot of section 2. Chunk-level context fixes the cause, which is a chunk that does not say what it is about.
- Misconception: "to answer from a manual, put the manual in the prompt." Heads it off with the cost, context rot and window-size arguments from sections 1 and 2.
- Citations:
  - Long documents are split into chunks, indexed and retrieved; chunks lose context; prepending chunk-specific context helps - https://anthropic.com/news/contextual-retrieval
  - Just-in-time retrieval with lightweight references such as file paths and queries, and the hybrid with up-front loading - https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - Do not name or explain the search methods behind the index here (see Out of scope).

## Section 5: Main worked example and faded practice: design the assistant's memory (5 min, 750 words)
- Objectives: 1 to 4 together. No new terms.
- Task for the walk-through (about 380 words): design what the makerspace assistant does for one session, using the Monday/Thursday student from the opening. Produce a three-column table: Keep in the window now, Save between sessions, Find in the manual. Steps:
  1. List the pieces: instructions, tool definitions, the student's question, calendar result, manual pages, training status, booking confirmation, safety rules.
  2. Sort each piece with a reason tied to cost and rot. Instructions, tools and the question stay in the window. The calendar result is used, then cleared to one line. Training status is saved to a note and read at session start. The manual is found through `search_manual` and loaded only as the top chunks. Safety rules are small and always needed, so load them up front.
  3. Check the total: add up an invented per-call token budget and compare it with the paste-everything design. State the saving as a ratio, not a price.
  4. Write one sentence Riley could say at the design review for each of the three decisions.

## Section 6: Summary and Go further (3 min, 450 words)
- Summary (about 150 words): four lines, one per objective.
  - The window is everything the model sees on a call, and its size is what you pay for and what rots.
  - Between steps, keep the smallest set of tokens that lets the next step work, and clear or compact the rest.
  - Between sessions, only what you save outside the window survives, as small notes the program reads back.
  - For a long manual, retrieve a few chunks on demand, and give each chunk context of its own.
  - Prompt: "In your own words, explain to a teammate why we do not paste the manual into every request." Answer is not revealed, but give two points a good answer touches (cost per call and context rot).
