Context and memory: what the assistant keeps, saves and finds

By the end of this lesson you can decide what the makerspace assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long machine manual, and give a reason for each choice that fits a small budget.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (your earlier session)
Why this matters for you

Your assistant has to answer from long manuals and remember each student's training status between visits. It also has to do both on a small model budget. Every choice in this lesson is a choice you will defend at your design review.

Warm-up 3 min

Picture this. On Monday a student named Sam asks the assistant, "Can I use the laser cutter?" Sam then finishes the laser cutter training. On Thursday Sam asks the same question again.

The right answer on Thursday depends on a fact from Monday: Sam's training is done. Where can that fact live?

It cannot live in the model. The model knows only its training plus the text it is given, so Monday's chat is not in it. It also should not be everything said on Monday. Carrying Monday's whole chat, plus a 60-page manual, in every request would be slow and costly.

So the assistant needs three decisions. What do we keep in front of the model right now? What do we save for next time? How do we find the one right page in a long manual? Those are the three questions of this lesson.

The context window 5 min

Think of a game engine with a fixed memory budget for one frame. Whatever does not fit cannot be drawn this frame. A language model works the same way: it can use only what is in front of it on this call.

Two terms. A token is a small chunk of text, a word or part of a word. The model reads and writes tokens, and requests are limited and billed in tokens. The context window is the tokens the model is given on one call: instructions, the conversation, tool results and anything else the program adds. Anthropic defines context as the set of tokens included when the model writes its response.

Two more words, used throughout. A request is one student question. A call is one trip to the model. A request can need several calls (section 2 shows this), and cost is counted per call.

One more piece goes into every call: the tool definitions. A tool definition is a short description of a tool (its name, what it does, what input it takes). It is sent with every call, and it is how the model knows which tools it may ask for.

Every number in this lesson is invented, with round values so the arithmetic is easy. They are not real limits or prices for any model. Real limits and prices change, so look them up when you pick a model.
Worked example: one call of the assistant

The assistant gets the question "Is the laser cutter free on Friday?" The model first asked for check_calendar, and the program ran it. This is the second call of the request, and it carries the calendar result back to the model. The program builds a Python list for the call. The sizes are invented, and they leave out the model's own tool-request tokens to keep the arithmetic simple:

Part of the callTokens
Instructions ("You are the makerspace assistant...")400
Tool definitions (search_manual, check_calendar)300
The student's question20
Calendar result (a dump of the week's bookings)1,500
messages = [
    {"role": "system", "content": INSTRUCTIONS},   # about 400 tokens
    {"role": "user", "content": "Is the laser cutter free on Friday?"},  # about 20
]
tools = [search_manual_def, check_calendar_def]     # about 300 tokens
messages.append(calendar_result)                    # about 1,500 tokens
reply = call_model(messages, tools)  # the model sees only these

In the code, system marks the instructions and user marks the student's words. The tool definitions travel with the list on every call.

  1. Add up the call: 400 + 300 + 20 + 1,500 = 2,220, so about 2,200 tokens. That list, as text, is the context window for this call.
  2. The model's whole view is that list. If a fact is not in it, the model cannot use it.
  3. The window has a maximum size. If the list is over the maximum, the call fails or the program must cut something.
  4. Cost follows size. Every call sends its whole list, and the budget counts tokens. At 200 calls a day, that is 200 x 2,220 = 444,000 tokens a day (input only).
  5. Now compare a design that pastes the whole 60-page manual (invented: 40,000 tokens) into every call. Each call is 2,220 + 40,000 = 42,220 tokens, so 200 calls cost 200 x 42,220 = 8,444,000 a day. That is about 19 times more. This is a design to compare, not a rule.

Takeaway: the context window is the list of tokens given on one call, and its size sets both what the model can use and what each request costs.

A common mix-up

"The model remembers on its own." A chat feels like talking to one continuous mind, so it is tempting to think that telling the model your name once is enough. Try it in code:

call_model([{"role": "user", "content": "I'm Sam."}])
call_model([{"role": "user", "content": "What's my name?"}])  # no history sent

The second call has no name in it, so the model cannot know it. A chat app seems to remember because the program resends the earlier messages inside the list. That is a choice the program makes.

What stays between steps, and what to clear 5 min

Here is the key fact, and it closes a gap from the agent loop: every step is a separate model call. The model keeps nothing between calls. So the program resends the whole history, meaning the instructions, the question and every tool result so far, on each step.

A game that restored its state by replaying every frame since launch would be slow and full of noise. A good save keeps only the state that matters. An agent loop has the same problem, because its history only grows.

Two new terms. Context rot is the model using information less well as the window fills with more tokens. Anthropic describes context as a finite resource, with a limited attention budget, so a bigger context is not always better. Compaction is summarizing a long run when it nears the limit and starting a new window from the summary.

Worked example: "Book the 3D printer for 2 hours Friday afternoon"

The tools are check_calendar, search_manual and book_slot. Invented sizes: instructions 400, tool definitions 450, the question 25, so the start is 875 tokens. The calendar result is 1,500, a whole manual page is 3,000 (before section 4 improves this) and the booking confirmation is 50.

  1. Call 1 sends 875 tokens. The model asks for check_calendar.
  2. The program runs the tool, not the model. It adds the result to its history and makes a second, separate call: 
    history.append(tool_result)                       # the program adds it
reply = call_model(instructions, tools, history)  # a brand-new call
    Call 2 sends 875 + 1,500 = 2,375 tokens. The model asks for search_manual("3D printer booking rules").
  3. Call 3 sends 2,375 + 3,000 = 5,375 tokens. The model asks for book_slot.
  4. Call 4 sends 5,375 + 50 = 5,425 tokens, and the model writes the answer. The four calls total 875 + 2,375 + 5,375 + 5,425 = 14,050 tokens. Yet the model needed only one fact from the calendar ("Fri 14:00-16:00 free") and one rule from the page ("max 2 hours").
  5. Clear instead. After call 2 the model has used the calendar, so the program replaces it with a 30-token note: "calendar checked: Fri 14:00-16:00 free". After call 3 it replaces the page with "rule: max 2 h per booking" (30 tokens). Clearing old tool results like this is also something Anthropic's platform offers: it removes stale tool calls and results from the window.
  6. Recount. Call 1 is 875. Call 2 is 2,375. Call 3 is 875 + 30 + 3,000 = 3,905. Call 4 is 875 + 30 + 30 + 50 = 985. Total: 8,140 tokens, about 1.7 times fewer than 14,050, for the same booking.
  7. For a long chat nearing the limit, use compaction, the heavier tool. Suppose a 3,000-token chat becomes one summary: "Sam booked the 3D printer, Fri 14:00-16:00; prefers afternoons" (about 30 tokens). The booking and the student's choices are kept. Greetings and raw tool output are dropped. Clearing is the simpler tool, and Anthropic's post calls clearing old tool results a light-touch form of compaction.

Takeaway: between steps, keep the smallest set of tokens that still lets the model do the next step, and clear or compact the rest.

A common mix-up

"More context always helps, so keep everything." Throwing information away feels risky, and a bigger window sounds like a better one. But keeping everything cost 14,050 tokens against 8,140, for the same answer. It also adds noise: the one free slot sits among 1,500 tokens of other bookings. At this size the noise is small, but as windows grow it becomes context rot.

Check yourself

Show the answer

Second option. The confirmed booking is small and later steps depend on it. The greetings, the raw calendar and the old pages are noise once their one useful fact is kept.

Between sessions: notes as memory 4 min

A game's RAM is wiped when you quit, but the save file keeps your progress, so the next launch loads it. The assistant has the same split.

A session is one conversation from start to end. When it ends, its window is gone. Memory is information the assistant saves outside the window, such as a file, and reads back into a later window. Anthropic's memory tool works this way: a file-based store outside the context window, which persists across conversations and which the developer runs.

Worked example: Sam's training status

The assistant has a save_note tool and a folder with one file per student, such as students/sam.md. Invented sizes: instructions 400, tools 300, question 20, and Monday's whole chat 6,000 tokens.

  1. On Monday, after Sam's training, the model asks for save_note. The program, which your team wrote, runs it: 
    def save_note(student, line):
    with open(f"students/{student}.md", "a") as f:
        f.write(line + "\n")

save_note("sam", "laser cutter training: done, Mon")   # about 15 tokens
  2. The session ends and its window is discarded. Nothing is left inside the model.
  3. On Thursday a new window starts empty. The program reads the note into it first (a read_note tool that the model asks for would work the same way): 
    notes = open("students/sam.md").read()
instructions = INSTRUCTIONS + "\nStudent notes:\n" + notes
  4. The window now holds 400 + 300 + 15 + 20 = 735 tokens, and the model answers correctly: training is done.
  5. Reloading Monday's whole chat instead gives 400 + 300 + 6,000 + 20 = 6,720 tokens, about 9 times more, with the same fact buried in it.
  6. Notice who does what. The model only asks. Your team writes the tool and the storage. This is the agent loop again, with a file as the tool.
  7. What to save: facts that matter next time and are costly to find again, such as training done, preferences and open bookings. What not to save: raw tool output and whole chats.

Takeaway: between sessions only what is saved outside the window survives, and small notes read back into a new window are the cheapest way to carry it.

Anthropic describes structured note-taking: an agent writes notes outside the window and reads them back later. Their example is an agent playing Pokémon, which keeps maps and tallies in notes and reads them after a context reset to continue over thousands of steps.
A common mix-up

"Memory means the model was retrained, or has learned something." People say the assistant "learned" Sam's training, and Thursday's answer changes, so it looks like learning. Test it: delete the file and ask again.

os.remove("students/sam.md")   # same model, same Thursday question

The assistant now says it does not know Sam's status. The model never changed. The knowledge was in the file the program reads back.

Check yourself

Thursday's session starts, and Sam finished laser cutter training on Monday. What puts that fact into Thursday's window?

Show the answer

Fourth option. The note was saved to a file on Monday, and the program (or a read tool the model asks for) puts it into the new window. Nothing else carries the fact across sessions.

Retrieval: finding the right page 5 min

You do not read all of a game engine's documentation to learn one function. You search, open one page and read it. The assistant should do the same with a 60-page laser cutter manual, without loading it on every call.

Two terms. A chunk is a short piece of a long document, cut so it can be searched and loaded on its own. Retrieval is finding the few chunks that best match a question and putting only those in the window. Anthropic's write-up of contextual retrieval describes this setup: long documents are split into chunks, indexed and retrieved.

Worked example: "Why does the laser cutter show an air-assist error?"

The manual is about 40,000 tokens (invented, as in section 1). Cut into chunks of about 200 tokens, that gives 200 chunks.

  1. Prepare once, ahead of time. Cut the manual into chunks and store them in a searchable list: 
    chunks = [
    {"id": 41, "text": "If air assist fails, check the hose and the pump switch."},
    {"id": 87, "text": "Check that it is connected before starting."},
    # ... about 200 chunks
]
  2. The model asks for search_manual("air assist error"). The query is a small reference, not the whole document.
  3. Picture the search as scoring each chunk by how well its words fit the words of the question. How the scoring works is skipped here. The program returns the three highest scores, and only those go into the window: 3 x 200 = 600 tokens. Pasting everything sent 40,000, which is about 67 times more.
  4. The model answers from the chunks and names the page.
  5. Now a failure. Chunk 87 may hold the real fix, but "Check that it is connected before starting." never says which machine or which part. The word "it" and the topic are on other pages, so the chunk may not match "air assist" at all, or may match many unrelated questions. Chunks lose context when they are cut out of the document.
  6. The fix: before indexing, add a short line to each chunk that says what it is about. Someone, or a program, writes it from the manual's title and section headings: 
    chunk["text"] = ("Laser cutter manual, Troubleshooting, Air assist. "
                 + chunk["text"])
    Now chunk 87 contains the words a student would ask with. (The line adds about 15 tokens per chunk, invented.) Anthropic's article recommends this: prepending chunk-specific context to each chunk.
  7. Fetch chunks only when needed. The window holds just small references, such as manual names and section titles, and a chunk is fetched when the model asks for it. Short, always-needed text like the safety rules is put in from the start. Anthropic describes this mix of loading some data up front and fetching the rest on demand.

Takeaway: retrieval puts only the best few chunks into the window, and each chunk needs a line of context of its own so it can be found.

A common mix-up

"To answer from a manual, put the manual in the prompt." It is the simplest way to be sure the right page is present, and it is what you do when you paste a document into a chatbot. But the whole manual cost about 67 times the tokens of three chunks, on every call, and the right page sits among thousands of unrelated tokens, which is context rot. Retrieval loads only what this question needs.

Check yourself

Design the assistant's memory 5 min

Now put the three decisions together. No new terms here, only the ones you have met.

Worked example: one whole session

On Thursday Sam, who finished laser cutter training on Monday, asks: "Can I book the laser cutter for Friday afternoon?" These are invented sizes, reusing numbers from sections 1 to 3. This is a different tool set from section 2, with four tools.

PieceTokens
Instructions400
Tool definitions (check_calendar, search_manual, book_slot, save_note)400
Sam's question25
Calendar result1,500
Whole laser cutter manual40,000
Top three manual chunks600
Sam's training note15
Safety rules250
Booking confirmation50
A one-line note replacing a used result30
  1. Sort each piece, with a reason:
    PieceWhere it goesWhy
    Instructions, tools, questionKeep in the windowNeeded for every step
    Safety rules (250)Keep, loaded up frontSmall and always needed
    Calendar result (1,500)Keep for one step, then a 30-token lineLarge, and goes stale
    Training status (15)Save as a note, read in at session startSmall, stable, costly to rediscover
    Manual (40,000)Find: top chunks only (600)Too big to resend on every call
    Booking confirmation (50)KeepSmall, and needed for the answer
  2. Add up the budget. Call 1: 400 + 400 + 250 + 15 + 25 = 1,090. Call 2 (calendar added): 1,090 + 1,500 = 2,590. Call 3 (calendar now one line, chunks added): 1,090 + 30 + 600 = 1,720. Call 4 (chunks cleared to one line, confirmation added): 1,090 + 30 + 30 + 50 = 1,200. Total: 1,090 + 2,590 + 1,720 + 1,200 = 6,600 tokens.
  3. Compare with pasting everything. Instructions, tools, question and manual are 400 + 400 + 25 + 40,000 = 40,825. Call 2 adds the calendar (42,325), and call 3 adds the confirmation (42,375). Pasting the manual removes the search_manual step, so this design needs one call fewer. But the call count is not where the cost comes from; the 40,000-token manual in every call is. The total is 40,825 + 42,325 + 42,375 = 125,525 tokens, and it still does not know Sam's training. That is about 19 times more than 6,600.
  4. Write one sentence per decision for the design review:
    • Keep: "We keep only the instructions, tools, question and safety rules, and clear each tool result once it is used, because every kept token is resent on every call."
    • Save: "We save one small note per student outside the window, because the window is gone when the session ends."
    • Find: "We search the manual and load three chunks, not 60 pages, because that is about 67 times fewer tokens and less noise."

Takeaway: each piece goes where its size, how often it changes and how soon it is needed say it should go, and together the choices cut the cost per request by an order of magnitude.

Your turn, task A (half filled)

A student asks, "Can I book the 3D printer next week?" The first row is done: instructions (400), tools (400) and the question (25) are kept in the window, because every step needs them. Sort the other three pieces as keep, save or find, and write a reason for each: the next-week calendar result (1,800 tokens), the student's past bookings (12 entries, 400 tokens), and the 3D printer manual (30,000 tokens).

Show a solution

Calendar result: keep for one step, then clear to a one-line note. It is large and changes by the hour, and once the free slot is noted the rest is noise.

Past bookings: save only a one-line preference such as "prefers 2 h, afternoons". The full list is large and changes, so do not save it. If the exact list is needed, the model asks check_calendar and the result is cleared afterwards, as in section 2.

3D printer manual: find, loading only the top chunks. Thirty thousand tokens on every call is too much, and three chunks are about 600.

The most common misfilings are keeping the full calendar result for the whole session, and saving the whole chat or the full booking list. Both put large, changing text into every later window. Ask: does the model need these tokens for the next step, or the next session? If you put the manual under keep, recompute: 30,000 tokens times every call.

Summary 2 min

  • The context window is everything the model sees on a call. Its size is what you pay for, and a fuller window can make the model use it worse.
  • Between steps, keep the smallest set of tokens that lets the next step work, and clear or compact the rest.
  • Between sessions, only what you save outside the window survives, as small notes the program reads back.
  • For a long manual, retrieve a few chunks on demand, and give each chunk context of its own.

Say it in your own words: explain to a teammate why we do not paste the manual into every request. A good answer touches two points: the cost per call, and what happens to the model's use of the right page. Naming retrieval as the alternative is a bonus.
